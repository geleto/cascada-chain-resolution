# Ordered Array iteration and partial publication

Implementation design for [Phase 9](docs/runtime-evolution-plan.md#phase-9-implement-incremental-managed-access-and-iteration), using [queryable block layouts](array-layout-approaches.md) and [Variant B](docs/remap-structure-variant-B.md). The [Chain-mode contract](poison-policy-plan.md) is authoritative for the selected complete, sequential-stream, and unordered-stream policies, payload versus structural poison, fallback positions, markers, and [status-only repair](repair-simplification-plan.md). This plan specifies their Array integration and rollout. The kernel exposes all three cursor modes. The delivery stages below specify the embedding cutover and the checks on the shared layout. The [method implementation specification](docs/array-method-specification.md) supplies normalizer/correlation rules, coupled copying, sorting/flattening failure, placement roles, and work/lifetime obligations, including the [selected sort exception](#13-selected-decisions). Current kernel APIs, including bounded demand, item metadata and push-only entry, are documented in the [integration contract](docs/integration.md) and [entry contract](docs/enter.md). Update the authoritative runtime contracts as each new capability ships.

## 1. Scope and semantic changes

The standalone Chain package supplies managed Array operations, captures, cursors, entry reservations and failure publication. The embedding supplies one context with its compiler-declared external mutation tree. Compiled loop bodies, branch insertion, native iterator adapters and template loading are integration work in that embedding. [Kernel API](docs/integration.md)

Implement shallow iteration over captured managed Arrays, including ArrayViews and sparse Arrays. Sequential streaming issues the structurally published prefix in numeric order: membership, current index, clear slot status and final payload source are established, while payload values may remain pending or ordinary poison. Complete mode applies a strict captured-Array access gate; out-of-order mode (also called unordered stream) can deliver guaranteed surviving occurrences before their indexes settle. Cascada preserves logical command order under every mode.

The selected layout supplies shared partial Array state. Each controlled operation describes a source-to-destination mapping. Common machinery composes it with captured predecessors and answers shape, presence and value queries. Settlement advances affected facts without replaying operations. The ordered cursor keeps its next numeric position. Unordered discovery tracks distinct occurrences within the current demand and retains skipped causes through terminal delivery. Both use the same captured layout.

Under the selected mode's access rules, partial publication benefits ordinary reads, searches, copies, writes, and Error queries across independently available regions. In every mode, a possible whole-Array failure blocks access even to an unchanged region. More structural failures have that footprint in complete mode. Restricting iterator delivery to the prefix does not restrict the shared layout to prefix-only storage. [Section 8](#8-representation-and-lifetime-requirements) defines its integration; the layout document owns blocks, composition, optimization, and the selected storage design.

The immediate workload is a compiled loop over an Array whose positions become usable before all its data does: [pendingA,B], a remap of pending payloads, or a splice with a known insertion point and pending deletion count. The first two already benefit from captured placement versions; the third needs partial layout publication. Measure these separately. This revision does not assume that every pending structural operation exposes a useful prefix.

The kernel uses captured length bounds and in-range questions for indexed growth and partial layouts. Its public managed iterator and controlled Array methods consume those facts and the existing property versions. A mutation that can still fail the whole Array or a strict ancestor publishes a transition at that scope. Ordinary consumers, including iteration, pass through it before accessing the captured data. The broader-scope sort and repair witness exercises that boundary under all three delivery timings. [Regression tests](test/array-iteration.test.js)

### Sequential equivalence is the publication criterion

In every mode, run the same source program with the same inputs and host outcomes in all-ready issuance order. Its observable trace is the specification for ready and deferred execution, including failed operations. The same bodies run and the same reads, sparse presence, lengths, aliases, identities, application effects, causal failures and repaired data are observed. The comparison uses Cascada's controlled-method semantics. Unordered discovery may change physical scheduling. On actual overflow, every schedule uses the same [maximum logical count](#maximum-logical-count) for Array data and the same [native capacity fallback](docs/array-method-specification.md#native-diagnostic-list-capacity) when full consumption reaches an oversized Array or the Error report itself cannot fit. [Diagnostic ordering exceptions](docs/data-limitations.md#deterministic-error-reporting) leave language results and effects deterministic.

For compiled control flow, start the reference from the same source program, inputs and supported host outcomes. Which bodies and commands are issued is itself observable; do not feed an oracle only the commands chosen by the concurrent implementation. Compare conditional issuance, break/return, else selection, native effects and the first subsequent reads as well as final values. An earlier optional occurrence whose body breaks must prevent later conditional effects exactly as in the all-ready execution, even when that later occurrence was available first.

At a native boundary, keep the documented input contract in the reference program. A mutable external property returning `[thenable]` fails ready-data snapshot validation even for a synchronously fulfilling nested thenable. A property directly delivering `[A]` can instead supply a detached Array. For an already managed snapshot source, record the logical readiness required at that ordered host read. A pending identity decision alone permits capture and release of the native reservation. Compare schedules with the same snapshot inputs and host outcomes. Ordinary managed iteration over `[thenable]` transfers the payload to its binding. [External property snapshots](docs/data-limitations.md#external-operations)

Apply the existing late-first-registration exception at actual live native access. If an operation crosses an unregistered external alias and waits, first registration of that identity elsewhere blocks continued access. The all-ready call may already have performed its host effect. Record that specific route and outcome in the oracle. Managed occurrence selection, inert item transfer, repair and branch ordering retain their usual guarantees. [External authority and diagnostic exceptions](docs/data-limitations.md#deterministic-error-reporting)

The arrival sequence of [trusted unordered pulls](#unordered-pulls-are-a-scheduling-interface) is a scheduling trace, not the application's logical iteration order. Its physical first result can differ across delivery schedules. The compiler must preserve logical first-item selection, conditional execution, break/return and effects through ordered branches; a raw first-arrival selection is not an equivalent implementation of those language operations.

Before publishing any item, result or effect, establish that it is valid for every still-permitted success and failure of its earlier dependencies. If any such outcome can block the whole captured Array, reserve its transition before suspension and hold all publication through the affected scope, including writes whose effects repair could later expose. Pending controls retain their producers. Apply a fallback only on established relevant failure. The first item already delivered from a capture proves that no earlier work can subsequently fail that whole Array.

The proof covers intermediate observations and effects, not just final export. Capture a read before a write even if it settles afterward; later work consumes the appropriate successor. Already exposed results cannot be revised. Preserve duplicate occurrence multiplicity, holes versus present undefined, omitted versus explicit arguments, overlap source versions, and direct-result completion. Shape equality does not prove payload selection, and equal final contents do not erase writes. The [sequential-equivalence review](docs/iterate-sequential-equivalence-review.md) records concrete witnesses, the whole-Array ordering rule, and remaining integration obligations.

This revision changes the following contracts:

| Current rule | Replacement in this revision |
| --- | --- |
| A controlled structural mutation gates and, on failure, poisons its whole Array or selected broader scope. | Complete mode preserves that atomic data-publication rule: failed mutation leaves existing data under repairable own status. Streaming modes publish independent facts and use regional poison/fallback; sorting and explicit length assignment retain their whole-Array barriers. Broader authority does not enlarge streaming regional coverage. |
| A failed managed mutation retains its selected scope's data. | Complete-mode candidate changes remain private until success; failure marks retained current data. Streaming regional changes can commit independently. Repair clears own status without restoring a predecessor. Native isolation remains necessary. |
| Result layout construction finishes before handoff; payloads may remain pending. | A valid prepared Array may also contain pending or failed layout facts. Required call validation still precedes result-root handoff. |
| Controlled argument preparation can fail before determining whether an argument affects the operation. | Determine actual dependencies first. A poisoned, invalid, or pending argument cannot fail or delay effects/results proved independent of it. |
| Captured Array structure has numeric placements and pending value deliveries. | A partial layout can also retain children before their destination keys are known. Captures protect those dependencies; parent edges cover established placements, while aggregate queries also account for output-relevant deferred regions. |

Streaming controlled commands can commit independent changes. A committed independent write survives another region's failure, and later commands can use healthy facts without repairing the whole Array first. Later work consumes the declared fallback and any actual remaining failure dependencies; one failed region does not abort every fact of that later command. Complete mode does not expose candidate changes before successful mutation completion: required failure marks the retained Array or explicitly selected broader scope. Repair clears status over that current data, with no rollback. Required source relationships survive composition; adding stronger independence rules is a semantic decision, not a storage optimization. Regional repair is deliberately unavailable. Restoring an explicitly saved predecessor as a new assignment remains possible; automatic restoration could discard intervening effects.

Mutation scope still selects authority, ordering, and path-failure ownership. The revised regional footprint applies after successful selection of a controlled Array operation. Opaque native managed calls retain selected-scope isolation and failure ownership; access through their retained path status follows the Chain policy after its cutover. Narrowing native failure to the receiver would be a separate architecture revision, not a consequence silently inferred here.

Successful valid-input mappings retain the existing controlled-method semantics, including holes, fixed external locations, ownership, and write-based identity. Use existing argument conversion only where that argument is needed. Skipping irrelevant conversion/validation and publishing independent effects after failure are deliberate semantic revisions; JavaScript's eager validation and abrupt completion are not their reference behavior. Ready failure and deferred failure use the same revised reference execution.

Native host iterators and their finalization remain Phase 8 work. Object enumeration, new Array method names, and a separate append-only stream API are outside this revision. Here, streaming means incremental delivery of the Array at the iterator's logical command position. Later commands are excluded; all logically earlier commands are included, even if some have not settled.

### Complete mode: strict access

The [complete-mode contract](poison-policy-plan.md#complete-mode) preserves atomic mutation failure and forbids ordinary access through whole-Array poison. Before consuming a captured Array, prove that logically earlier work cannot still poison it or an applicable ancestor scope. An unresolved relevant outcome waits; established poison propagates without exposing the retained prefix. A clear physical flag is not a readiness proof.

The shared [access gate](poison-policy-plan.md#complete-access-gate) covers lookup/observations, method receiver selection, assignment/deletion inside the Array, iteration including successful empty completion, export/native graph preparation including nested Arrays, and direct result publication. Internal reference capture may carry the gate. Error queries, repair and permitted whole-Array replacement/deletion keep their own contracts; none requires the selected value to be healthy. No deep payload scan or repeated per-item health check is added.

The [complete-mode validity rules](poison-policy-plan.md#tracking-complete-mode-validity) derive the gate from captured failure ownership, required validation/publication and relevant issuer closure. Register dependencies before suspension and discharge them on completion or proved irrelevance. Neither healthy arguments nor zero pending commands establish safety while an issuer can still introduce a relevant failure. Reuse existing transition/placement and producer facts; add no failure-history ledger or second scheduler. Once validity is established, remaining payload/layout dependencies need not all settle before the first established occurrence is consumed.

A failed mutation leaves retained current data under selected-scope status; repair exposes those data. Earlier successful commands remain committed. A failed copy returns root Error. Receiving the failed capture in another mode preserves its blocker.

The gate belongs to the predecessor at this operation's logical position. Producer commands consume their private earlier-command view, never the enclosing output they are creating; later mutations cannot invalidate an earlier capture. An outside consumer of an open producer waits while that producer can still introduce whole-Array poison. Its completion must not depend on consuming the same gated output. Stored payloads may remain pending when they cannot poison the Array itself.

### Sequential-stream mode: ordered prefix

The [sequential-stream contract](poison-policy-plan.md#sequential-stream-mode) delivers established occurrences in numeric order. Each needs final membership, the captured numeric index, clear slot status and a final payload source. An accepted fallback or successful exact repair supplies ordinary coordinates for subsequent captures. Ordinary reads and writes may use other independently established regions; iterator prefix order does not restrict layout storage to a prefix.

On actual structural failure, deterministic fallback retains guaranteed survivors with own status where their intended positions are lost; uncertain contents/survival become structural Error data. The iterator reports its first structural obstruction. Whole-Array or ancestor failure blocks all positions of that version. Exact-path repair clears its own status for later commands.

### Out-of-order-stream mode: guaranteed survivors

The unordered stages implement the selected unordered-stream mode, followed by bounded-window integration. Deliver a guaranteed surviving occurrence with its final captured payload dependency before its numeric index is known. Neither payload readiness nor an optional index query gates unrelated body work. Do not emit an occurrence that may still be deleted or overwritten.

Keep three facts distinct:

- **Published sequential occurrence:** membership, current numeric index, clear slot status and payload source are established. The payload can remain pending or ordinary poison.
- **Published unordered occurrence:** survival, clear slot status and the final payload source are established. Its index can remain pending.
- **Fallback position:** after a relevant positional failure, the selected recovery layout supplies a deterministic position. This is not proof of the position originally requested.

After a=[A,B]; a!.splice(P,0,X), failed P uses fallback [A,B,X]. Sequential mode flags the potentially misplaced occurrences; unordered mode leaves all three usable and adds no positional marker or Array-path poison. A marker is for possibly missing output, not lost order. The [mode contract](poison-policy-plan.md#2-failure-categories-and-fallback-layouts) owns these outcomes.

The two streaming modes intentionally make different ordering/failure guarantees. Each must match its own all-ready reference execution for the same inputs and failures; changing settlement order cannot change its result. Array access, fallback, and later effects remain in logical issuance order, never arrival order.

An index future resolves from the captured successful or fallback layout when its required facts are available; it may remain pending behind a required dependency. Position-only failure in unordered mode does not automatically poison that future. Actual root/publication failure keeps its normal failure channel. The scheduler gives the body its captured position as a Number or guarded future. Existing loop metadata projects from that position and the same captured shape.

Occurrence discovery must distinguish duplicate copies of one payload, deliver each occurrence once, and release its uses without rescanning unresolved slots. The layout supplies these facts; Cascada owns command-buffer ordering, pacing, and the existing Array loop metadata. Extend the existing command-buffer tree without adding another Array layout hierarchy or layout engine. Preserve that metadata at the first compiled cutover.

The selected ordering design is [indexed command-buffer branches](#indexed-branches-for-unordered-bodies): receive an occurrence before its position is ready, and give its body branch that captured position as a Number or future. Corresponding branches in every used Chain's buffer share that ordering fact. Mutations and order-sensitive control follow final captured/fallback order; observations may run early when their required mutation interval is already established. Delivery or Promise settlement never becomes logical precedence.

### Pending mutations versus unknown future commands

An entry reserves the producer's logical position while its callback may still issue commands. The table describes structural progress. All modes order the successor behind any earlier command or issuer that can still poison the whole Array. Once that possibility is excluded, each mode applies its declared regional or complete publication rules.

| Producer state | Required consumer behavior |
| --- | --- |
| Relevant commands have been issued with pending arguments, payloads or regional effects | Preserve their captured dependencies. Once whole-scope failure is excluded, publish independently determined regions under the selected mode. The ordered streaming cursor can deliver the established prefix. |
| An entry has closed its reference while contained work remains unfinished | Hand off its captured successor with all required gates intact. An open nested issuer or already-issued command that could still fail the Array gates dependent operations. Unrelated body or native completion keeps its own lifetime. |
| An entry may still issue an unrestricted mutation of this Array before the consumer's logical position | A current prefix is provisional. The remaining commands could clear, replace, or reorder it. Existing path-only access declarations cannot prove it final. Preserve protection until issuance closes or a sufficient remaining-effect guarantee exists. |

The desired optimization is proof of a final observable region, not an append-only requirement. Append-only production is one sufficient restriction; a sealed range or a guaranteed unaffected final suffix can also suffice. Path-only entry declares paths and mutation authority. Push-only entry supplies a narrower mutation contract. Shape bounds and failure coverage remain separate prerequisites. Do not infer a remaining-effect guarantee from commands observed so far or impose this open-issuance limitation on the first two rows.

For a loop that issues every push with a pending payload, the consumer need not await those payloads. Once command issuance closes, it can traverse the resulting captured positions. When future iterations themselves are unknown and can issue more mutations, the missing fact is what those earlier commands may do, not whether existing values are ready.

**Follow-up: push-only entered references.** The [entry extension](array-layout-approaches.md#46-follow-up-open-append-regions-in-enter) declares and enforces the capability per reference, including nested calls and overlap. It reuses the layout queries and cursor and represents later pushes behind an earlier open contribution before their absolute indexes are known. Private reads use the command prefix; outside consumers capture the eventual post-entry version.

Land the mode/failure foundation first. In streaming modes, failed conditional or enumeration control uses compiler-selected targets and the declared structural footprint: preserve issued contributions, represent possibly missing output with the one marker when required, and retain genuine path failures where applicable. Independent result failure and pushed payload rejection keep their narrower effects. Both streaming modes still require final occurrence facts, capacity, and authority; neither bypasses a genuine path blocker. Use the kernel's push-only entry for a proved append contribution and ordinary coordinated entry for wider coverage.

An open push-only producer is an ordered sequence of append commands, not one atomic append of its unknown eventual total. Validate each issued append and its selected destination capacity. In complete mode, those internal commits do not authorize outside consumption while producer failure could still poison the captured output; failed production retains earlier committed data under blocking status. In streaming modes, no bound on every future append is required before exposing an established prefix that all remaining work preserves. Capacity failure creates the declared poisoned tail without blocking the prefix; other failure categories retain their own specified status or marker rules.

Actual overflow needs no extra marker slot or exhaustive traversal merely to publish/query poison. A Complete producer's capacity failure blocks every consumer of that captured scope. A streaming producer retains its unaffected prefix and publishes structural Error in the tail. A Complete cursor receiving that streaming capture can deliver its prefix and stops at the first obstruction. Already delivered values and completed earlier results remain unchanged. An unordered later contribution still needs its own membership, placement/capacity proof and ordering prerequisites; an open tail is not permission to guess those facts.

## 2. The logical model

### Independent facts

At a captured program position, distinguish:

| Fact | Possible answer |
| --- | --- |
| Array root/category | A managed Array, pending root, or root Error |
| Captured Array access validity | Ordinary access is established, waits on an earlier transition that can block this scope, or reports the owning or ancestor failure. |
| Exact length | A Number, pending dependency, or structural Error |
| In-range at numeric index i | True, false, pending dependency, or structural Error |
| Own presence at i | Present, absent, pending dependency, or presence Error |
| Value at i | A language value, pending dependency, or Error |

Length bounds remain useful when exact length is pending or failed. A hole inside length is an iteration occurrence yielding undefined; absence is still distinct from present undefined for copying, searches, and writes. Unknown layout is not a hole. An Error in presence or mapping is not proof that the position is out of range.

Ask only for facts required by the consumer. A definitely absent property reads as undefined whether it is an in-range hole or outside length, so ordinary lookup need not consume an unresolved in-range fact in that case. Iteration still needs existence to decide whether to issue that position. All consumers retain root/path prerequisites.

Sparse occurrences also carry captured status. A positional flag on an in-range hole blocks that occurrence without creating a present undefined element or a managed-child parent edge. Store such status with the absent-slot fact or a symbolic span; ordinary access checks it before using absence to return undefined. Repair clears the status and preserves the hole. Structural moves/copies preserve hole status, densifying methods preserve the status while creating their specified undefined placement, and explicit overwrite/deletion removes the selected status. For `new Array(2)` followed by failed-position pure insertion of X, sequential fallback retains two flagged holes and flagged X; unordered fallback retains two distinct healthy hole occurrences and X. Permanent structural Error and marker slots remain actual present Error data.

Availability is monotonic within one captured version: a delivered fact cannot be retracted. A later command creates a successor version; it does not revise an earlier capture. Value readiness means the element root is available, not that its descendants have settled.

### Guaranteed prefix, independently of ready values

Sequential publication needs more than inRange(i)=true. Establish which surviving occurrence supplies slot i, including all earlier writes that could delete, replace, or move it. Capture its final payload producer before exposing the step. A known hole yields undefined. Later commands use successor versions.

[pendingA,B] issues both positions immediately: the placements are final and only their values remain pending. An already-poisoned payload is also an ordinary item. In contrast, a Promise that must first choose between A and X after an unresolved splice is a structural selection dependency. Do not issue it as if it were a pending payload; it could later become structurally poisoned.

Length bounds guide membership and absence. A lower bound m proves [0,m) exist but does not prove their source selections. Apply the required shape/selector reductions at the next position and wait only for unresolved structural prerequisites. Numeric lookup may return a Promise for a still-unknown selection; iterator delivery has the stronger published-occurrence requirement.

Perfect publication is not required. Conservative delay beyond the specified bounded rules is acceptable; premature publication, extra timing-dependent poison, and fallback that retracts an issued fact are not. Include the selected failure outcomes in bounds and publication proofs.

Use one common fact interface for operation-local shape, presence, source selection, survival, and payload capture. fill/copyWithin/reverse preserve length; capacity-safe push/unshift adds known argument count; pop/shift use max(0,L-1); splice uses its normalized ranges. A marker contributes its declared one-slot fallback only where applicable. Preserve necessary captured relationships without a general solver.

Complete mode establishes its captured-version access validity and the requested structural facts before consumption, not unrelated payload health. Unordered mode requires survival and final payload source but can omit the numeric-position prerequisite. All modes retain root, authority, and capacity requirements.

A healthy streaming Array can expose its structurally established prefix while later slots remain unresolved. If an earlier operation or open issuer can still poison this whole captured Array, even the first item and successful empty exhaustion must wait. Once issued, a later operation targets a successor and cannot invalidate an earlier capture. [Whole-Array failure and ordered repair](poison-policy-plan.md#whole-array-failure-and-ordered-repair)

### Fact evaluation and failure dependencies

Each controlled operation defines its successor from captured operands. Facts independent of an unfinished operand can be published immediately. If that operand fails, dependent facts expose its contextual Error while independent facts retain their own values and producers.

Do not classify failure by what happened to be ready when it arrived, by whether someone already observed a region, or by which physical representation was selected. Ready poison, a synchronously delivered rejection, and a later rejection must produce equivalent facts and effects.

Apply the [common availability and failure contract](AGENTS.md#errors), with this plan's explicit mode/fallback revision: fallback indexes are selected recovery positions, not claims that the intended positions were established. Update that production contract at the [migration cutover](#migration-inventory). The reference model must state the supported reductions and resulting failure footprints before production; an uncovered failed-input case is a specification gap, not an implementation-selected Error. Delivering an elem Chain establishes its occurrence and final payload source, not a healthy eventual payload. Sequential delivery also establishes the occurrence’s numeric index in this capture. Unordered delivery carries its captured index separately. Both consume an accepted fallback in the producer’s retained order.

Use one evaluation rule for ready, pending, invalid, and poisoned controls:

1. Describe a needed control by its normalized semantic range and constraints. For splice, 0 <= d <= L-s. Pending controls retain alternatives. A failed control retains the information needed to prove relevance and select the declared mode-specific failure/fallback; do not choose an arbitrary successful input value. Other captured facts may still prove the control irrelevant.
2. Evaluate each output fact from the method's mapping, using range arithmetic, conditional selection, and exact captured source selectors. A selector names a source placement/version, an argument payload slot, a hole, or a prescribed literal. When a supported rule establishes that every remaining alternative selects the same fact, forward it without the control dependency. Failure to establish that proof remains uncertainty, not permission to guess. Distinct payloads that happen to compare equal are not the same selector.
3. Preserve constraints and captured source relationships required by the semantic rules, such as d <= L-s. An internal conservative approximation may admit extra possibilities, but must not turn those invented alternatives into extra failure or withhold a required answer. For `copyWithin`, the selector is the immediate predecessor position. Alternatives among clean holes are equivalent. Distinct positions with any present or flagged candidate depend on the control regardless of their earlier producer. Other mappings preserve the captured source relationships their rules require. No general symbolic constraint solver or production enumeration is required; extending the supported dependency rules is a contract change.
4. Retain required pending dependencies until selection or relevance is established. After actual relevant failure, apply the declared footprint: complete-mode mutation status over unchanged data or copying-result Error, permanent structural poison, sequential positional status, unordered survivor fallback, missing-output marker, or the streaming sort exception. Do not finalize a failure while another required fact can eliminate or change it. The mode's actual retained frontier determines Error collection; unordered position-only fallback creates no duplicate Array Error.
5. Evaluate prescribed writes and operation completion separately from resulting values, using the method's semantic no-op rules. In particular, controlled copyWithin with provably identical normalized source/destination starts prescribes no writes, even when end is pending or poison. Other required writes retain their specified effects and failure footprints; equal payloads alone do not erase an explicit assignment or earlier command's effects.

The successful semantic range describes uncertainty, not validation success. An impossible request remains an independent validation failure; an empty set of valid indexes does not make with on an empty Array vacuously valid. Authority and required external-action failure are also not hypothetical successful argument values.

Return a determined result immediately, even when some arguments are pending, invalid, or poisoned. An eager preparation order or an incomplete list of examples is not evidence that an input is required. The evaluator uses structural range/shape simplification, identical selectors, ordinary available comparisons, and absorbing Boolean results such as false AND unknown. Apply proofs equally to ready and deferred failures and keep the reference model aligned. Do not speculate about sorted prefixes or search combinations of hypothetical comparison outcomes. These limits on proof work do not justify withholding an answer already established by ordinary comparisons or mapping composition.

An input is required only while a prescribed effect or returned fact depends on it. A method's argument table identifies potential inputs, not unconditional conversion or Error-collection obligations. Preserve complete collection for the actual dependency set; exclude inputs proved irrelevant. A conversion failure cannot make its own otherwise-unused argument required.

### Shared inputs and occurrences

Preserve sharing already explicit in internal captured layout/control facts. One internal fact has one outcome; repeated use must not turn it into independent hypothetical values. Each method argument position is an independent control, even when two positions receive the same variable, Promise, or Error. This does not prevent comparing successful normalized numeric values when they become available.

Reusing a source, as in concat(a,a), creates separate destination occurrences and parent keys. Shared payload identity does not merge them.

For one=[X], a=one.concat(one), followed by a!.splice(p,1), successful starts 0, 1 and 2 all select the same captured X payload at output index zero, but neither input occurrence survives every start. A proved positional payload selection therefore does not establish that either original occurrence can be emitted early by unordered discovery. This successful-selector witness does not bypass required failure/status proofs. Preserve the distinction in iteration, searches, parent relationships, Error queries and prescribed writes; it needs no broader callback/provenance optimization.

### Captured control identity at the API boundary

Each argument position starts an independent control. Neither exact Promise identity nor a common Error establishes a shared coordinate; separate lookup wrappers obey the same rule. Add no wrapper/provenance API, cross-argument identity inference, or Error comparison for this purpose.

For copyWithin, compare normalized numeric starts when available. Equal starts prescribe no writes regardless of where the numbers came from; otherwise wait for required controls unless normalization/shape facts already prove equality for every independent possibility, as on an empty Array. Incidental Promise wrapping or delivery timing cannot select a different poison outcome.

Keep local same-control folding only for internal facts reused by a mapping, such as one normalized deletion count used in both removed and retained extents, or the two sides of one split. It does not merge distinct argument positions. For nonempty `a.slice(x,x)`, equal successful numeric bounds give an empty result; failed bounds are independent controls even if x is one rejected Promise or one ready poison. In streaming modes, raw failed bounds produce the full-length structural-Error fallback; complete mode returns root Error. Test these forms and separately wrapped reads against the same reference, while testing internal shared-fact reductions separately.

### Structural proofs and payload inspection

Reductions are fact-specific. Equal payload selectors do not establish equal presence, positional status, or structural role. A healthy hole and a flagged hole both yield undefined only after different access prerequisites; a structural Error and an ordinary payload Error can share the same Error object but have different iteration/search behavior. Coalescing or forwarding must preserve every fact consumed by the result. An unchanged value does not prove unchanged writes or status.

Use captured shape, bounds, equivalent coordinates, shared selectors, and repeated-source blocks to establish independence. These facts must survive composition and materialization wherever the specified result relies on them. Do not add an old-value equality pass, or await old payloads solely to avoid a write or preserve identity. The rule is the same for ready and pending payloads.

Reads, searches, conversions, and sorting still inspect the values their actual algorithm needs. This restriction on extra equality work does not suppress ordinary comparisons or their short-circuit results. Repeated payload provenance is not permission to skip a required sort comparison, callback, or conversion: the same logical input must have the same result and failure dependencies whether built by a literal, fill, copying, or materialization. Only the method's semantic comparison-free cases, such as fewer than two sortable occurrences, remove comparator work. The method's prescribed writes and identity outcome remain separate.

### Universal rule: irrelevant arguments never introduce poison

The [universal dependency rule](AGENTS.md#errors) governs every argument and independent outcome. The Array-specific rules below apply it under the explicit mode/fallback revision described above; they do not limit its scope.

If an input Error is ready while the proof of its relevance is pending, keep that Error conditional. For example, fill with failed bounds cannot fail immediately while an earlier shape dependency may still establish an empty receiver. Complete available proofs before deciding the failure frontier. Provisional input reception already required for ownership is not a reason to retain an irrelevant Error in the outcome.

When a proof removes a dependency, release that operation's unused captures, waits, and Error-collection state. Preserve already-owned rejection handling and shared settlement needed by other consumers; do not cancel the input or attach observers to otherwise unconsumed host inputs. If the receiver's length bound already proves at most one sortable occurrence, do not resolve that occurrence merely to prove that its comparator is unused.

In the examples below, P is an ordinary poison or a pending input that later rejects. The necessary shape/presence facts are known; omitted inputs retain ordinary defaults.

| Operation or proof | Determined behavior despite P |
| --- | --- |
| Empty a: a!.fill(P,P,P), a!.copyWithin(P,P,P) | No writes; return a unchanged. Observation mode returns the ordinary distinct empty Array. No new poison. |
| Empty a: a.at(P) | Return undefined; the index cannot select any occurrence. |
| Empty a: a.includes(P,P), a.indexOf(P,P), a.lastIndexOf(P,P) | Return false, -1, -1 respectively. There is no candidate comparison. |
| Empty a: a.slice(P,P), a.flat(P), a.toSorted(P) | Return a fresh empty Array; bounds, depth, or comparator cannot affect it. Empty a!.sort(P) returns a without a write. |
| a.join(P), length 0 or 1 | Return "" at length 0; at length 1 convert only that occurrence. No separator is used. An Error in the occurrence still propagates. |
| a!.fill(P,P,0), or a!.copyWithin(P,0,0) | The selected write interval is empty regardless of the unknown bound/target. Return a; preserve existing data poison without introducing argument poison. |
| a!.copyWithin(0,0,P) | Source and destination positions are identical for every end. Return a unchanged, preserve identity, and ignore end; no mutation copy or identity poison is needed. |
| a.slice(P,0) | Return a fresh empty Array; every normalized start is at least the normalized end 0. |
| a!.splice(P,0), with no inserted arguments | Removed result is []; contents are unchanged. Preserve the captured shape and perform the prescribed same-length write without consuming start. Existing root/shape failures remain; start adds none. toSpliced(P,0) returns the ordinary dense copy subject to its result boundary. |
| Empty a: a!.splice(P,P,"X") | Start and deletion count normalize to 0. Publish ["X"] and return []; neither control argument is needed. This is a determined effect, not a no-op. |
| sort/toSorted with fewer than two non-undefined sortable occurrences | Comparator selection, validation, export, and invocation are unnecessary. Preserve the normal known permutation, holes/dense semantics, and prescribed writes. Example: [7,undefined] has no comparator dependency. |

| A search range proved empty | includes returns false; indexOf/lastIndexOf return -1 without consuming the search argument. On an all-hole Array, indexOf/lastIndexOf return −1. Includes reads each eligible slot through its status. A clear hole compares as undefined, and a flagged hole supplies its obstruction unless an independent hit settles the search. |
| [1].indexOf(2,P), [1].lastIndexOf(2,P), [1].includes(2,P) | Return -1, -1, false immediately. The only possible candidate is a known mismatch, whether the range includes it or not. |

These proofs use shape, bounds, argument count, and the algorithm's actual comparisons/mapping. They do not compare alternative payloads to guess equivalence. Equal before/after values do not prove a no-op: same-value writes still affect identity. Existing zero-argument endpoint-mutator length writes remain prescribed effects. A deterministic result does not erase an independent required effect or its failure.

Some arguments remain necessary. A nonempty [A,B].with(P,"X") cannot select or validate its replacement index; a.includes(P) with candidate occurrences cannot decide whether they match; a.concat(P) cannot classify the appended part. Stored poison is data: a valid with(0,P) produces an Array containing P, and an inserted splice/push payload poisons its actual placement rather than disappearing as an unused control.

Receiver selection, supported dispatch, authority, and fatal failure are prerequisites, not optional arguments. Do not inspect a poisoned path's hidden value to prove emptiness. Opaque native calls do not inherit these controlled-operation proofs. Intrinsic invalidity also remains failure: an empty Array has no valid with index, and capacity overflow prevents a requested write. Neither is a proved successful no-op. Report that independent validation failure without consuming irrelevant argument poison.

This removes eager-validation ordering where it manufactured dependencies. In particular, comparator readiness no longer precedes the proof that no comparisons are needed. Do not add a separate poison-only fast path: valid, pending, invalid, and poisoned inputs use the same demand-driven preparation.

### Example: partial splice

For a streaming Chain:

    a = [A,B,C,D]
    removed = a!.splice(2,pendingCount,"X")

Normalized deletion count is in [0,2]. Once capacity and publication prerequisites are safe, A/B/X have final positions 0/1/2. Their payloads need not be ready. The remaining receiver layout and the separate removed-elements result depend on the count.

While the count is pending, length bounds are [3,5]; positions 3/4 have uncertain membership/selection. If the count fails, the selected streaming fallback is [A,B,X,Error,Error], length five: C/D may have been deleted and are permanently poisoned. Both streams retain the clean prefix of three; unordered delivery may also use any other guaranteed survivors in more general cases. The removed result is poison because its required count failed.

Complete mode exposes no candidate changes: on this mutation failure it flags the retained [A,B,C,D], and repair exposes those unchanged data. In streaming modes repair cannot restore C/D or undo X; explicit replacement remains available. Ready poison and delayed rejection follow the same mode-specific outcome.

Capacity is mode-specific. Complete mode requires total validity before consumption. Streaming fallback uses structural Error beyond the successful Array limit and preserves unaffected published facts; only positions whose payload preservation depends on unresolved controls need that wait. Section 12 defines the capped logical extent without a permanently frozen poisoned-size state or a global streaming capacity gate.

## 3. Controlled operation rules

### Method catalogue and mappings

All 22 current names in ARRAY_METHODS participate. The nine mutation-capable names are copyWithin, fill, pop, push, reverse, shift, sort, splice, and unshift. Without !, each returns a transformed copy and preserves its source. With !, it publishes receiver changes and returns the JavaScript result: push/unshift length, pop/shift removed value, splice removed elements, and the receiver for the other four. Retain the current uniform observation-copy contract; this supersedes the earlier proposal to change five observation return types.

Source and destination dependencies are separate: a failed copyWithin source contributes failure to dependent destinations, not to its original source positions. A failed deletion count affects splice layout. Streaming receivers can release the independent prefix after excluding whole-scope failure. A Complete mutation with a required failed count blocks that entire receiver capture.

Successful mutation identity follows logical writes, not value equality. Same-value assignment is a write; an empty fill range is not. Preserve presence-sensitive no-op rules for reverse, copyWithin, and sort, add the proved self-copy rule above, and retain specified length writes of endpoint mutators.

The current PASS_AS_PAYLOAD behavior already handles pending/rejected inserted values for push, unshift, fill, splice, with, and copying methods. Preserve it. Do not add another transport for payload Errors. Preparation must stop discarding all success payloads merely because an independent structural argument failed: retain exactly the payloads used by surviving output facts.

Apply the determined-outcome rules through the same method dependency descriptions, including at, searches, join, slice, flat, sort, and copying forms. Check argument preparation and comparator demand at the public method boundary against the same examples in all modes. Empty/presence/range proofs can eliminate inputs before conversion; available structural arguments can prove another argument unused. Do not add a second no-op dispatcher alongside the normal algorithm.

For sort, establish comparator relevance and selection separately from callback-only preparation. Once a required supplied comparator is invalid or poisoned, do not switch to default sorting or await/export descendants used only by that callback. Any retained data keeps its original payload producers. Callback-only preparation failures remain conditional on that preparation being needed, regardless of which settles first. Source classification, presence, failure publication, and independent effects retain their own required work; fatal failures are never masked.

Invalid dispatch, unsupported names/modes, selection failure, and authority rejection keep their existing classification and owning-path failure rules. They are not fictitious regional Array operations. A supported selected operation's argument, mapping, comparison, and publication failures follow this specification. No custom Array property, accessor, prototype method, Symbol protocol, or host iterator participates.

### Search demand and completion

Pending membership is not poison. After [A,B,C,D].splice(2,pendingCount,X), includes(D) must wait while normalized count may be 0, 1, or 2: D survives for 0/1 and is removed for 2. If the count fulfills, return exactly that successful sequential answer. In either streaming mode, includes(X) may already be true after root/capacity prerequisites. For a Z distinct from every payload, includes(Z) still waits: all successful counts give false, but a relevant count rejection produces structural Error slots and the search must report their cause. Complete mode first waits on its shared Array gate for both searches. Neither uncertainty nor the current set of delivered occurrences permits an early false or Error.

A negative proof covers all permitted outcomes, including structural failure, not just successful candidate values. Structural selection failure and missing-output markers are not ordinary payloads that can be compared as mismatches. A real match may make those other regions irrelevant under includes' any-match rule; absent that match, retain a dependency able to introduce a relevant structural failure. Ordinary payload poison keeps its separate comparison rules. Conversely, a control affecting only eligibility may still be irrelevant when every actual candidate is a known mismatch. Do not turn this distinction into an unconditional Error scan or whole-layout wait.

Share the unordered occurrence-discovery machinery with includes, without changing the source Chain's mode or exposing an iterator as another semantic operation. A search needs a complete possible-candidate frontier, range eligibility, hole semantics, payload/identity comparison, and closure of every still-relevant dependency before a negative result. An iterator that has merely delivered all currently ready survivors is not exhausted. Reuse internal captured occurrences and query state; do not allocate an elem Chain per comparison or drain a public iterator solely to implement a search. indexOf/lastIndexOf also need directional exclusion and an exact numeric answer.

For each possible candidate i, separate eligibility E(i) from comparison M(i). Eligibility includes range membership and, for indexOf/lastIndexOf, own presence. A hit requires E(i) AND M(i). Either known false operand makes that candidate a non-hit without awaiting or propagating poison from the other. Thus a known mismatch removes dependence on a pending/failed start, just as a known excluded position removes dependence on its value. Comparison uses ordinary captured language values and identity rules; do not inspect a hidden predecessor to invent a positional value.

A candidate can be a captured block occurrence whose absolute index remains unresolved. Includes needs an in-range slot and a visible match, including undefined from a healthy hole. Directional search additionally needs own presence, and returning the matching index needs the occurrence's absolute coordinate. Use the same range eligibility rules in either coordinate system.

- includes returns true when a definitely eligible candidate matches. It returns false when every possible candidate is a known non-hit and no relevant structural-failure outcome remains, even if the exact selected range remains unknown.
- indexOf/lastIndexOf return a matching index when it is definitely eligible and all possible candidates before it in their search direction are non-hits with no relevant structural failure. They return -1 when the full frontier satisfies that proof. A known mismatch may be inspected past a pending range control; it does not authorize returning a later match past an unresolved possible earlier hit or structural failure.
- Once the first required obstruction in the search direction is established, release the suffix in that direction. Any-match search retains a possible hit on either side. [Directional failure witness](docs/array-method-specification.md#9-searches-and-scalar-producers)
- Keep uncertain eligibility and its Errors conditional. A later established mismatch removes them; a later exclusion removes a comparison Error. Propagate only failures still required for the result after these reductions, following the existing any-match/directional completion rules. Arrival order must not choose between an early Error and a subsequently proved deterministic answer.

Scan the union of possible candidate positions at most once under maintained captured bounds, narrowing it as facts settle. Empty and hole ranges remain symbolic; indexOf/lastIndexOf skip definite holes, while includes can reuse the comparison with undefined across a definite hole range. Do not require exact length merely to certify that this union is complete. If possible additional positions or required comparisons remain unresolved, retain those dependencies. Cache candidate decisions and aggregate progress rather than rescan all candidates on each settlement. Required work is bounded by relevant source structure, comparisons, and pending dependencies; it does not enumerate combinations of possible starts or comparison outcomes.

### Indexed writes and dynamic selection

Known-index assignment/deletion, length writes, and replacement consume the same facts; their supersession rules are in section 6. A pending key is not necessarily an index. In a[pendingKey] = 0, the key can resolve to "length" and clear the Array. Neither bracket syntax nor a pending language value proves an index-only domain.

Keep general dynamic-path selection behind its existing selection dependency until its effect can be classified. Narrow protection after selection, and then publish through the shared point/length transition. This revision introduces no trusted numeric-only key hint or speculative per-index dispatch. Cover index, length, invalid-key, and poisoned-key outcomes; do not promise that every old position stays in range while an unrestricted key is unresolved.

## 4. Ordering and irreversible publication

Cascada reserves each control-flow operation's logical position before asynchronous work starts. Individual loop bodies may be issued later through that reservation; section 7 defines the compiler integration. Independent observations can finish out of order, but conflicting effects retain their command order. Kernel Promise settlement does not establish that order.

A controlled mutation reserves its successor facts before suspension. Later operations capture that successor, including unfinished dependencies; they cannot fall through to stale physical slots. Earlier operations continue using their exact predecessor captures.

Where failure can cover the whole Array, the reservation also orders every conflicting write, repair and later body or native effect against the predecessor. An earlier blocked indexed write cannot modify the data that repair will expose. A later write sees the repaired successor only at its own turn. Acknowledging issuance, capturing a handle or preparing an unrelated operand has no effect on this ordering. Use the existing transition and COW paths for the applicable scope.

Complete mode keeps the following candidate data changes private until required mutation success. Its shared access gate also protects unchanged regions: even an unaffected prefix cannot be consumed while the captured Array could still acquire whole-Array poison. All access routes listed in the mode contract use this gate. On failure discard the candidate changes, publish own status over the retained current data at the selected scope, and preserve earlier operations. Independent payload rejection or an Error returned by a successful removal is not mutation failure. Streaming modes instead permit regional publication:

1. Capture the receiver, needed operands, and authority at its ordered turn. Protect still-unread data before callbacks or subscriptions can advance other work.
2. Finish required ancestor/destination setup and every preflight capable of blocking the whole selected path before exposing changed receiver facts. Dynamic selection may temporarily gate a broader prefix; narrow that protection when the selected target becomes known.
3. Install successor shape/range dependencies and independent facts through one logical publication path. Regions proved independent of both the mapping and any whole-scope failure remain readable. A broader ! scope grants authority but does not justify keeping healthy siblings behind the selected Array's unfinished layout.
4. Complete independent regions under captured publication authority. Finish required semantic validation before committing each logical fact. Managed physical backing is a representation of that state, not an independent veto whose outcome can vary with readiness or materialization. Once committed, later ordinary regional failure cannot roll it back or widen poison over it.
5. Detach superseded destinations. Shared producers still serve earlier captures and required direct results, but cannot overwrite later commands, regrow a truncated Array, or reconstruct a replaced ancestor.

Managed logical storage is canonical. Materialize from captured logical state when physical storage cannot represent a controlled update; optional cache writeback cannot select poison. Do not replay comparators or other external work to retry representation. Required source inspection and external/native actions retain their fallible boundaries; internal invariant failures remain fatal. Update the production managed-storage contract at cutover. Native managed methods remain opaque and isolated; do not run their arbitrary JavaScript against a partially published receiver.

For borrowed Array storage, host readability follows the [managed Proxy contract](docs/data-limitations.md#proxies-in-managed-storage). A descriptor that begins throwing after import reports its failure at the guarded read that encounters it, which may be a later export.

Authority is checked before regional execution, including for an otherwise no-effect request. Today's explicit managed scope containing a registered mutable external location is invalid before Array argument preparation. Thus arr!.splice(5,pendingCount) with a registered resource at index 7 cannot publish a prefix and later discover that its scope was invalid. Preserve this preflight; this revision does not add mixed-scope mutation authority. Any other supported route whose whole-path validity depends on a control must establish that validity before changed facts escape. A genuinely local publication failure keeps its local footprint instead.

Independent streaming destination writes continue after a genuine regional semantic failure; dependent destinations retain its cause. A Proxy backing's refusal is not such a semantic failure for controlled managed writes: use canonical logical storage, so ready and deferred controls cannot choose different results. A failed opaque native call retains its separate isolation contract.

The Array can be usable while its mutation's direct result is pending. That result still includes every required validation and publication effect promised complete on delivery. Installing a pending region is not by itself completion of a mutating command's required effect. A removed payload can extend the returned value's lifetime without gating an already completed receiver transition.

Distinguish unfinished work introduced or consumed by this mutation from unchanged predecessor data. A bounded fill whose destinations are proved in range can finish its writes while an untouched predecessor remainder stays pending; a streaming call can return that partial receiver. Complete-mode public handoff still obeys its captured structural gate, independently of completed effect work and released source protection. A splice whose count still selects the remainder cannot finish merely because its insertion is visible; an empty-source splice has no such count dependency. A remap that still needs predecessor shape to determine its affected writes retains that dependency. Ordinary payload versions do not become completion barriers simply because the method returns its receiver.

### Identity policy and implementation cost

Keep write-based identity: a semantic write creates a new identity even for an equal value; a command publishing nothing preserves identity. Derive no-write decisions from structural facts and existing effect reporting, without resolving or comparing old payloads merely to avoid a write. copyWithin(0,1,1) has an empty write range; copyWithin(0,1,2) writes even when both values are X.

Pending controls can leave the write decision pending. The existing identity mechanism can consume that outcome without waiting for element values. Conditional argument relevance already requires its own wait under the poisoning contract; changing every ! call's identity would not remove that wait.

Do not add substantial identity-only state or retained history to preserve no-op identity. If implementation evidence exposes that cost, revisit the policy uniformly as an explicit contract revision. There is no per-call fallback based on timing, physical storage, or successful optimization, and no blanket fresh-identity rule is selected here.

### Command identity

Reserve one source-free successor decision per semantic command and affected logical node, using the existing captured identity mechanism. The first irreversible write or new poison fact proves effectiveness; identity need not wait for unrelated regions. A genuine no-op forwards to its predecessor. Installing an ordering dependency or changing representation is not a semantic write.

The write/effect decision is itself captured state. First apply semantic no-op rules: controlled self-copy prescribes no writes and forwards identity, even with a failed irrelevant end. Other prescribed writes cannot be erased by equal final contents. Argument failure alone does not prove a write; effectiveness follows the specified failure publication. Section 12 uses mode-specific capacity failure publication and introduces no failed-identity state.

For failed controls in streaming modes, complete independent writes and publish the specified dependent poison, then classify the actual semantic publications. Complete-mode failure publishes own status and no candidate data writes; that new status is itself effective. Do not guess which writes would have occurred had the control succeeded. If no write or new poison fact is published, identity forwards even though an independent result can fail. Repeated equal payloads do not remove a required write decision: copyWithin(0,1,P) can be a no-op for P=1 and an effective write for P=2, regardless of equal final contents.

Identity finality, publication completion, and operation closure are different. Refactor the current IdentityPublication completion coupling where needed; do not close its operation owner to settle identity. Later regional completion must neither allocate another successor nor reset a generation installed by a later command. Containing nodes still reflect descendant logical writes through ordinary path publication.

#### Deleting inherited uncertain presence

For an ordinary index below MAX, a permitted deletion establishes absence and clears selected own status without consuming the old payload. Apply the table after excluding failures of the deletion itself, including the [complete-mode candidate capacity check](#complete-mode-receiving-an-oversized-value). Its identity decision depends on the captured predecessor's own-presence and own-status facts.

| Previous captured state | Identity outcome |
| --- | --- |
| Absent, with known clean own status | No-op; forward identity. |
| Present, or carrying own status even when absent | Effective deletion/status clearing; create the command's successor identity. |
| Presence or relevant own status pending | Publish clean absence independently; leave identity pending only while these facts can still distinguish no-op from an effective publication. A known effective deletion needs no further wait. |
| Failed | Replacing failed presence with definite absence is an effective publication; create the successor identity. Do not propagate the overwritten failure into the deletion. |

At an existing virtual index, deletion first removes the old slot and then projects the mandatory structural Error for that position before publishing any override. If membership is unresolved, retain the selection dependency. The [virtual-position rule](#virtual-positions-and-full-consumers) determines the cause, presence and identity together. Use the existing mutation decision cell, retaining only the required presence/status dependencies. Pending facts follow the same rows as ready input. An unrelated failed length does not make deletion effective when clean absence is already known. Receiver/path prerequisites and a failure of the deletion itself still apply.

## 5. Result boundaries and partial producers

### Validate a result before handing out its root

```text
[A, B].with(99, "X")            -> PoisonError; source unchanged
[A, B].with(pendingIndex, "X")  -> Promise<Array | PoisonError>
```

Validation poison fulfills the ordinary kernel Promise; it is not a rejecting expression value or a partially successful Array. A valid result root is never later retracted. Fatal failure retains the normal fatal rejection contract.

A result-root Error is an Error value, with no hidden Array to repair. An Array retained under own-path poison is a different state: it keeps data plus status, and requires [captured-state transfer](#captured-state-across-handoff). Such a managed capture can travel through a result/temporary holder before assignment to a named channel; a bare native backing Array cannot carry omitted placement status. Do not add a failed-result wrapper merely to replace the specified root Error.

Required root validity and the complete access gate precede publication; unfinished payload contents need not. A pending internal handle may transport its dependency, but is not a healthy Array handoff. "Required" means still relevant after section 2's dependency reductions, not every input inspected while finding those dependencies. An empty slice or a comparison-free toSorted can return immediately despite unused poisoned or never-settling arguments. An actually dependent with index retains the Promise/poison contract above.

| Dependency | Result-root behavior |
| --- | --- |
| with index validity, required sorting success, selected source/category/authority, and complete-mode structural validity/capacity | Finish the required check before the handoff it protects. On copying-result failure return ordinary result poison. Bounds may establish validity before exact layout or payload completion. |
| Captured source placements, inherited partial layout, or retained payload data transported without consuming it as validation | A valid Array root may contain their pending/failed facts. |
| A control conversion or algorithm step needed only to construct some output facts, including concat/flat contribution discovery and streaming capacity | Use the selected structural mode and per-method failure/fallback rule. Being introduced by this call is not proof of whole-result invalidity. |

Use the [reviewed failure inventory](poison-policy-plan.md#whole-array-failure-in-streaming-modes) rather than an open-ended class of root checks. Failure form is fixed by operation and mode: ready failure, delayed rejection and an unread result have the same logical outcome. Do not replace a streaming regional fallback with root Error simply because that execution has not exposed an item yet.

| a!.splice(2,1,"X") | [C] | [A,B,X,D] |
| a.toSpliced(2,1,"X") | [A,B,X,D] | [A,B,C,D] |
| a.push("X") | [A,B,C,D,X] | [A,B,C,D] |
| a!.push("X") | 5 | [A,B,C,D,X] |

Splice's copy preserves holes; toSpliced densifies them. Pop/shift observations return shortened copies, while their mutations return removed values. Preserve ordinary no-op copy identity and backing-sharing rules.

For a!.splice(2,P,"X"), a failed required deletion count poisons the separate removed-elements result; independently determined receiver facts follow the mode's partial-publication rules. In the observation form, the returned transformed copy instead follows the copying-result contract below. These are distinct language operations, not inconsistent result timings.

### Constructed Array results

Copy-producing calls use the source Chain's selected mode. This applies uniformly to observational mutators and ordinary producers such as slice, concat, flat, toSpliced, toSorted, and with.

| Mode | Copy result |
| --- | --- |
| Complete | Pass the source and result access/validity gates before healthy Array handoff. Relevant structural failure returns ordinary root Error; stored payloads may remain pending. |
| Sequential stream | After root validity, expose the partial copy and its fixed prefix. Later structural failure is represented by the specified regional Errors, markers, or positional flags. |
| Unordered stream | After root validity, expose guaranteed survivors and permit positional fallback without positional poison. Retain actual content/survival failure and missing-output markers. |

An exposed copy's root is not later replaced by a call Error or retroactive path flag. Its producer refines the captured layout under that mode. Sorting is an explicit whole-result exception to unordered position-only recovery: the request requires a sorted result, so required sorting success is a root-validity prerequisite in every mode. Do not expose that result's items or fixed suffix while a required comparator/key/preparation failure can still block the whole result. Other methods retain their declared positional fallback without a hidden Array-level diagnostic.

Required target/category/authority and selected whole-result exceptions still precede the handoff they protect. Invalid with returns result poison and preserves its source; prove validity from available bounds without demanding exact length. Complete mode retains required discovery/cycle and capacity validity. In the two streaming modes, concat part roots and flat nested expansions are independent contributions: actual required failure uses a structural placement or missing-output marker, and pending contributions do not block independent output. Streaming capacity likewise uses the shared regional tail rule. The [method specification](docs/array-method-specification.md#8-flat) owns the contribution and cycle details.

For the singleton cycle `const a=[]; a[0]=a`, finite-depth flat retains a cyclic value while Infinity fails at the recursive edge. A pending depth therefore leaves that contribution unresolved. Complete mode cannot expose a healthy root until required whole-result validity is established. Streaming modes can expose other guaranteed leaves under their ordinary position/capacity rules; Infinity cuts the cyclic edge with a structural marker. A relevant failed depth uses the ordinary regional fallback, without exploring a hypothetical Infinity branch merely to validate the root. No pending control is replaced by a marker or Error.

Mutating ! calls expose receiver progress through the selected Chain independently of their direct result. The direct result waits for its required effects, controls and any payload it actually returns. On `[p]`, `a!.pop()` commits length zero while its scalar result waits for p. From the same input `a!.splice(0,1)` can return a removed Array with p still pending in its sole placement. Both permit a subsequent push on the empty receiver. The [method specification](docs/array-method-specification.md#1-one-operation-separate-outcomes) defines these boundaries and the per-family rules.

### Transfer production before closing an invocation

A non-mutating call may finish with a prepared partial Array only after its remaining data producers have transferred to shared captured state. Before handoff, install known parent relationships, pending-publication obligations, and retained inputs. Its future layout must not depend on an operation-only continuation that stops when the invocation closes.

Shared settlement preserves values for all live captures and destinations. It does not extend the completed invocation or create a second public result. Full export and script return still consume the complete required graph; handing out a partial Array is not permission to finish a script that owes its complete contents.

## 6. Failure, queries, and supersession

### Local failure rules

The [mode/failure table](poison-policy-plan.md#2-failure-categories-and-fallback-layouts) owns the contract. Complete-mode mutation failure flags unchanged current data; failed copies return ordinary root Error. Streaming modes preserve independent facts, positional survivors, and the declared fallback; neither automatically flags the whole Array. Sort retains its explicit whole-Array boundary, while finite and open-producer capacity overflow use regional tail Error data. See the [failure inventory](poison-policy-plan.md#whole-array-failure-in-streaming-modes) for the remaining selected boundaries.

- Stored payload rejection stays at its placement with its original cause. It does not fail the retaining call or Array structure.
- Structural selection, presence, or membership failure follows the method's declared permanent-poison or positional-status rule. Do not confuse it with ordinary payload rejection.
- A source capture failure affects consumers of that capture. Managed representation refusal cannot create a different logical outcome; required native/external actions retain their own failure boundary. Required direct-call failures retain their own completion boundary.
- An irrelevant failed argument adds no poison, marker, or status.
- Required root/ancestor publication and authority failures can prevent safe exposure. Complete capacity gates the result; streaming capacity affects the positions that cannot retain healthy data. Do not claim a region that was never publishable or allocate an illegal native index to carry a diagnostic.
- Compute fallback and failure coverage from the command's captured successor. A late callback cannot poison a replacement, regrow a truncated suffix, or append a marker to the later live Array.

### Failed ranges and surviving occurrences

A pending bound remains a structural dependency until it settles or is proved irrelevant. A failed range belongs to the command's captured extent, not all future indexes.

fill uses normalized start/end bounds, not a signed count. Negative bounds are end-relative; internal signed remap counts describe traversal direction only.

For streaming mode, [A,B,C,D], healthy X, and failed P:

| Operation | Fallback slot outcomes |
| --- | --- |
| fill(X,2,P) | [A,B,Error,Error] |
| fill(X,P,2) | [Error,Error,C,D] |
| fill(X,P), omitted end | [Error,Error,Error,Error] |

These Errors are structural: the affected contents may have been overwritten. Their positions are not streamed, and repair does not recover the candidates. Length remains four. A later push(Z) can add a healthy fifth occurrence. Ordinary reads can use established siblings; sequential iteration still cannot cross its first structural obstruction. Complete-mode mutation instead flags the unchanged Array.

Use only bounds derived from captured method facts. A raw failed start on length four has normalized domain [0,4], not an invented [1,2] annotation. A failed deletion count at known start 2 is clamped to [0,2]. A previously attempted application calculation does not leave a range annotation on its Error. Tighter internal bounds require an explicit derivation from retained method/layout facts; arbitrary range annotations are not part of the run API.

Pure insertion maps every original occurrence and every inserted argument. The [positional fallback](poison-policy-plan.md#pure-insertion-with-a-failed-position) supplies their order. Sequential mode flags lost intended positions. Unordered mode accepts the fallback order. Apply the [capacity projection and count clip](#maximum-logical-count) before deciding which of those mapped occurrences a consumer can receive. A failed deletion count has the separate fallback illustrated above.

A failed supplied length is an invalid required resize input, not an arbitrary legal size to choose. Section 12 retains its invalid-request boundary. Do not add a frozen failed-size state.

### Common consumer behavior

The table's selected-fact rules operate after applicable mode/path prerequisites. Every ordinary complete-mode consumer uses the [shared access gate](poison-policy-plan.md#complete-access-gate), including methods, writes, direct results and nested export/native preparation. Metadata queries and permitted recovery/reference operations retain the exceptions stated there.

| Consumer | Required dependency set |
| --- | --- |
| Numeric/nested lookup, expression extraction, positive at | Selected shape/presence/value facts and genuine path prerequisites. No deep whole-Array Error precheck for a usable streaming Array. |
| Bounded slice, fill, copyWithin, narrow mutation/entry | Selected range, normalization, authority, and mode-specific publication requirements. |
| Searches | Eligibility/comparison reductions and ordinary result-selection rules; independent mismatches remove irrelevant range dependencies. |
| Ordered iterator | Final membership, current captured index, clear slot status and final payload source at the next position. The producing operation’s accepted fallback supplies its coordinates. Ordinary payload poison runs a body. A structural obstruction rejects the step. |
| Unordered iterator | Guaranteed surviving occurrence and final payload source, with independent index future. |
| isPoisoned | Selected value/path classification; no descendant scan. |
| hasError / getErrors | The captured retained failure frontier, including real marker elements and positional flags; see the common query contract. |
| Full export, native preparation | Complete required graph, with normal Error collection and path blocking; do not omit markers or silently strip flags. |
| Mutable-external snapshot | Existing synchronous ready-only boundary; no waiting into validity or treating unfinished data as holes. |

Do not traverse obsolete predecessor alternatives or repair baselines as current data. After failed-count splice fallback, A/B/X and the actual structural Error slots form the current frontier; discarded C/D payloads are not hidden recoverable values. hasError can use a certain retained failure, while getErrors still completes all relevant collection, including pending payloads.

Failure membership can remain conditional while another required fact may prove the affected range empty. No marker or permanent poison is published merely because a producer failed; its effect must still be relevant under the declared rules.

After an unordered position-only fallback, do not retain a second Array Error solely to remember the order that mode does not promise. Existing explicit flags and actual payload/structural Errors remain meaningful. Different modes have explicit reference semantics; timing and storage representation cannot choose between them.

### Shallow isPoisoned query

The [query contract](poison-policy-plan.md#4-error-queries) owns naming, selected-state outcomes, captured status, and external metadata behavior. Cascada's x is error uses deep hasError. isPoisoned is distinct from both isPoisonError (language Error predicate) and isPoisonedValue (expression-wrapper predicate).

For partial Arrays, local layout/presence/value failures enter deep queries without making the usable root itself poisoned. Feed the common query machinery captured shape and conditional failure membership; do not classify an Array by scanning only established placements. The [open-entry status rule](poison-policy-plan.md#earlier-open-entries) applies even to an empty current Array and must not be implemented by draining the iterator.

### Explicit replacement

Index writes, index deletion and length assignment consume the Array receiver. All modes therefore obey an applicable whole-Array blocker. Whole-location replacement/deletion can supersede its old value without consuming it, respecting its ordered turn, any ancestor blocker, prior captures and required effects.

| Later command | Effect |
| --- | --- |
| Assign index i | Replace that placement's value/presence dependency without reading its old payload; apply ordinary length growth. |
| Delete index i | Remove its selected data and status without shrinking length. Publish absence at an ordinary index. At a virtual tail member publish the projected capacity Error from the deletion. |
| Assign valid length n | Set length, discard indexes at or above n, preserve contents/status below n, and expose only genuine holes. |
| Replace/delete the Array location | Detach its current destination and failure data; preserve old captures and still-required operation results. |

After streaming splice fallback [A,B,X,Error,Error], truncating to length three leaves [A,B,X]. Repair cannot reconstruct C/D; extending again creates ordinary holes where truncation removed them. Deleting a structural Error or marker below MAX leaves a hole. At a retained virtual member the same deletion publishes its own capacity Error at that index, preserving the logical length and the older capture’s original cause.

Before fallback settles, a successful delete at an ordinary index below MAX can establish an absent property even if the source's length is still pending. Numeric property lookup can return undefined while iteration still needs membership and a captured structural selection. Do not force an irrelevant shape query on that read.

A valid length write fixes the new extent. For each retained index below it, keep the predecessor's captured membership and placement until the mapping determines its contents. For streaming `a=[A,B]; a!.splice(1,p); a.length=2`, index 0 remains A. Index 1 is B for p=0, a hole for p=1, and structural Error if p fails. With p pending forever, length and index 0 are available while index 1 waits. A subsequent assignment to index 1 supersedes that selection in the new version. The earlier capture and the splice result keep their own dependencies.

An Error or flag ceases to affect current data when ordinary replacement/removal discards its last relevant placement; no second Array-wide failure ledger preserves it. Other retained occurrences and earlier captures keep their own outcomes.

Representation copies preserve current data, structural obstructions and their causes, positional flags, and required facts. A semantic projection may construct a healthy result from independent selected data without repairing its source. Ordinary access cannot traverse a genuinely poisoned path; see [access and extraction](poison-policy-plan.md#3-access-and-extraction).

## 7. Ordered iterator API

Use the standard async-iterator protocol for trusted kernel integration. `[Symbol.asyncIterator]()` returns the cursor itself. Every valid `next()` and `return()` returns a `Promise<IteratorResult>`, including a ready item, empty exhaustion and repeated close. Capture the holder or finish local cleanup synchronously before exposing a settled Promise. A ready recoverable failure or fatal on a valid step rejects its Promise. Reuse the one guarded public result for unfinished work. The compiler supplies the source Chain/path/context, dynamic-path facts, and the binding's context and construction mode. [Holder delivery](docs/array-iteration-technical-analysis.md#7-select-chain-valued-iterator-steps)

Capture the source's logical version at factory issuance, not lazily at the first pull. Earlier effects are included and later mutations are excluded. Cursor creation can retain a pending complete gate; no first item or successful empty exhaustion passes that gate before validity is established. Protect unread facts with existing captures, leases, and COW; reuse entry protection when it already covers the correct view and lifetime. This need not copy or resolve the whole Array.

The cursor owns source-selection work started at factory issuance even before the first pull. Handle its exact pending outcome through ordinary guarded continuation ownership, transfer completed selection into the captured view, and release obsolete source bindings. A recoverable selection failure is retained for the first requested step, which rejects with that poison; it is not successful empty exhaustion. `return()` before any pull releases cursor-only work without waiting for selection, and resumed work cannot repopulate the closed cursor. Shared settlement and execution fatality keep their existing contracts; an idle cursor needs no execution registry or pending-result registration when no public result is pending.

For an expression-produced Array, transfer the captured result into an ordinary temporary inheriting the [expression's mode](poison-policy-plan.md#expression-temporaries), or pass that same capture directly when the compiler elides the holder. Do this before raw value extraction so both forms carry pending status and validity. Release the holder when the capture owns the state. Other source categories keep their existing adapters.

### Unordered pulls are a scheduling interface

An unordered next() transfers one available guaranteed occurrence, its elem Chain and its captured index fact to a trusted consumer. Delivery order may differ from logical order. It is not an application-visible first(), ordered collection operation, or arrival-order loop. Consumers implement language-visible decisions and effects through the indexed branch protocol or the ordinary ordered selection queries. Closing this cursor after its first available result does not prove that the logical first occurrence was consumed.

Witness: two independently guarded contributions append A and B in that logical order, and both guards eventually succeed. A pending A contribution can permit B to be handed to the scheduler first when B's survival/admission is proved. A compiled loop returning its logical first item must still return A; it cannot return B merely because it closed after that handoff. Compare physical delivery only for the ordered cursor. For unordered scheduling, verify occurrence/index captures and exactly-once delivery separately from application-level sequential equivalence. Add no runtime permission mechanism or second iterator representation to enforce this trusted integration contract.

### Select once before dispatch

Dynamic loop sources need one ordered selection and category decision at the loop's reserved position. Dispatch from the captured value's admitted category and authority, preserving that same capture into the selected adapter. An ArrayView is a managed Array despite Array.isArray returning false; a declared external Array remains external even though that JavaScript predicate returns true. Do not classify a raw value in the compiler and then perform another live lookup or import to obtain the source.

Reuse the common receiving/path-selection boundary and Phase 8 native-iterator integration. The managed-only factory may reject unsupported categories, but the general loop dispatcher must choose among adapters from this single selection, without consuming or reclassifying the source twice. Preserve pending selection, supported getter/reflection failure, error context, external reservations and early-close ownership. Fix the trusted adapter handoff with the first compiled-loop integration; no new language value transport or standalone public type probe is required.

Consume availability at the source expression's receiving boundary and pass the resulting capture to dispatch. A supported settled thenable returns its callback's result directly. Cascada's current `RuntimePromise` can store the delivered Array and later call `.then` on that Array. Complete the Phase 8 removal of this wrapper on the expression-to-loop route. Use the public guarded continuation, proceed immediately on a ready capture, and retain its returned chain while selection remains pending. Preserve the producer context on failure. Apply the same input rule when the loop consumes its limit, after source selection. For a loop returning its only item, a ready `[A]`, a supported synchronous source of `[A]` and a deferred source of `[A]` must all return A. A synchronous source rejection takes the same loop failure route as deferred rejection. [Supported thenables](docs/data-limitations.md#promises-and-supported-thenables) · [Public composition](docs/integration.md)

### Protecting unread inputs

Each iteration receives its selected item into a new elem Chain through captured-placement transfer and receiving protection, including pending delivery. This is not a raw lookup/extraction of the payload; the [item boundary](#item-boundaries) preserves inert external references. Once that binding owns the item, the cursor needs no duplicate hold solely for that item. Remaining shape/index dependencies keep their own captures.

Before an unread item is independently captured, a later body write could replace it. For [A,B], a body handling A may write live index 1 to X; the captured iterator must still deliver B. Allow writes to current, earlier, and unread indexes, and structural changes to the live Array. Writing the elem binding instead follows ordinary owner isolation.

Looking up published items quickly is useful but is not an ordering guarantee. The general mechanism preserves the unread logical view; eagerly creating every elem Chain would impose traversal/allocation even for bounded consumption or early stop. Capture through the entry's private command prefix, not its enclosing future.

Out-of-order delivery can transfer and release occurrences earlier. A whole-Array hold becomes unnecessary once required items and remaining shape/index facts are independently captured, or existing protection already suffices. Unpublished dependencies still need protection. Body readiness never changes logical write precedence.

### Cursor algorithm

1. Select and capture the source at issuance under ordinary ordering, authority, and the Chain mode. Unsupported categories produce NotIterable without coercion. Complete mode passes the shared captured-Array gate before any successful source step, including empty exhaustion; ordinary payloads need not settle. Reuse this proof for the fixed captured version.
2. Keep the next numeric index i and the captured layout/placement view.
3. Establish `inRange(i)` on the accessible captured version. Pending membership retains the question. Structural failure reports its cause. When membership is false, finish only after the mode's terminal check, including accumulated unordered skips. A failed source never produces successful empty exhaustion.
4. Establish final membership/presence and the payload source at i. Use the producing operation's settled coordinates and preserved flags, including across modes. Wait for structural selection still able to delete, overwrite, or move the occurrence. A blocker on the selected slot itself prevents delivery there, as does structural Error data. A flag strictly inside a healthy payload stays inside the delivered holder. Check the captured slot facts without traversing the payload. [Fallback across modes](poison-policy-plan.md#ordered-and-irreversible-fallback)
5. Receive the captured occurrence in its ordinary elem Chain, advance i and fulfill the step with `{ done: false, value: elemChain }`. An established payload may be pending or ordinary Error data. For a healthy hole install a **present `undefined` root** in the binding. The source stays sparse. A flagged hole takes the structural failure route in step 4.
6. Continue from the capture, never the later live Array or a rescanned prefix.

Complete and sequential modes use this ordered cursor with their respective structural readiness rules. The first step through a failed Array reports its cause and starts no body. On an accessible Array with a regional obstruction, both ordered cursors stop at the first blocked position. For example, a Complete holder receiving streaming `[A,marker E,B]` delivers A and rejects at E. Its slot 2 remains readable as B after cursor failure. No cursor failure adds a source flag. Unordered iteration can deliver guaranteed survivors and then reject its terminal step with the skipped structural causes. Ordinary pending or poisoned payloads are delivered in item holders. A raw numeric end cannot erase a failure obligation.

The Chain in the step owns its pending payload. Cascada binds that exact Chain without importing it as language data or wrapping it again. An async generator yielding raw payloads would await them; a standard async iterator returning holders avoids that wait. Keep ready transitions sync-first and use existing guarded continuations for pending structural facts.

Cascada's trusted consumer pulls one step at a time but may start many bodies without waiting for earlier payloads or independent bodies. No per-element deep health check or new worker scheduler is required.

### Completion and early stop

A done step from active next() means successful natural exhaustion, not completion of independent payloads, bodies, or native effects. The done records returned by return() or later calls on a closed cursor instead acknowledge local termination; they do not prove healthy empty input or authorize loop-else. Cascada retains the stop/failure outcome through its existing control flow and owns body/effect lifetimes and pacing.

For a root or structural enumeration failure, the adapter returns a rejected step Promise containing the existing PoisonError, including when failure is ready. Never return a bare Error as a step record. This is a narrow iterator transport rule; graph operations still fulfill with language poison. Ordinary element poison stays inside the elem Chain; a pending payload publishes poison there on recoverable failure. Fatal execution failure retains rejection. The trusted consumer uses isFatalError and isPoisonError under its guarded composition boundary, covering synchronous entry throws and step rejection. Managed capture failure retains LookupReflectionFailed without a second IteratorFailed wrapper.

Before healthy natural exhaustion, establish that no required captured structural failure remains. Unordered skips retain their causal failures for terminal rejection under existing Error combination/deduplication; do not deep-scan ordinary payloads or create an Array-wide historical error ledger. After structural failure, close enumeration and release cursor-only unread uses synchronously before exposing the rejected step, then perform the loop handling below. Do not rely on the consumer calling `return()` after a rejected `next()`. Preserve only the causal failure and genuinely required independent work. A failed boundary is not successful empty exhaustion. Keep didIterate on the loop, not on Error objects.

`return()` closes future enumeration and releases cursor-only unread uses without scanning the suffix or cancelling shared production. An already-issued pending next() retains its own required capture and finishes with its original result or failure. Return reports done after local cleanup; it does not wait for that request, body work, or payloads. The consumer must receive or discard an outstanding result through ordinary binding cleanup. A required never-settling dependency can keep that one issued request pending.

Give the pending step its own work owner before releasing cursor state. Do not strand its Promise by closing an owner used by its continuation. In a live execution, repeated `return()` and `next()` after local termination return fulfilled done Promises. A valid call observing execution fatality returns its rejected Promise through the common boundary. One-pull-at-a-time trusted consumption requires no request queue. The [lifecycle table](docs/array-iteration-technical-analysis.md#8-close-the-cursor-not-an-issued-step) and ready/deferred witnesses define the selected behavior.

An already delivered step owns its index and requested metadata through the same captured producers as its binding. Closing the cursor releases unread occurrences. If B arrived before an optional predecessor resolved, its pending `index0` still resolves to 0 for an empty predecessor or 1 for one item or marker, even after source replacement. Under an indefinitely open predecessor its proved `last` remains true while `index0` waits. Retain only the required shape dependency for each outstanding projection. [Metadata](#metadata-and-value-ready-batching)

An issued bounded pull can still need a completion credit from an already admitted body. Keep that update route and any required skip progress with the request through close. At bound one, issue the next pull while body A owns the credit, then close. If A finishes and B is next, the outstanding request still delivers B for binding or disposal. Later pulls acknowledge closure. Independently, an already started native source observation holds its ordinary reservation through its promised completion even when the cursor is closed before a pull.

#### Receive the item before returning the step

Construct the ordinary elem Chain inside `next()` from the selected placement. Transfer present data, pending versions and status under the applicable access rules. ### Compiler ordering and loop failure

Before source selection or any body can suspend, reserve the loop's ordered entry for the compiler-declared observation and mutation paths using the Phase 8 entry protocol. Capture the source/read dependencies through the correct pre-entry or contained view; an iterator must not wait on its own entry's completion. Bodies issued after later parent commands still issue through the loop's reserved views. A Promise settling first never grants a body a new parent position.

The enclosing reservation orders the loop against outside commands; it does not by itself order the bodies. For ordered iteration, reserve each body's declared reads and mutations in numeric occurrence order before starting work that can suspend. Reuse the contained batch-entry/buffer protocol so a delayed body 0 cannot issue conflicting work after body 1 merely because body 1 is ready. The future compiler rewrite will lower `break` through a mutable control Chain. Its ordering follows the same rule as `return`. Attach the existing control and application Chains to the same branch event. Unordered delivery uses the indexed-branch extension below.

The planned break channel starts false and is set true at the ordered break point. Later iterations conditionally skip processing once it is true; branches whose preceding break decisions have been discharged can still run independent work concurrently. This body gating is not, by itself, cursor return or cancellation of source production. When enumeration continues through skipped bodies, it reaches ordinary terminal success/failure and retains that completion through the existing loop reservation. Do not add a post-close source-status subscription for that case or demand every payload merely to skip its unused body. Preserve ordinary body completion, window credit and didIterate accounting; a break-suppressed body is not an unordered structural-error skip.

Function return uses the same ordinary channel-and-conditional mechanism at every affected scope. The return channel starts false; return sets it true. Code before a possible return retains its ordinary dependencies, and later code executes only while return is unset. If a return is nested inside a loop, guard the remaining code in that loop and the code after the loop in each enclosing affected scope. Attach these control operations to the same ordered branch events as the application operations. A return-channel write neither cancels source production nor certifies completion of already-issued steps, body commands or enclosing effects. This is the selected language contract; any existing shortcut that stops source pulls must preserve it, not establish a separate return policy.

The [Phase 8 batch-entry and compiler cutover](docs/runtime-evolution-plan.md#2a-integrate-the-operation-chain-boundary-in-cascada) is still planned. Its overlapping multi-reference reservation, captured readonly views, and closure guarantees are prerequisites for shipping general compiled-loop integration in stage 1. The standalone cursor already exists. A compiled loop that covers multiple references must pass those ordering checks.

The iterator's completion means no further bodies will be issued, not that all commands inside those bodies have been issued or completed. The higher runtime owns body/effect completion and preserves every reference through which more commands can still be issued. Reuse ordinary entry closure and nested reservations for those lifetimes.

Do not conflate loop-result completion with managed publication. Once an entry's own issuance closes, transfer its current partial placement/layout; already-issued child dependencies remain in that state and external effects retain their own reservations. A pending payload or unrelated body/native effect cannot hold a determined managed region behind an enclosing completion gate. Conversely, a still-open reference able to issue an arbitrary conflicting mutation cannot be released merely because the cursor finished. This preserves the existing separation in docs/enter.md rather than adding an early-close API.

On structural enumeration failure, preserve completed body effects and Cascada's compiler-declared loop failure targets. A skipped position starts no body and does not increment `didIterate`. Handle a missing append contribution at that position through its reserved branch. The terminal rejection completes loop failure handling for the declared body targets and, if no body was issued, the else targets. An already represented contribution adds no further marker. Ordinary payload Error still runs the body with Error data. Loop-else runs only on healthy natural empty exhaustion. Apply the compiler’s ordered control guards when it lowers `break` and `return`. [Failure position](poison-policy-plan.md#marker-position-and-ordinary-array-behavior)

Use the source mode for enumeration and each affected target's mode for publication. A complete output's missing append flags the retained output at the skipped contribution, before the next conflicting push. A streaming target records its marker there. Run either publication under the same ordered control guard as that contribution. Keep the terminal source failure even when this guard suppresses the output. Place remaining loop-terminal target effects after the preceding body branches on those paths and before later parent commands. A skip alone leaves else eligibility open. A first issued body releases else-only coverage. On terminal failure with no bodies, apply the compiler's ordered body targets followed by eligible else targets, preserving overlapping publications and one contribution per distinct target at that event. [Failure target ordering](poison-policy-plan.md#marker-position-and-ordinary-array-behavior)

The [push-only entry follow-up](array-layout-approaches.md#control-flow-failure-and-path-status) preserves issued appends and represents an unrepresented missing contribution with the declared marker. A known inserted occurrence with uncertain position needs no missing-output marker. An independent callback result or ordinary payload poison does not by itself poison entered targets.

#### Destructuring in an enabled body

Tuple validation and binding reads belong inside that iteration's ordered, enabled body branch, after the ordinary break/return guard. A suppressed body does not consume its tuple, validate its type, or publish destructuring poison. Receiving an inert elem Chain and reserving its branch can happen earlier. A genuine source-selection/enumeration failure remains a source failure and reaches ordinary loop handling independently of tuple reachability.

Pass the captured item holder as one argument to the generated managed-Array body entry. Pass the captured metadata and operation context in fixed arguments. Use this entry for sequential, limited and unbounded Array pacing. Inside the reserved branch, evaluate the lowered break/return guard first. On the enabled arm, bind a single loop variable directly to the received holder. For destructuring a managed Array, bind exactly the declared number of slots through captured placement reads. Missing entries and healthy holes supply undefined. Excess slots are unused. If the enabled tuple root is ordinary payload poison, bind its original Error to each declared variable and run the body under the existing poisoned-value rule. ### Bounded-window iteration

Demand belongs to the individual cursor. Its lower bound certifies the finalized prefix and never moves backward. Translate both the proved exclusion and the required containment of a candidate through each intervening cut. With `["old"].splice!(p,1,"new")`, an unordered window covering both possible positions can deliver "new" first. At p=0 its index is zero. Trimming to [1,2) must finish an outstanding pull once the old slot is excluded. Two readers of one insertion capture keep independent delivery sets and use the same coordinate partition for their metadata. [Public cursor contract](docs/integration.md)

Add a separate phase for bounded unordered loops whose bodies can depend on earlier iterations. Reuse captured layout ranges to restrict admission to a logical window; command-buffer ordering still decides when admitted commands execute. This phase preserves Cascada's existing control-flow semantics.

The window's capacity ceiling is the maximum logical count, Number.MAX_SAFE_INTEGER, rather than the smaller successful-payload limit. The layout independently excludes poisoned tail positions from body delivery and can finalize a proved structural Error span in bulk. An oversized tail must not strand a pending pull at the successful-payload boundary or require one credit/callback per poisoned position. Possible eventual count saturation creates no extra admission prerequisite.

The selected window counts unfinished positions, not numeric width. It covers the earliest B unfinished logical positions together with finalized positions between them. A position is finalized either when its delivered body finishes under Cascada's existing rules, or when the layout proves that unordered iteration skips that captured structural-failure position and retains its failure obligation. Skips are not successful body completions and do not increment didIterate. Keep a lower frontier f and an exclusive upper boundary r, so demand is [f,r). Finalized positions consume no capacity. Undiscovered positions reserve capacity until one of those outcomes is established; a known index alone is not completion.

For a window not clipped by Array capacity or the source end, the invariant is:

```text
(r - f) - finalizedPositionsWithin(f, r) = B
```

For effective demand clipped by a proved enumeration end, substitute min(r,end) for r in that formula; its left side is at most B. Derive this clipped end where used. Stored r is capped only by Array capacity and never shrinks to a merely available prefix. A proved structural failure retains its terminal obligation at the captured end. The rules implementing this invariant are:

1. **Initialize.** Cascada consumes `concurrentLimit` at the existing loop boundary, preserving its ordinary poison and thenable handling before numeric validation. For a managed Array, omitted, undefined, null or zero means unbounded. A finite positive Number supplies B = min(ceil(limit), Number.MAX_SAFE_INTEGER), preserving the existing Array worker count for fractional limits. Other values follow the existing InvalidConcurrentLimit failure path. Preserve sequential-loop selection and trust the normalized internal demand. Start with f=0 and r=min(B, Array capacity). Source membership and a proved terminal end limit effective demand, but do not clamp stored r to the currently available prefix or lose earned credits. B=1 admits at most the earliest unfinished position; structural skips still retain unordered terminal-failure semantics. An omitted bound retains the unbounded unordered contract.
2. **Admit.** For each distinct guaranteed surviving occurrence, query its possible final captured/fallback indexes through the existing layout. Admit it only when its payload source is final and its entire possible-index set is inside [f,r). A sound inclusive range [lo,hi] suffices when lo >= f and hi < r. Exact index readiness is unnecessary; overlap alone is insufficient. Already-delivered occurrences are excluded, including those that have completed but whose exact indexes are still pending.
3. **Credit finalization once.** When an admitted body finishes, or a captured structural position is proved skipped under unordered failure handling, extend r by one, capped by Array capacity. The skip proof establishes membership within demand and records its retained failure obligation in the same transition. Batch k newly finalized positions extend r by k. Never credit a position again when its index resolves, a duplicate notification arrives, or it joins the retired prefix. If its index is pending, its prior containment proof and distinct occurrence establish that it lies below r; finalization need not await that index. Body completion and structural skipping use this one accounting transition, with distinct iteration/failure outcomes.
4. **Trim the finalized prefix.** Advance f across the maximal prefix proved finalized. Do not extend r merely because f advances. A newly finalized first position normally moves both boundaries by one through rules 3 and 4. Crossing additional positions already credited moves only f, shrinking numeric width by the number removed. Pending indexes can postpone trimming without postponing earned credit; captured range/count proofs can establish a finalized prefix without resolving every index. Clear spent finalization/occurrence facts as that prefix retires.
5. **Continue within the updated demand.** Deliver eligible, not-yet-delivered occurrences in any availability order, each once, with its existing index future and elem Chain. A pending payload consumes unfinished capacity without delaying delivery. A pending pull must consider eligible occurrences throughout the current window, rather than select an outside item and wait on it while an eligible predecessor is available. Start available work without waiting for the window to fill. Required layout/index waits remain legitimate; eligibility and index facts must not require draining this iterator or completing future bodies.

An equivalent accounting identity is r=B+F before capacity clipping, where F counts distinct finalized positions since this capture began, including structurally skipped positions. This explains the rule; it does not require a second stored counter or a history log. Retain only finalization facts needed for trimming and duplicate suppression, plus the causal failures required by terminal reporting.

For B=3:

| Event | Window | Completed positions still inside | Unfinished positions reserved |
| --- | --- | --- | --- |
| Start | [0,3) | None | 0,1,2 |
| Positions 1 and 2 finish | [0,5) | 1,2 | 0,3,4 |
| Position 0 finishes | [3,6) | None | 3,4,5 |
| Position 4 finishes | [3,7) | 4 | 3,5,6 |
| Position 3 finishes | [5,8) | None | 5,6,7 |

Thus finishing position 0 after positions 1 and 2 earns only one new position: the upper boundary goes from 5 to 6, not 8. The lower boundary advances over all three completed positions, reducing width from five to three. The upper boundary never moves backward, and no still-unfinished admitted occurrence is evicted. Initially an occurrence with index range [1,2] is eligible while [2,5] is not; after extension, eligibility uses the new r and the same full-containment rule.

The bound applies to unfinished positions, both admitted and still reserved for undiscovered predecessors. Distinct captured occurrences occupy distinct final indexes, and each counted finalization removes one of those positions from unfinished work. Consequently later bodies cannot occupy all B unfinished slots while also excluding an earlier unfinished position inside the window. Completed bodies can refill capacity even while an early body remains pending; required structural/ordering dependencies can still limit actual progress.

Structural skipping must make progress before an item is returned. For B=1 and [structuralError,B], initially [0,1) contains no deliverable item. For `[A,B,C,D].toSpliced(3,count)`, issue a read of slot 3 and start an iterator before clearing the source and result Chains. In a streaming mode the prefix remains available while `count` is pending. A count of 0 delivers `D` to the read and iterator. A count of 1 gives the read `undefined` and ends the iterator after `C`. In a length-only run, the cut can stay pending without a reference from the length question to D. Account separately for a live content producer that still needs D and for permitted shared backing. With an independently backed D and its last content use released, verify collection while the count stays pending. Also exercise `fill!` with a direct result consumed immediately by a condition or argument.

Use one cursor lifetime and guarded result boundaries for public pending step requests. Per-item graph capture is not a separate public command; closing the cursor and completing a step have distinct lifetimes. Fatal resumption and local closure retain existing shared-settlement/operation-work checks. No iterator registry, producer scheduler, execution-wide sweep, or new thenable transport is needed.

### Work bounds

Prototype measurements establish costs for the measured representation and workloads. Verify the production kernel separately with both structure and payloads pending, deep chains of mixed edits, sparse observers, and multiple readers of a retained capture. Record issuance, intermediate delivery, source settlement, and release separately. [Production work cases](docs/work-bounds.md#controlled-array-work)

Work is proportional to consumed data, produced output, captured versions, and necessary unfinished transitions. Preserve sparse gaps symbolically; do not allocate per possible hole or failed index. A value iterator may visit every index it actually issues, but an early exit must not allocate the remainder. Reuse maintained range indexes; do not repeatedly scan delivered prefixes or settled command history. Test N unfinished operations on a fixed small graph, including repeated captures/reads and operations later proved to have no effect; distinguish unavoidable retained versions/output from avoidable history traversal. Settling one branch must release its spent predecessors while unrelated branches remain pending.

Drain history-sized forwarding, completion, and release with loops or synchronous worklists. Keep ready transitions synchronous and use existing ordered thenable continuations. Required dependencies may remain pending indefinitely; neither timeout invention nor a later command becoming an earlier prerequisite is acceptable.

Finite flat depth is a Number control, not a work allowance. Existing conversion accepts large finite integers, while `2**54 - 1 === 2**54`; even smaller large depths can overflow the call stack on a tiny cyclic graph. Reuse the existing depth-safe finite-cycle implementation, adapting its count limit and partial-output semantics. At Infinity share input inspection and cut the active ancestry of each expanded occurrence. The [flat rule](docs/array-method-specification.md#discovery-and-payload-retention) gives the two-root cycle witness. Do not unfold one recursive frame or retained remap per conceptual depth, silently cap the depth, or treat a large finite depth as Infinity. The singleton cycle has one retained output at every finite depth; branching expansion still needs capacity validation before allocation. Ordinary shallow graph walks remain recursive; this requirement addresses repeated cycle traversal, not a new general graph scheduler.

## 9. Repair integration

Use [exact-path status clearing](repair-simplification-plan.md). Complete-mode failed mutations retain unchanged data under repairable own status. Sequential positional flags retain the known payload at its fallback position and are repairable. Permanent structural poison, markers, ordinary payload poison, and failed copying-result Errors are not hidden values waiting for repair.

Required preparation/comparison failure in mutating sort uses the complete-mode rule and its streaming exception. Repair reveals the unchanged pre-sort data without retrying sorting; no sort data writes were published and no repair-only baseline is needed. Copying sorts expose no repairable failed copy. Later publication failure retains its mode-specific rules.

Repair returns undefined after successful status publication and does not await the selected payload merely to decide that return. It acts on the state at its ordered turn, after earlier conflicting writes. Writes blocked on the way to repair add no data for it to reveal. It preserves current writes and positions, does not discover intended order, and does not restart an old iterator. Ordinary replacement/removal can discard Error data.

Keep only captures needed for ownership, snapshots, native isolation, unfinished results, or retained current data. No rollback baseline is kept solely for repair. Basic positional status and its protection are prerequisites of structural prefix integration; the general policy/repair cutover also covers native and canonical external boundaries.

### Self-modifying iteration

Keep arbitrary source mutation supported. The iterator preserves its captured view; each elem Chain protects its received item. Do not rely on lookup speed, body pacing, or a ban on writes to unread indexes. Reuse entry protection where sufficient and retain unread version facts where it is not; a capture need not copy or resolve the whole Array.

At implementation completion, review the ordering and lifetime argument alongside these integrated cases:

- A body writes the current, earlier, or next unread index, including nested managed children and aliases. Run immediate mutations inside the same entered reference without an intervening await. Distinguish mutation of the elem binding from mutation through the live Array.
- A body appends, removes, inserts, reorders, fills, copies, truncates, or replaces the source. Iteration still enumerates its captured occurrences: appends do not extend that iteration, and later removal does not erase an unread captured occurrence.
- Combine ready and pending payloads, pending layout controls, earlier pending entries, rejection, and delayed body commands. Vary settlement order under sequential, bounded, and unbounded pacing; repeat with index futures when out-of-order delivery lands. Both the captured items and final live Array must match logical command order.
- Stop early or replace the source while items remain pending. Transferred items retain their own protection; unread captures release at their last use without stale publication, lost items, or retained abandoned regions.
- Capture through the entry's private prefix, including when the body mutates that same source. Check that iterator acquisition, queries, nested entries, and closure introduce no dependency on the loop's own future completion.

Use existing public-operation, model, conflict, consistency, and lifetime verifiers. Add an independent bounded enumeration oracle for the specified dependency rules: on small Arrays, enumerate legal normalized controls and source selectors, preserve [shared internal facts and repeated occurrences](#shared-inputs-and-occurrences) and [coordinate normalization](docs/array-method-specification.md#preserve-normalizers-not-independent-intervals), and check facts at every partial-settlement state. Keep method argument positions independent. Include failure membership, root validity, write decisions, capacity outcomes, and all-ready results. Exercise capacity near the real maximum with symbolic lengths and sparse spans, without allocating those elements. Ready poison and delayed rejection use the same relevance rules and fallback; pending controls retain their legal domains until settlement. Ordinary JavaScript is only a successful-layout oracle because its eager validation differs from these failure semantics. Test accessibility with never-settling unrelated dependencies and controlled delivery, not timing-sensitive sleeps. Do not implement enumeration in production or make the oracle demand proofs outside the agreed rules.

## 12. Required-effect failures

Do not add a frozen poisoned-size state, a capacity-only marker, or a retained command-error log. Structural failure publishes the specified fallback and status/Error placements. With a known source length and otherwise settled controls, failed-count splice has a concrete fallback length; unrelated unresolved source facts can still delay that length. Subsequent operations consume the fallback's shape and endpoint relationships. Failure does not itself freeze later size writes.

### Capacity by mode

Let MAX be the ordinary maximum successful Array length, currently `0xffffffff` (`2**32 - 1`). Smaller limits such as MAX=3 in examples and model probes are illustrative; this plan adds no configurable per-Array capacity. Complete mode retains its existing capacity validation and atomic failure boundary. The two streaming modes use the [poisoned-tail rule](#streaming-capacity-revision), for both open production and finite operations:

| Mode | Capacity failure |
| --- | --- |
| Complete | A failed mutation retains current data under selected-scope status; a failed copy returns root Error. The access gate prevents exposure while that outcome remains possible. Repair clears status over retained data. |
| Sequential stream | Preserve the determined prefix and logical fallback length. Positions at or beyond MAX are structural Error data, so ordered iteration stops at its first structural failure. No capacity-only Array-root flag is added. |
| Out-of-order stream | Use the same logical data and count. Deliver guaranteed surviving occurrences below MAX; skip structural Error runs under existing terminal-failure handling. No capacity-only Array-root flag is added. |

Neither stream requires a global proof that every output fits before exposing an independent prefix. Each healthy occurrence does require proof that its final/fallback position is below MAX and its payload survives the operation. A later contribution behind unbounded earlier output may still need that position/capacity dependency. Pending controls remain pending; no speculative overflow or Error placeholder is introduced.

Complete-mode required capacity failure cannot be replaced by a smaller convenient insertion or diagnostic marker. In streaming modes, apply the declared structural fallback and the common poisoned-tail transition, preserving every previously established fact. A failed control contributes its own causal failure to affected facts; it does not automatically block the Array root merely because the intended total is unknown.

Open push-only production applies the transition at each append's reserved position. Preserve earlier commands, issued effects, historical captures and later logical ordering. Recording/querying a known poisoned tail and skipping it structurally require work bounded by the shared captured regions, relevant restrictions and causes. Alternating causes do not require one visit per position. No auxiliary capacity marker, failed-size state, timeout, or command-error history is introduced.

#### Required capacity proofs

Capacity uses the same bounded dependency rules as layout queries. Its precision is part of the contract: a wider cached interval must not introduce a wait or blocker that a required rule removes. Let L be the captured source length, k a known insertion count, and MAX the maximum successful Array length. The relationships below precede the streaming tail transformation and final count cap.

| Operation | Required length relationship or upper bound |
| --- | --- |
| fill, copyWithin, reverse, sort, and length-preserving copies including with | L. A known valid input bound can discharge complete-mode capacity without exact length; an inherited oversized or potentially oversized source cannot. Genuine mutating no-ops remain separate from new copies. |
| Valid length assignment; canonical index assignment at i; deletion | n; max(L,i+1); L respectively. An unresolved general property key is not yet an index. |
| push / unshift | L+k. With k=0 the candidate length is L. Reuse the [prescribed endpoint write](docs/array-method-specification.md#5-endpoint-and-copying-families) for identity and capacity. A returned length can depend on captured shape. An observational call creates a copy. |
| pop / shift | max(0,L-1); cannot introduce growth. Existing streaming tail Error data may remain. |
| splice / toSpliced | L-d+k, with normalized deletion count 0 <= d <= L-s. Preserve correlated totals: d=0 gives L+k; d=L gives k. Omission and defaults follow the method rules. |
| concat | Sum of classified Array-part lengths and singleton contributions, including one marker for each required failed part in a streaming fallback. Classification alone does not establish Array-part lengths. |
| slice | Normalized selected count, at most L. |
| flat | Sum of discovered output contributions, with required classification/depth/cycle checks. Use established expansion bounds; do not infer a bound from outer length alone when flattening can expand it. |

Apply these relationships through captured versions, shared controls, and composed mappings. Use the supported normalized ranges to prove total validity for complete mode, and per-occurrence preservation below MAX plus the output count for streaming modes. Preserve exact correlated totals rather than summing independently widened pieces. Otherwise only the facts still depending on those controls wait. Required failed controls follow their mode and regional fallback; capacity alone adds no streaming root blocker. These relationships do not waive argument validity, root classification, or other prerequisites.

Examples:

- With L <= MAX-1, `splice(P,0,"X")` fits for any successful start. A failed required start uses the producing mode's failure rule. With L=MAX, every **successful** start overflows. Complete mode still needs P for the visible cause. A failed start supplies no candidate and reports the start Error alone. A valid start reports capacity failure. Both leave the original Array under the selected scope's status. In a stream the failed start selects an actual fallback insertion. Apply capacity to that mapping and include both the required start failure and any new capacity loss in the mutating result. [Failed-control validity](docs/array-method-specification.md#4-fallback-preserves-the-semantic-bounds)
- A Boolean and a diagnostic can have different prerequisites even at a whole-scope gate. On healthy `r={a:fullArray,tag:0}` in Complete, issue that one-element splice at explicit root scope, capture a step on a, try `tag=9`, then repair r. Every outcome of P blocks that write and retains the same record. Shallow and deep Boolean queries issued before repair can return true, even if P never settles. The step starts no body and its rejection, the direct failure and a pre-repair Error read still need P’s actual cause. With selection and authority fixed and no outstanding host effect, repair clears the status and a later read yields tag 0. With one free slot a successful start can commit, so the write and repaired observation must wait while both outcomes remain possible. [Query and repair](poison-policy-plan.md#earlier-open-entries)
- After an unrestricted pending length assignment, the only available upper bound may be MAX. A positive-count push cannot expose a healthy appended payload without a tighter bound: a valid resize to MAX puts that payload in the poisoned tail. This capacity dependency is separate from the [selected resize/key failure barrier](#assigned-length-validity); issuance remains non-blocking. With zero arguments the candidate count stays L. The method still prescribes a length write and retains source validity, the applicable capacity policy and the returned-length dependency.
- On an accessible Array with a regional failure fallback, a later valid length reset supplies its own exact shape. An established fallback length is already concrete; genuinely unresolved predecessor shape keeps its ordinary dependencies. A reset cannot bypass an owning-path blocker.

Verify total and per-occurrence capacity decisions as well as bound soundness. Complete-mode blockers, streaming tail coverage and fallback count must not vary with settlement order, caching, or representation. Include reverse, pop, shift, slicing and prefix replacement after overflow, and final-count saturation without allocating the tail.

#### Complete mode receiving an oversized value

An explicit complete-mode receiving channel can retain a streaming-produced oversized Array. At illustrative MAX=2, a streaming push of C onto `[A,B]` produces `[A,B,E]`. A Complete cursor on that capture issues A and B and rejects at E. The same push on a Complete source flags its retained `[A,B]`. An unordered cursor on that successor issues zero bodies, and exact repair of a holder of the reached Array exposes `[A,B]`. Reception does not reinterpret the earlier producer, add an own-path flag merely for its size, truncate it, or discard its existing structural Errors. Access to existing facts follows the complete access gate and the selected placement's ordinary status; the gate does not imply that inherited length is at most MAX. A query or read does not construct a new Array merely by capturing that value.

Separate three cases:

| Operation on the inherited value | Capacity obligation |
| --- | --- |
| Existing-data observation or genuine mutating no-op | Existing blockers and Error data remain. A proved self-copy forwards the receiver and requires no new capacity validation. The endpoint methods' prescribed length writes belong to the write policy. |
| Effective complete-mode mutation | Prove the candidate successor fits MAX before committing data. A same-length prescribed write, including `a!.push()` with zero arguments, follows this rule. If the candidate count exceeds MAX, return the capacity Error and flag the retained predecessor at the selected scope. A shrink from L greater than MAX can commit when its new count fits. |
| Newly produced complete-mode Array, including an observational no-op copy | Prove that particular result's count fits MAX. A bounded slice can fit even when its source does not. A length-preserving oversized copy returns result-root Error; sharing storage does not turn the new result into a no-op. |

At illustrative MAX=3, zero-argument `a!.push()` on inherited `[A,B,C,E]` reports capacity Error and flags that retained Array. Exact-path repair reveals the same four slots including E. On an ordinary empty Array the call returns 0 and advances identity. Complete-mode mutating pop of inherited [A,B,C,E] can commit [A,B,C] and return the removed Error E. That returned Error is not a failed receiver mutation. Pop of inherited [A,B,C,E1,E2] would leave length four, so it instead fails before mutation and flags the unchanged length-five receiver. A slice(0,3) result can fit in both cases. Apply the separate capacity relationships to splice's receiver successor and removed-elements result; their counts are L-d+k and d, respectively.

Check the Array whose data successor the operation actually writes. Capturing or transferring an existing oversized value, replacing its whole location, or clearing only status creates no new Array data layout there. For a point edit of the Array itself, a proved clean-absent deletion forwards identity. An effective edit with an oversized candidate fails at its ordinary selected scope. With explicit Array scope, deleting present index 0 from inherited `[A,B,C,E]` must leave A visible after repair. Publishing absence while deciding only identity would lose A. Keep old presence/status conditional when it distinguishes a permitted no-op from a failing edit. Apply the check once in the common publication transition.

#### Oversized removed result in complete mode

Complete-mode mutating splice checks its receiver successor and removed-elements result separately. If the receiver change is valid but the removed Array exceeds MAX, commit the receiver change and return an ordinary result-root capacity PoisonError instead of the removed Array. The receiver gains no own-path poison from that independent result failure, and there is no hidden removed Array to repair. Receiver validation, authority and required mutation completion still apply; a failure of the receiver change retains its ordinary complete-mode boundary.

With illustrative MAX=3 and inherited complete-mode a=[A,B,C,E1,E2], apply each example independently:

| Call | Committed receiver | Direct result |
| --- | --- | --- |
| a!.splice(0,5) | [] | Capacity PoisonError: the removed Array would have length five. |
| a!.splice(0,4) | [E2], preserving that existing structural Error | Capacity PoisonError: the removed Array would have length four. |

Use the same outcome for ready and deferred controls, independently of private preparation order. Deliver the direct result only after the call's required receiver effects complete; deciding the result Error early does not complete the mutation. Earlier captures retain their original data. Ordinary pop of an Error value, failed receiver-capacity handling, and the prohibition on potential MAX_SAFE_INTEGER overflow gating streaming remain unchanged.

### Streaming capacity revision

The selected design direction keeps logical length beyond the ordinary Array limit and treats every position at or beyond that limit as poisoned. The user's clarification includes remapping: reverse can move tail poison into the prefix and lose formerly healthy prefix values when they move beyond the limit. This applies to the two streaming modes, not complete mode. It is the common streaming capacity transition, rather than a second overflow representation. The user's tolerance for an exceptional fallback in astronomically oversized failed results permits the capped-count rule below. The implementation must integrate virtual indexes, direct results and compressed spans through the existing logical-property boundary. The [failure inventory](poison-policy-plan.md#whole-array-failure-in-streaming-modes) distinguishes the other selected boundaries.

Let MAX be the ordinary Array length limit and N the determined logical result length, subject to the exceptional count cap below. The common transition first applies the operation's ordinary mapping, including all earlier Error data, then makes its result region [MAX,N) structural Error. Preserve mapped existing structural Error placements and their causes; replace newly lost contents/presence with capacity Error attributed to this operation. Represent the tail as compressed spans, not one retagged Error for its entire extent. Do not retain displaced values for repair. Existing Errors moved below MAX remain Errors; an ordinary later assignment below MAX can replace one. Earlier captured versions retain their own data. If a flagged ordinary occurrence is displaced into the tail, the new capacity slot replaces its data and its positional flag. Exact-slot repair still exposes the capacity Error. If the mapped occurrence already has structural Error S under its own flag F, preserve the whole placement. Lookup reports F, repair exposes S, and transporting it incurs no new loss. Apply the projection once per logical operation. A healthy occurrence can be exposed only after its output membership and position bounds prove that this transition preserves its payload. An append-only overflow therefore cannot invalidate an established prefix, but an unresolved insertion before an occurrence can still leave its capacity eligibility unresolved.

Using a small illustrative MAX=3:

| Operation | Successor and consequence |
| --- | --- |
| [A,B,C].push(D) | Length 4, [A,B,C,E]. The mutating push reports capacity failure, but commits the tail Error position. This is partial structural publication, not a failed no-op. |
| [A,B,C,E].pop() | Length 3, [A,B,C]; removed-value result E. The length change completes even though the removed value is Error. |
| [A,B,C,E].shift() | Length 3, [B,C,E]; removing the overflow tail does not restore its discarded D. |
| [A,B,C,E].reverse() | Length 4, [E,C,B,E2]. The former A moves beyond MAX and is discarded in this successor. |
| [A,B,C,E].slice(0,3) | Independent length-3 result [A,B,C]. Source failure and earlier captures are unchanged. |

E and E2 denote structural capacity Error data, not optional positional flags; unordered delivery cannot ignore their existence when deciding terminal success. Reuse existing Error transport and structural-run skipping rather than enumerate an enormous poisoned tail. Clearing own-path status cannot recover discarded payloads. Shrinking or removing Error positions can remove this failure without a special overflow repair operation. Native export still cannot assemble an oversized Array and must fail before allocation; this does not poison the managed source.

#### Preserve loss at each operation

Every semantic operation consumes its predecessor after that predecessor's tail transition. At MAX=3, [A,B,C] followed by unshift(X) then shift() produces [A,B,E], not [A,B,C]. Reversing [A,B,C,E1] twice can likewise leave [E2,B,C,E1]. A tree may flip orientation to calculate each reversal's mapping, but its successor must also represent the loss before a following operation consumes it. Never cancel or fuse edits across this loss unless the replacement preserves data, presence, Error causes/roles, counts and prescribed effects. A proof that all affected layouts fit can retain ordinary simplifications. Use spans/restrictions for the loss; no command-history ledger or full-array scan is required.

The final logical count cap is also part of each operation: at that cap, a failed push followed by pop reduces the settled length by one and cannot be cancelled. When a safe simplification is unproved, retain the symbolic projection/clamp rather than waiting for global size readiness. Optimization uncertainty creates no new publication barrier.

#### Tail causes and result failure

Two overflowing pushes at different source locations produce distinct causal Error regions. After pushes of D and F onto [A,B,C] at MAX=3, positions three and four retain the first and second push's causes respectively. Moving or retaining an existing structural Error preserves its cause. An explicit overwrite or removal applies its prescribed mapping before the tail projection. A newly lost replacement is attributed to that operation. Write identity follows the command's prescribed publications. Coalesce uniform-cause spans only when all their structural and causal facts agree. Share joins and repeated subtrees across alternating causes. Aggregate skips and deduplicated collection can cross those boundaries.

A streaming mutator reports capacity failure for required positions it loses in this command. Transporting inherited structural Error through an oversized successor preserves the ordinary result and prescribed writes. At MAX=3, shifting `[A,B,C,E1,E2]` returns A and commits `[B,C,E1,E2]`. Mutating splice removing all five commits `[]` and returns the removed Array with its two inherited structural Errors. A reverse that newly loses healthy A reports its own capacity failure and commits the projected mapping. Full export of the reached oversized Array returns a capacity Error at export before processing its prefix. Exporting a bounded slice uses that slice’s visible causes. A failed capture discards assembly work before a native size exception could add another cause. [Export completion](docs/outbound-export.md)

At the final logical count cap in a streaming mode, a nonempty append can have no representable new position. Its direct result is the new operation's capacity Error. Preserve the existing receiver length, data, tail causes and identity when no data/status publication occurs; do not retag old tail slots, add an own-path flag, or keep an invisible failure log solely to store the new cause. Required command ordering and effect completion still apply. Zero-argument `push()` has no missing new occurrence. It returns the captured length on success and commits its prescribed length write, advancing receiver identity once.

Apply that direct-result rule to any prescribed growth beyond the count cap K. The requested extent cannot be published even when every retained virtual slot already carries structural Error. At illustrative MAX=2 and K=4, start with four distinct structural Errors `[E0,E1,E2,E3]`. Mutating `unshift(X)` commits `[X,E0,E1,E2]` and advances identity. The displaced E3 falls outside the result. Mutating `push(X)` from the same initial state commits no representable change and forwards identity. Both direct results report the new command's capacity failure. Use the existing count and publication decisions. An observation copy receives the projected Array under its own result contract.

#### Maximum logical count

The maximum fallback logical length is Number.MAX_SAFE_INTEGER. Retain the count through that limit so a later pop or end-relative selection uses the exact captured extent. Compact flattening/repetition can exceed the new bound without a correspondingly large input. Cap such an already-failed result's length at Number.MAX_SAFE_INTEGER, with its entire region beyond MAX still structural Error. Do not round arbitrary oversized counts, make decrement a no-op, allocate one record per virtual slot, or introduce BigInt. Use cap-aware sums for counts that may saturate. Compute retained positions and source offsets exactly by subtracting proved bounds before adding. The [copyWithin selector](docs/array-method-specification.md#copywithins-coupled-coordinates) applies this at both exact and uncertain bounds. This preserves exact subsequent count arithmetic, pop, the healthy prefix and the absence of a root blocker; it explicitly abandons exact requested extent above that second bound. Apply the cap to the operation's final output count, not an intermediate sum before a deletion, and preserve every issued command's required effects and failure result. Saturating nonnegative count evaluation may stop once that final-count threshold is proved; it must not expand the mathematical output to discover its exact size.

Potential Number.MAX_SAFE_INTEGER overflow must not gate streaming, trigger a global size preflight, or delay an otherwise established occurrence, observation or effect. Apply saturation as ordinary count evaluation reaches the threshold; no proof that all future production stays below it is required. A query that actually needs an unresolved end/length retains that semantic dependency, and healthy payload publication still respects the much smaller MAX boundary. Those are ordinary data dependencies, not permission to introduce a separate maximum-count safety gate. The sole numeric concession is the cap on the exact mathematical extent of an actually oversized failed result. The capped count, retained positions, failure and effects are deterministic on every settlement schedule.

The capped length is the actual settled fallback length, not a lower-bound counter hiding an unknown larger sequence. Later operations consume that fallback normally, without inheriting counterfactual position uncertainty; this is the same [ordered fallback rule](poison-policy-plan.md#ordered-and-irreversible-fallback) already used after failed structural controls. In particular, reversing a length above twice MAX loses the entire healthy prefix to the poisoned tail, while the output prefix consists of poison. A valid truncation or replacement can re-establish a small shape. Ready and deferred executions must choose the same fallback at the same logical operation. All schedules preserve the same ordering, fallback results and effects, including on failure and after repair.

Retain the first K positions of the operation's ordered mapped output, where K is Number.MAX_SAFE_INTEGER. Resolve back-relative selection against this retained extent. At length K with final structural cause E, `a.concat([X]).at(-1)` selects E. Prepending X instead shifts the former last position beyond the cut. Neither a discarded occurrence nor its cause contributes to iteration or collection of that result. Preserve independently owed input actions and direct mutation failures. For a concat whose prefix already has length K, a later part of unknown width cannot change the retained count, suffix or capacity projection. Release its use for those questions. An exact count of the mathematical overflow and a global K preflight would both add unnecessary waits. Apply the same clip when a bounded skip crosses the end.

For splice with determined count L, deletion d and k insertions, first compute `kept = L - d`. Compare k with `K - kept`. On equality the count fits exactly. On excess, publish the first K mapped slots and report failed requested growth on the mutating call. On an unordered receiver already at K, `splice(failedStart,0,X)` chooses the end, clips X and preserves the former last slot. Its direct result includes both the start and growth failures. On either boundary the retained count is K. Only form `kept + k` when the sum fits. Generalize the same comparison to joins and window extensions with their respective effect rules. With L=K, d=2 and k=2, computing `(L+k)-d` in JavaScript loses one slot to rounding. With k=3, the correct retained count is still K but the requested growth fails. Use structural spans around both real limits to check retained causes, writes and the direct result under different delivery schedules.

Integration must cover virtual numeric-index recognition, writes/deletion in the permanently poisoned tail, compressed Error causes and count/status queries, the separation of a failed mutator's direct result from its committed successor, and oversized copying results. These follow the common tail transition where possible; do not leave finite copies using the old root-capacity gate or apply the clamp only to push. The [streaming failure inventory](poison-policy-plan.md#whole-array-failure-in-streaming-modes) separately identifies other whole-result barriers; an overflow change does not automatically resolve them.

#### Virtual positions and full consumers

Keep creation of an ordinary Array index distinct from selection of an existing virtual position. The existing canonical-key rules still reject creating index "4294967295" on an empty Array; do not make every integer below Number.MAX_SAFE_INTEGER a growable ordinary key. A position in the captured virtual tail can instead be selected using its logical membership facts and yields its retained structural Error. Preserve canonical spelling, absent/out-of-range rules and ordinary non-index rejection outside that virtual range. Pending membership retains only the dependencies needed by the actual selection. Host import must not reinterpret named native Array properties as virtual elements.

For a streaming edit to a virtual member, apply its ordinary mapping and tail projection in one publication. At MAX=3, deleting index 3 of `[A,B,C,E1]` produces `[A,B,C,Edelete]` of length 4. Removing the old slot would create a hole in the required Error tail, so the deletion supplies the cause and advances identity. The old capture retains E1. No reader observes a transient hole. Deleting ordinary index 2 instead leaves a hole there and retains E1. Resolve virtual membership before treating a key as selectable. Removal of positions and valid truncation can shorten the tail. The extent of an oversized result grants no new index-creation authority.

`hasError` can finish from one known tail failure. Full `getErrors`, export and intrinsic Array-to-string conversion stop on a reached oversized Array with one recoverable capacity Error. A lower bound above MAX suffices. A possible future overflow adds no readiness barrier. A bounded selection consumes only its own range and preserves the causes of its selected positions. Traverse required shared subtrees once per restriction. Retain ordinary whole-Array or ancestor access gates, required argument stages and independently owed effects. [Reporting boundary](docs/array-method-specification.md#native-diagnostic-list-capacity)

### Assigned length validity

In every mode, a loop capturing the Array after an explicit `a.length = n` waits for that write's resolution and publication before its first item or successful empty exhaustion. On an invalid or poisoned length, report the causal failure and retain current data under the selected own-path status. With `[A,B]` and a pending length, success at 1 yields only A, while failure yields zero items. A cursor captured before the write still sees `[A,B]`. An explicit length write and a method that changes the count through a regional mapping have different failure footprints.

Use ordinary assignment scope for this intrinsic in every mode. In `r={a:[2,1],tag:0}`, assign `r.a.length=n` with explicit authority and failure scope at r. Next capture a cursor on a, assign tag=9 and repair r. With n=1 the cursor gets 2 and repair exposes tag 9. With n=−1 the cursor gets zero items, the tag write encounters r's blocker, and repair exposes the original record. With default scope the failure belongs to a and the sibling write commits. A failed computed key similarly belongs to its reached prefix or selected broader owner. Only selected controlled methods have the streaming footprint exceptions. Check a dependent write through its captured publication, including when the public assignment returned an issuance acknowledgement. [Structural failure ownership](docs/data-limitations.md#mutation-scopes-and-ownership)

The successful-layout wait and the failure policy are distinct. Unknown survival requires waiting even if the input is guaranteed healthy. Retaining own-path poison on actual invalid length is the selected failure exception, not a consequence that sequential equivalence alone dictates. An unresolved general mutation key can select length and has the same unrestricted problem; once a target is known or proved regional, use its ordinary narrower dependency/failure rules. Do not transfer this whole-region barrier to known-index payload assignment or a controlled range operation.

The user selected keeping this exception in the two streaming modes for simplicity. Reuse existing dependency gates; introduce no regional failed-resize fallback, special suffix access, or separate recovery mechanism. Failure retains current data for ordinary status-only repair. A later push or unshift cannot bypass that possible own-path blocker merely because its new values would survive every successful earlier write.

For `a.length = pendingLength` followed by `a!.push(X)`, successful resizing cannot delete the later X; its index can remain unknown. Nevertheless, X is publishable only after earlier whole-path failure is excluded and its position is proved below MAX. Small valid lengths and the valid length MAX give different payload-versus-tail-Error outcomes. Removing whole-path poison would not remove this unrestricted capacity dependency. This uses the ordinary Array limit, not potential MAX_SAFE_INTEGER overflow; the latter still adds no global streaming gate.

Release work as soon as existing validity and bound proofs suffice, without requiring unrelated payloads or exact count. Unordered delivery can then expose X with a pending index; sequential delivery retains its prefix requirements, and the push's numeric result retains its completion dependencies. No new range-provenance machinery is required to obtain tighter proofs for unrestricted application inputs.

### Controlled self-copy: semantic no-op

When copyWithin's normalized source and destination starts are provably identical, every possible copied position maps onto itself. Values, presence, length, and identity remain unchanged. The mutating call returns its receiver and prescribes no data writes. End is therefore irrelevant under the [universal argument rule](#universal-rule-irrelevant-arguments-never-introduce-poison), rather than a special exception for this method or parameter. Selection and authority still precede the call.

Avoid mutation isolation/copying once the no-op is known. If necessary preparation created a private representation before the decision, finish it as no-effect and preserve the original captured identity using the existing forwarding/assembly mechanisms. Observation mode retains its ordinary distinct-result contract and may share backing storage rather than copying elements.

This revises controlled self-copy's write rule, not equal-value writes: an explicit same-value assignment and two cancelling mutations retain their prescribed effects. This no-data-write proof needs no old-value comparison or failed-identity state. It does not justify preserving identity for a different-position copy that performs a write, even when its resulting values are equal.

No general rule erases a write whenever a source maps to the same position. reverse does not write its middle position; controlled self-copy has this explicit no-op rule; sort still prescribes writing a present singleton and therefore advances identity. Those per-method write rules remain independent of comparator relevance.

## 13. Selected decisions

Mode is selected per channel through a constructor argument/option, with out-of-order stream as the default. Complete and sequential stream are explicit choices. The kernel constructors accept `CHAIN_MODE.Complete`, `CHAIN_MODE.Sequential` and `CHAIN_MODE.Unordered`. The embedding inherits the source mode for transparent temporaries and uses the declared mode for an explicit receiving channel. [Construction contract](poison-policy-plan.md#cascada-mode-selection)

The user selected [indexed command-buffer branches](#indexed-branches-for-unordered-bodies) to preserve final captured/fallback order despite out-of-order delivery. The user also selected a whole-Array/path failure for required sorting failure, including unordered mode: explicitly requesting sort requires ordering. This supersedes healthy unordered sort fallback. Publishing a new own-path flag is itself effective for identity, so unchanged payloads no longer imply a no-effect failed mutating sort.

Bounded unordered admission has a selected [stage 7 design](#bounded-window-iteration): captured range containment, one extension per newly finalized position (body completion or proved structural skip), and independent trimming of the finalized prefix. B bounds unfinished positions rather than numeric width. The compiler rewrite owns the pacing integration and future `break` lowering.

The following is the normative sort failure contract. Other planning documents link here for these outcomes:

1. **Preparation/comparison failure in mutating sort.** Finish required sorting before publishing its data writes. If required preparation or comparison fails, `a!.sort()` reports the failure and publishes repairable own status in every mode. Complete mode preserves the ordinary selected-scope rule; in streaming modes the affected Array owns this failure. Retain the captured pre-sort data, payload producers, holes, aliases, and existing structural roles; publish no fallback permutation. Repair exposes that unchanged data without retrying sorting. For `[undefined,B,A]`, repair exposes `[undefined,B,A]`. This is the ordinary complete-mode rule and an explicit streaming exception. No sort data writes committed, so no rollback or repair-only predecessor is needed.

   Apply the common owner-publication rule as soon as failure, retained data and ordered effects are fixed. For `r={a:[s,2,p],tag:0}`, with s a Symbol, default mutating sort at explicit root scope must prepare two or more keys. The conversion of s fails. Even while p is held, the failed owner’s Boolean status is true and exact repair can expose its retained data. A `tag=1` issued between sort and repair is blocked in Complete and survives in either stream, where the failure belongs to a. The direct result, a previously issued failing cursor step and complete Error collection still need p because it can contribute another cause. Keep those consumers on their captured failure through repair. With `[s,p]`, delivery of `undefined` would make comparison unnecessary, so even the failure decision can still depend on p. [Publishing at the owner](poison-policy-plan.md#publishing-a-nested-mutation-at-its-owner)

2. **Copy-producing sorting.** On the same required failure, `a.sort()` and `a.toSorted()` return ordinary result-root poison in every mode and preserve a. No repairable failed copy is exposed or retained. Required sorting success precedes result/item exposure, including a fixed undefined/hole suffix.

3. **Publication after ordering succeeds.** Resolve every remaining prerequisite that could still fail the entire Array before publishing any sorted slot or allowing dependent writes. Once any sorted item is visible, subsequent failure from that work can only affect a region or independent result whose declared outcome preserves everything already published. Complete mode keeps candidate writes private through required success. Managed backing synchronization cannot veto canonical logical storage.

Existing source blockers retain their ordinary propagation boundary. An unused comparator introduces no failure; required failures retain their original causes. No missing-output marker duplicates this whole-Array failure. Publishing a new own-path flag is an effective semantic publication even though no payload moved. Successful sort retains its ordinary prescribed writes and identity rules.

Sequential equivalence covers successful and failed operations, intermediate effects, and data exposed by later repair. Each mode applies its declared failure scope. An operation that can still poison the entire captured Array gates every item and all subsequent effects that depend on that scope. Regional failure preserves independent survivors under the selected streaming rules. The [review](docs/iterate-sequential-equivalence-review.md) records the witnesses and outstanding runtime integration.

### Mode-specific validity and completion

**Complete mode.** Apply the [complete-mode validity rules](poison-policy-plan.md#tracking-complete-mode-validity) before the first successful item or healthy empty completion. An earlier source producer that can still poison this captured Array keeps that access pending. Once relevant failure is excluded, established occurrences may be consumed without awaiting unrelated payload or layout work. A loop that then stops early cannot later acquire source-own poison from that earlier production. Later source mutations belong to successor captures. Closing before the first gated step finishes still preserves the already-issued step's required dependencies; local return is not healthy exhaustion.

**Sequential and out-of-order streams.** Both must exclude an earlier whole-Array failure before delivering an item. Structural failure confined to a slot can still be reported at the ordered obstruction or at unordered terminal completion after survivors. Apply Cascada's declared failure targets and lowered break/return guards at every affected scope. Suppressing later bodies while continuing enumeration leaves the normal terminal reporting obligation in place. [Compiler ordering](#compiler-ordering-and-loop-failure)

**Integration and lifetime.** Cursor return releases unread enumeration; it does not certify completion of an issued step, body effects or a separate loop-failure dependency. Use existing operation/loop ownership for those obligations without retaining a closed cursor's source solely for reporting. Verify ready/deferred source failure, early break/return, affected-variable reads after the loop, no body issued, and source release while independently required work remains. In every mode, a possible whole-Array failure precedes body exposure and repair-dependent effects. Separately test a regional failure after a delivered prefix and unordered survivors on both sides of a failed slot. Neither mode may select an outcome from settlement timing. These are implementation acceptance requirements, not a request to redesign Cascada's existing control flow.

The break/return completion question is resolved by the scope-based channel contract. Check any early-close optimization against that contract, including a return nested in a loop followed by code in its parent scope. The low-level cursor's local cleanup does not create, detach or settle obligations already owned by loop or operation work. This is implementation verification, not an outstanding language decision. Source structural completion can still wait, while skipped bodies need not consume unused payloads.
