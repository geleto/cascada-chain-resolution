# Array iteration repair history and measurements

The November 28, 2026 retrospective records 78 runtime repair families, 15 planning findings and seven verification findings. Its 1–10 robustness and potential ratings describe each repair at that snapshot. Current refactor decisions use public witnesses, measured work and deleted implementation paths. ## What has actually been going wrong?

The ledger below groups the retained review findings into **78 runtime repair families**. Each family contributes once, under its primary observed consequence.

| Primary consequence | Families | What counted |
| --- | ---: | --- |
| Wrong result or effect | 25 | Incorrect data, presence, identity, Error or scope, host action or data visible after repair |
| Required progress lost | 15 | An answer, effect or independent branch could wait forever after its decisive facts were known |
| Fatal on a supported program | 5 | A valid resume, second cursor or deep command history could kill the execution |
| Excess work or allocation | 22 | The result was correct, but the implementation repeated avoidable work. Severe cases exhausted resources |
| Excess lifetime | 11 | A completed or narrowed consumer kept values, regions, gates or contexts alive while another input stayed open |

That gives **45 behavioral, progress or fatal families and 33 work or lifetime families** under this grouping. One independent check on the classification is the November 25 19-sweep review. Of its 14 named runtime reports, six were R1, W1, S1, S4, D1 and D2, covering crashes, a hang or wrong language behavior. The other eight were S2, S3, S5, S5b, S6, S7, S8 and L1, covering work or lifetime. The reviews selected deliberately difficult programs, and grouping several symptoms under one fix changes the totals. Neither ratio estimates how often an application will hit a bug. [19-sweep reconciliation][independent]

Numeric extremes explain some findings. Examples include preserving the original cause when moving an already lost slot, capping a diagnostic collection, and precise virtual indexing. The cutoff permits a simple shared Error. It does not justify growing a per-position diagnostic structure. By contrast, the hidden-child read needed one slot, a flagged hole changed sorting and flattening in two slots, and an ordinary three-item capture sufficed to strand a determined prefix. A long **command history over a small Array** is also a different dimension from a huge Array. [Array contract][contract] · [Point and range reproductions][follow]

There is evidence against abandoning the feature and against trusting one more clean pass. The ordinary Array and the optimized one can share a sequential meaning. One cut now supplies both parts of a splice, exact width readers share their producer, and placement versions preserve historical data through writes. In the other direction, a frozen review found no further issues on a snapshot where a later reviewer reproduced four issues in argument demand and lifetime. The coverage had stopped producing new distinctions. The reviews suggest that an LLM can implement the smaller mechanisms and also miss interactions shared by its implementation and its tests. Establishing a real-world defect rate would require independently evaluated usage evidence. It does show where to spend a human reviewer's attention. ## Where the design can buy more correctness

Three mechanisms elsewhere in this kernel illustrate the standard to aim for.

| Existing mechanism | The invariant enforced in code | Application to iteration |
| --- | --- | --- |
| Captured property version and placement gate | Install the destination transition before suspension. Readers keep the version they selected. Completion commits presence, status and baseline and releases the writer. Proof of obstruction may precede delivery of its exact cause. | Every access to a captured Array must pass its applicable scope gates. Once admitted, point access should project one selected placement. This fixes both early exposure and waiting for the wrong thing. [Placement implementation](../src/property-versions.js) |
| Operation owner and release at last use | One open fact, an idempotent close and removable release actions bound private observation work. Shared settlement continues for other readers. | Close a cursor's unread traversal independently of a pull it already issued. Give a count reader a numeric receipt and a point reader only its possible holders. [Owner implementation](../src/operation-lifecycle.js) · [Cursor implementation](../src/iterate.js) |
| Incremental parent placements and retirement | Maintain forward and reverse relationships at publication. At a graph transition, work from affected candidates and genuine live roots. The independent ownership model can check what should survive. | Derive candidate retention from the selected source ranges. Acquire surviving protection before releasing obsolete ranges. Test an orphan cycle and the same cycle with a genuine observer. [Parent placements](../src/parent-placements.js) · [Retirement](../src/ownership.js) · [Ownership model](../test/experiments/phase2-ownership-model.mjs) |

**The weakness is repeated interpretation of one fact.** A splice can identify its retained prefix while a bounded slice, point lookup, Error query, Unordered occurrence search and ownership calculation each decide independently what that proves. A correction in one reader then leaves a plausible wrong answer in another. The strongest existing Array code already shares the cut between prefix and suffix and transfers retained operands together. The largest remaining opportunity is to make the *meaning* of that cut authoritative across readers. The technical analysis already asks for this division between method semantics and storage. [Dependency rules](array-iteration-technical-analysis.md#2-keep-the-evaluator-separate-from-storage) · [Splice selection](../src/array-splice.js) · [Selected operand lifetimes](../src/array-sequence-layout.js)

Concretely, a captured splice has a predecessor version, normalized start and count, insertion occurrences, producing mode, and selected failure scope. From those facts its rules answer a short list of questions about whether a point exists, which predecessor placements or insertion can supply it, which range survives, which occurrence is guaranteed, and whether failure is certain. Each answer identifies the remaining prerequisite if one exists. A point reader consumes a selected placement, a length reader consumes bounds, and a Boolean observer can consume certainty while an exact-cause observer waits. The same possible sources determine what a reader must protect. This is a specification of the existing questions. A production implementation can compute only the projection requested. [Closed fact and query vocabulary](array-method-specification.md#2-closed-fact-and-query-vocabulary) · [Current sequence selection](../src/array-sequence.js) · [Occurrence traversal](../src/array-occurrences.js)

There is a real limit to consolidation. Ordered traversal owes the first obstructed position. Unordered traversal owes exactly-once eligible occurrences, bounded credit and terminal reporting. A directional search owes a qualifying first or last index. Storage may borrow a fixed prefix while another route constructs a private dense backing. Those operations can share a fact and have different completion conditions. An earlier experiment forcing one execution route lost **13 progress checks and 9 work or lifetime checks**. Another forced remap path lost a required `fill!` failure. Carry those witnesses into any proposed deletion. [Simplification trials](../simplifications.md#claude-review-follow-up-2026-11-24)

Consider one concrete boundary. Capture `[A,B,C]`, issue `splice!(start,count,Y)`, and export the first two successor slots. With both controls held, start could be zero, so publishing `[A,B]` would be wrong. Once start is two, any regional deletion or regional failure starts at position two. Both streaming modes owe `[A,B]` now. In Complete mode a count failure could still invalidate the whole capture, so the successor export waits. In every mode the older snapshot still yields `[A,B,C]`. A single cut and its enclosing validity gate explain all four observations. Issuing an extra lookup must not change them. [Range progress regression][follow]

### Point readers retain excluded operands

At `d6e668c`, keep only a capture of index 2 of streaming `[A,X,Y].toSpliced(1,p)`, with X and Y distinct managed children. Clear the source and result holders. A normalized count of zero selects Y, a count of one or greater selects absence, and rejection selects the count Error. In both streaming modes X and Y remained live with p held. A V8 heap snapshot showed the original native Array had collected and the pending `SelectedLayout` kept two individually captured placements. X was its left input and Y its right. Keeping only length or clearing every reader released both children. Holding an old snapshot preserved both. A write through a separate owner of Y left the saved point’s Y intact.

The same failure needs no splice. With only index 1 of `[X].concat(tail)` held, every possible element at that index comes from the tail. A lookup, `at(1)` and a captured point each retained X while the tail was open. A heap snapshot traced X through the sequence head’s captured placement. An empty tail, a one-element tail and a rejected tail subsequently delivered absence, that element and the original Error respectively. This is an operand-lifetime defect on two public routes. The observed values and failure scopes were correct. [Splice suffix selection](../src/array-splice.js#L213) · [Regional point capture](../src/array-region.js#L136)

Use a separately supplied tail to isolate the selector from physical storage. The left source cannot contain Y when the point is issued. With both inputs held, the point reader can release X immediately. A genuine borrowed native view can keep its physical backing, including out-of-range slots. Pair the collection test with that control and an outstanding Complete result that still owes its data. [Backing lifetime](array-view.md#incoming-placements) · [Required ranges](array-method-specification.md#restrict-source-retention-through-the-mapping)

Run this block from the repository root with `node --expose-gc --input-type=module` on standard input. The final assertion fails on the baseline for both routes in both streaming modes. Use the same public cases to qualify the replacement.

```js
import assert from "node:assert/strict"
import * as r from "./src/index.js"

function issue(method, mode, ctx, tail, count) {
    const raw = method === "concat" ? [{id: "X"}] : ["A", {id: "X"}]
    const outside = new WeakRef(raw.at(-1))
    const wrap = value => new r.Chain(value, ctx, mode)
    const a = wrap(r.import(raw, ctx))
    const joined = wrap(r.run(a, [], "concat", [tail.promise], ctx, {}))
    const out = method === "concat" ? joined : wrap(r.run(joined, [], "toSpliced", [1, count.promise], ctx, {}))
    const point = r.capturePath(out, [raw.length], ctx, mode)
    for (const holder of new Set([a, joined, out])) r.assignPath(holder, [], undefined, ctx)
    return {outside, point}
}

const retained = []
for (const mode of [r.CHAIN_MODE.Sequential, r.CHAIN_MODE.Unordered]) {
    for (const method of ["concat", "toSpliced"]) {
        const ctx = {execution: new r.Execution(), errorContext: method}
        const tail = Promise.withResolvers(), count = Promise.withResolvers()
        const {outside, point} = issue(method, mode, ctx, tail, count)
        for (let i = 0; i < 6; i++) {
            await new Promise(setImmediate)
            global.gc()
        }
        if (outside.deref()) retained.push([mode, method])
        tail.resolve([{id: "Y"}])
        count.resolve(0)
        assert.equal(await r.lookupPath(point, ["id"], ctx), "Y")
    }
}
assert.deepEqual(retained, [], "only the pending tail can supply the captured point")
```

### Captured ranges and slice history

The technical analysis already calls for a demand-driven selector and the layout design already groups methods by edit. The November 28 experiment described a captured source range by its origin, extent and direction. Joining ranges, restricting them, reversing one, or repeating a single placement describes the healthy output of **13 of the 22 methods**. A range can still depend on an unresolved cut. Its repeated uses share the same normalized fact. [Earlier analysis](array-iteration-technical-analysis.md#2-keep-the-evaluator-separate-from-storage) · [Method families](../array-layout-approaches.md#8-method-families)

| Methods | What the common mapping can express |
| --- | --- |
| `splice`, `toSpliced`, `with`, `fill`, `copyWithin`, `push`, `pop`, `shift`, `unshift` | Replace an interval with captured ranges. Endpoint edits use the first or last boundary. Fill repeats one placement. An overlapping copy reads each copied slot from the pre-write version. Mutating splice also selects the removed range. |
| `slice`, `concat`, `reverse`, `toReversed` | Restrict, join or reorient captured ranges. A copy can densify selected holes. Adjacent source positions can remain distinct even when they hold the same managed value. |
| `at`, the three searches, `join`, `toString`, `flat`, `sort`, `toSorted` | Consume the same captured placements where applicable. Lookup, search short circuits, conversion, discovery with cycle handling, and sort comparison each have their own demand and failure rules. |

Use the mapping in both directions. From a source occurrence, ask which output ranks it can reach and whether it survives. From an output window, ask which captured sources can still supply it. For a healthy splice at s deleting d and inserting w, prefix index i stays at i, insertion j goes to s+j, and surviving suffix index i goes to (i−d)+w. Removed index i goes to i−s in the direct result. Intersect those ranges for front or rear reads. Keep the original cut in that calculation when the extent is unknown. Check remaining capacity before adding offsets and apply the specified capacity projection at each command. A sole point reader could then retain the candidate ranges at their original coordinates directly. The current capture constructs a padded sequence to preserve those coordinates. [Current point capture](../src/array-splice.js#L466) · [Count cap](../iterate-plan.md#maximum-logical-count)

Three small examples expose the information each projection needs.

- **Which source can reach a position.** On `[A,B].toSpliced(1,k,X).at(-2)`, k=0 gives X and k≥1 gives A. For a failed k the streams give X and Complete returns its Error. Treating the suffix length and deleted count as independent admits the impossible source B. Both streams can already answer `includes(X)` while k stays pending. The point still waits.
- **Whether an occurrence survives somewhere.** On Unordered `[A].toSpliced(s,0,X)`, either point can hold A or X and `includes(X)` already returns true. Starting at `[A,X]`, issue `copyWithin!(0,1,p)` then `copyWithin!(1,0,q)`. Each point has the same two possible healthy values, yet p=0 and q=1 gives `[A,A]`. Here membership must wait. Shared occurrence traversal already replaced a separate insertion scheduler and retry list. Keep its occurrence and rank evidence available to searches and bounded cursors. A cursor also needs window eligibility, skip credit and terminal status. [Occurrence traversal](../src/array-occurrences.js) · [Earlier simplification trials](../simplifications.md#claude-review-follow-up-2026-11-24)
- **How much history can collapse.** Give `slice(-3).slice(0,2).slice(-1)` an unknown nonempty predecessor. For lengths 1, 2, 3 and 4 the single survivor comes from index 0, 1, 1 and 2. A fixed offset or one clipped expression of the form `clamp(length+k,low,high)` cannot select those indexes. More generally, keep the first or last j positions for j=k down to 1. For initial lengths 1 through k+1, each choice of the last j adds one to the survivor's origin exactly when the initial length exceeds j. That gives 2^k distinct origin profiles with the same final width. Fuse restrictions when their equivalence is proved. An unresolved origin may still need information from several cuts. [Composition rules](../array-layout-approaches.md#52-remap-composition)

**A concrete slice simplification.** For consecutive crops with known limits on one captured sequence, let n be its eventual length and c the smallest limit so far, initially the maximum possible length. A new limit t sets `next = min(c,t)` and the surviving width becomes `min(n,next)`. Keeping the first t preserves the first source index. Keeping the last t advances it by `min(n,c) − min(n,next)`. A looser limit disappears. Consecutive tighter limits on the same side combine into one because the width differences telescope. Mixed directions need at most one such term per surviving run of back cuts.

### Prefix index fallback

A separate arithmetic model isolates the avoidable coordinate walk. Keep A at zero and a log beginning with B,C. Each pair appends its two elements to the log. At step t (one-based) its length is E = 2+2t. If h is the previous head of the surviving suffix and the healthy nonnegative count is c, the new head is `h + min(c,E−h)`. Two adjacent transfers of that form compose into one clipped addition. A balanced interval index can update a delivered count and read the head for a historical prefix in logarithmic work each. An open count has a lower transfer with c=0 and an upper transfer that clips to E. Monotonicity makes the resulting endpoint bounds exact on this healthy domain.

The model matched enumerated native splices at 375 intermediate prefixes of three-step histories with held, zero and clipped counts. At H = 120, 240 and 480 it took 840 / 1,920 / 4,320 pair compositions to update the index and 528 / 1,172 / 2,580 to answer all H final point questions, with the same results as native Arrays. These counts measure arithmetic on coordinates. Correctly waking previously issued readers, handling failed controls, sharing or releasing managed sources, and preserving earlier publications remain production obligations. [Open issue and acceptance](array-iteration-robustness.md#known-work-bound-violation)

### Cost of ready middle splice

On a dense Array of scalars, repeat a two-item append followed by `splice!(1,1)`. The receiver presented to each splice has 5, 6, …, H+4 slots. At H = 40 / 80 / 160 the physical-copy loop read **980 / 3,560 / 13,520** slot descriptors, once per input slot each time. All three ready modes did that work at issuance. Deferred Complete did the same work during settlement. The streaming deferred path made zero visits to this particular loop. Deleting three instead kept the graph small and made only five descriptor reads in the loop across each run. A ready front deletion used the existing endpoint route. [Ready dispatch](../src/array-splice.js#L295) · [Physical capture](../src/array-remap.js#L139)

Use these structural counts to evaluate sharing unchanged spans and any eligible private-storage edit. Count unavoidable native moves, demanded source inspection, changed parent keys, and gratuitous reconstruction separately. One incoming logical owner does not establish storage permission. A borrowed slice, a pending placement destination, or the predecessor needed on failure can still use the backing. In-place publication needs existing permission and a commit that preserves those observations on every supported failure. Restoring an old address for identity is a separate retired proposal. Machine timings need matched payloads, sizes and setup before they can support a kernel-wide budget. ## Scored runtime inventory

**Now** rates the scope of the implemented prevention. A 1–3 is a correction tied to a single route or symptom. A 4–6 closes a real path while adjacent paths still require independent care. A 7–8 establishes a shared rule with identifiable gaps in coverage or an important caller obligation. A 9 places the fact at its natural owner and has evidence from distinct callers or adverse controls. A 10 would make the same failure impossible through every supported construction and demonstrate that property across the public paths. **Potential** rates the strongest proportionate solution available under the existing contracts. A 10 is a credible target for that particular invariant. Some specialized algorithms are already as shared as they should be. The numbers are judgments about breadth of prevention, independent of severity, confidence and test volume.

Each row groups reports that ask for the same correction, gives the observable witness or cost, and identifies how to realize or retain its potential. Categories record the primary consequence. A resource failure can also terminate an execution. Historical measurements belong to their cited revisions.
