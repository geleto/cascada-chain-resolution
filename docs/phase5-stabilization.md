# Phase 5: Runtime stabilization specification

**Status: specified; execution and acceptance are pending.** This is the detailed scope and acceptance specification for [Phase 5](runtime-evolution-plan.md#phase-5-stabilize-runtime-boundary-interactions). It applies the [systematic audit](prompts/audit.md) to the implemented runtime. The [data contract](data-limitations.md) and [AGENTS.md](../AGENTS.md) remain the semantic authorities; this document does not add runtime behavior.

## Purpose and scope

Find and fix defects in **all Phase 4/4A functionality and the shared mechanisms it relies on**, including unchanged code. Phase 4's implementation milestone is not an exemption from further review. A newly discovered Phase 4 regression belongs here just as much as an older publication, Array or lifetime defect. Determine when a defect was introduced only when a baseline comparison supports that conclusion; its origin does not determine whether to fix it.

The deliverable is a reviewed, corrected implementation with retained regression coverage and evidence for the scoped invariants. It is not another feature cutover or a claim that passing tests prove absence of bugs. Existing mechanisms and contracts can be challenged, but a proposed contract change needs its observable before/after behavior and the ordinary architecture decision; changing an oracle to match a failure is not a fix.

Current kernel entry, ordinary native observations, capture and publication are in scope. New Promise-valued path APIs, coordinated multi-reference compiler entry, compiler migration, deterministic collected-poison ordering and the future iterator specification keep their existing roadmap scope. These deferrals cannot excuse a failure through an already supported route. In particular, test existing entry/export ordering and distinguish a newly introduced kernel dependency cycle from the separate compiler coordination obligation. Physical substitution remains rejected.

The last recorded Phase 4 checkpoint reports 5,178 normal/traced passes and focused lifetime/work evidence. Those results belong to that source snapshot. Phase 5 must establish its own baseline, including the tests, fixtures, loaders and untracked files it actually runs. This specification review reconciled reports and current contracts; it did **not** rerun every historical reproduction or certify the present runtime anew.

### Settled decisions and rejected shortcuts

These are controls on the audit, not new defects to fix:

- First actual import preparation owns source context and derived deduplication/compound reporting; collected-poison order is currently unspecified. First encountered fatal wins immediately. Neither exception permits different values, validation policy, required causal failures or effects.
- Only explicit mutation has application-visible mutation authority. Pure reflection may follow availability; live native reads still respect writes. Do not restore the removed inspection queues, copies or waiting leases solely to enforce pure-hook order.
- Prepared results preserve producers; native mutation still validates its complete working receiver. Ordinary import cannot substitute for native finalization: a poison overlay does not make an actual callable native `then` safe.
- Import preserves healthy surroundings; export aggregates required poison. Fresh and prepared inert capability references gain no authority; capability use/export and exact-receiver restrictions retain their own boundaries. Do not restore obsolete fresh-result revalidation tests under old Error kinds.
- Receiver publication, result admission, source access, output disposal and complete poison collection have different completion points. A universal completion event, blanket preparation queue or earlier release is not a simplification unless all those obligations remain satisfied.
- Weak exact-receiver membership solves diagnostic-only retention; it does not replace strong protection for pending native access/publication. Hiding or formatting stacks, allowing spent runtime captures to leak, deep equality as identity, physical substitution, snapshot projection chains and a second lifetime framework are not selected fixes.
- Earlier suggestions that a surviving cleanup mutant proves dead code, or that every prepared container must have zero incoming placements before initialization, were not valid general proofs. Re-establish supported reachability, full state transfer and resource ownership before removing a guard.
- The proposed import-session object, generic classification wrapper, universal completion boundary and removal of the intermediate mutable snapshot were [evaluated without a retained improvement](phase4-review.md#independent-third-pass-reconciliation-2026-10-21). They are not unfinished deliverables. Revisit only with a concrete improvement over the current implementation, preserving the separate policy, collection, native-access and output lifetimes; shorter signatures alone are insufficient.

## Resource and work checks

For each relevant boundary, state who needs each resource and its actual last read/publication. Cover:

- Chain/root holders, lazy path locations, source containers, captured versions, recovery baselines and writer destinations;
- receiver shells, exported arguments/comparator inputs, successful but discarded payloads, Functions, healthy Errors and callback closures;
- prototypes, constructors, staged admission/inspection maps, failed-preparation records and native `Array.map`/constructor CallSite receivers;
- external resources, selected routes/tree nodes, reservations, weak binding/conflict records and live registry siblings;
- operation owners, gates, fulfilled intermediate Promises, exact-receiver policies, identity queries, cells/domains and completed-history records.

Test release before unrelated pending work completes, then complete that work finitely to verify no required use was lost. Keep positive controls for unread inputs, direct pending native work, surviving holders, recovery and successful outputs. Shared settlement remains independent of a closed consumer. Use unformatted fresh/prebuilt causes at stack limits 10, 50 and 1,000 where stack retention is relevant, including existing fixtures rather than only new probes. Distinguish retained exact host CallSite receivers from removable runtime captures; inspect a strong path when GC evidence is ambiguous, and do not treat WeakMap ephemeron edges alone as proof.

Measure work on large explicit inputs and long histories around small graphs separately. Include copies, inspections, subscriptions, parent/index work, forwarding/comparison work and retained records. Successful source collection does not prove completed metadata is collectible. A lower line count or Promise count does not establish a simpler implementation; account for state, callers, repeated scans, allocation and lifetime obligations.

## Test-evidence requirements

Past clean reviews missed defects partly because the evidence did not execute the claimed condition. Phase 5 must enforce the following before counting a run:

1. Pin production sources **and test/tool inputs**; label scratch prototypes, faulted runs, reviewer-reported results and current executed results separately. Build the final implementation with superseded paths removed; a loader bypass is not cutover acceptance. Verify hashes when reusing partition results after edits.
2. Check child/VM execution explicitly. Forward or explicitly supply required loaders to every relevant runtime worker; validate substitutions/hits with mandatory anchors/receipts and a failing no-op-loader control where substitution is used. Normalize file URLs, including Windows drive-letter case. Parent loading is not evidence of child loading. Tracer/fault hooks must compose without silently skipping bodies.
3. Keep transformed-source coverage separate or accurately mapped. Same URL/length is not a source map. An unexecuted branch needs a producer/caller investigation; do not fabricate malformed integration controls to hit it or declare it removable from zero hits alone.
4. Migrate obsolete assertions individually and execute the remainder of each test. Preserve topology, isolation, causes, ordering and recovery assertions. Tests stopped before delivery, untracked/unlaunched fixtures and stale safeguard anchors are gaps. Verify the final commit candidate includes every required file.
5. Generate programs and random inputs before replay; use equivalent input ownership and immediate managed handoff in all runs. Keep operation contexts distinct where attribution is tested. Do not let a later import repair missing admission, settle all inputs before purported pending reuse, or let observation instrumentation retain/index data invisibly. Pair observed/verified runs with bare semantic controls.
6. Compare the dimensions a generator actually models. Normalized poison markers in the publication model do not prove cause membership/source/kind; kind-only equality does not prove values, aliases or effects. Apply the narrow import/reporting exceptions explicitly, alongside separate checks that no causal failure vanished. All-ready native comparison supplements, rather than replaces, the written contract and identity oracle.
7. Use representative safeguard faults to falsify each distinct changed enforcement/release obligation. A fault must cause the intended assertion to fail; startup errors and timeouts are not detections. After one leak is fixed, retest for masking paths. Surviving mutants require explanation, stronger coverage or a supported removal argument, not automatic deletion or a new production guard.
8. Use process deadlines with startup margin for hangs/GC and external process limits for microtask starvation. Assert ready completion directly where the contract promises it, then release test gates. A required never-settling Promise is permitted; an unnecessary wait or introduced dependency cycle is a defect. An overloaded test timeout needs an isolated rerun and cannot count as either a semantic failure or a pass.

## Execution stages and acceptance

1. **Baseline and reconciliation.** Create `docs/phase5-review.md` when execution begins, with the exact candidate, B01-B21 dispositions, route/resource inventories and gaps. Reconcile all supplied findings, including subsequent reviews, against the current contract. State unsupported cases or superseded obligations precisely; do not silently inherit a historical "no issues" verdict.
2. **Targeted audit.** Trace the matrix, first exercise the mandatory intersections and earlier reproductions, then explore short conflicting histories and missing routes. Treat the newest snapshot domain/cell implementation as a full Phase 4 audit target, not already proven by its recent suites. Keep concrete independent oracles and actual path/condition receipts.
3. **Fix and simplify.** Reduce each defect, identify its invariant family, fix the authoritative boundary and inspect every sibling caller/producer. For an experiment, record its question, semantic controls, whole-cost success criterion and revert condition before evaluating it. Retain only improvements; remove adapters/obsolete paths in the same change. Stop for a contract/design discussion if the solution is uncertain or materially more complex. An approved future-feature deferral cannot conceal a present-contract defect.
4. **Validate the candidate.** Run the normal and traced suites with strict unhandled rejections and suitable test timeouts; explicitly run affected subprocess fixtures with their required instrumentation. Run the complete safeguard registry against a clean matching baseline, distinguishing witnessed faults from mere anchor matches. At closure run the applicable 400-seed preparation/lifecycle, placement, Array, nested, external, boundary and genuinely pending histories, plus the complete conflict and publication-pair partitions described in [the test guide](../test/README.md#scaling-generated-runs). Check independent membership/identity diagnostics in addition to normalized differentials. Run the lifetime/work cases above and required positive controls. Earlier manifest results do not certify later fixes; re-run changed obligations, and justify any reuse of unaffected expensive evidence explicitly.
5. **Final review and close.** Review the stabilized candidate against the full scoped matrix, including assumptions and cleanup introduced by fixes. No known actionable present-contract defect or unexplained required evidence gap may remain. A new finding reopens its family and affected acceptance gates, even when it is a direct Phase 4 bug. Closure records the final source/test snapshot, commands, results, addressed findings, contract decisions, exclusions and residual confidence limits. Update current docs and remove obsolete execution scaffolding; preserve useful regression tests and historical evidence.

Stages 1-5 are pending. The initial 5,178-test checkpoint does not satisfy them. No fixed number of clean passes or promise of exhaustive correctness is required: completion means the defined obligations have current evidence, known defects are fixed, and the final scoped review identifies no further actionable issue. A new known defect cannot be moved to another phase merely to meet that criterion.
