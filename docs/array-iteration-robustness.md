# Array iteration simplification, robustness and repair history

[Source growth and rewrite decision](#source-growth-and-rewrite-decision) · [Implementation plan](#implementation-plan) · [Work for all 78 repair families](#follow-up-work-for-every-scored-family) · [Scored repair history](#scored-runtime-inventory)

**I would keep iteration and put a smaller partial-Array implementation to the test.** A valid one-slot program exposed the wrong value after a failed splice. Two cursors on the same ordinary Array once killed the execution. Those defects and the measured source growth justify comparing a focused consolidation with a fresh design for the same operations. Both must preserve the language's behavior while an input remains pending.

## What has actually been going wrong?

The ledger below groups the retained review findings into **78 runtime repair families**. I assigned one primary consequence to each family so the counts can be read together.

| Primary consequence | Families | What counted |
| --- | ---: | --- |
| Wrong result or effect | 25 | Incorrect data, presence, identity, Error or scope, host action or data visible after repair |
| Required progress lost | 15 | An answer, effect or independent branch could wait forever after its decisive facts were known |
| Fatal on a supported program | 5 | A valid resume, second cursor or deep command history could kill the execution |
| Excess work or allocation | 22 | The result was correct, but the implementation repeated avoidable work. Severe cases exhausted resources |
| Excess lifetime | 11 | A completed or narrowed consumer kept values, regions, gates or contexts alive while another input stayed open |

That gives **45 behavioral, progress or fatal families and 33 work or lifetime families** under this grouping. One independent check on the classification is the November 25 19-sweep review. Of its 14 named runtime reports, six were R1, W1, S1, S4, D1 and D2, covering crashes, a hang or wrong language behavior. The other eight were S2, S3, S5, S5b, S6, S7, S8 and L1, covering work or lifetime. The reviews selected deliberately difficult programs, and grouping several symptoms under one fix changes the totals. Neither ratio estimates how often an application will hit a bug. [19-sweep reconciliation][independent]

Numeric extremes explain some findings. Examples include preserving the original cause when moving an already lost slot, capping a diagnostic collection, and precise virtual indexing. The cutoff permits a simple shared Error. It does not justify growing a per-position diagnostic structure. By contrast, the hidden-child read needed one slot, a flagged hole changed sorting and flattening in two slots, and an ordinary three-item capture sufficed to strand a determined prefix. A long **command history over a small Array** is also a different dimension from a huge Array. [Array contract][contract] · [Point and range reproductions][follow]

There is evidence against abandoning the feature and against trusting one more clean pass. The ordinary Array and the optimized one can share a sequential meaning. One cut now supplies both parts of a splice, exact width readers share their producer, and placement versions preserve historical data through writes. In the other direction, a frozen review found no further issues on a snapshot where a later reviewer reproduced four issues in argument demand and lifetime. The coverage had stopped producing new distinctions. The reviews suggest that an LLM can implement the smaller mechanisms and also miss interactions shared by its implementation and its tests. Establishing a real-world defect rate would require independently evaluated usage evidence. It does show where to spend a human reviewer's attention. ## Where the design can buy more correctness

Three mechanisms elsewhere in this kernel illustrate the standard to aim for.

| Existing mechanism | The invariant enforced in code | Application to iteration |
| --- | --- | --- |
| Captured property version and placement gate | Install the destination transition before suspension. Readers keep the version they selected. Completion commits presence, status and baseline and releases the writer. Proof of obstruction may precede delivery of its exact cause. | Every access to a captured Array must pass its applicable scope gates. Once admitted, point access should project one selected placement. This fixes both early exposure and waiting for the wrong thing. [Placement implementation](../src/property-versions.js) |
| Operation owner and release at last use | One open fact, an idempotent close and removable release actions bound private observation work. Shared settlement continues for other readers. | Close a cursor's unread traversal independently of a pull it already issued. Give a count reader a numeric receipt and a point reader only its possible holders. [Owner implementation](../src/operation-lifecycle.js) · [Cursor implementation](../src/iterate.js) |
| Incremental parent placements and retirement | Maintain forward and reverse relationships at publication. At a graph transition, work from affected candidates and genuine live roots. The independent ownership model can check what should survive. | Derive candidate retention from the selected source ranges. Acquire surviving protection before releasing obsolete ranges. Test an orphan cycle and the same cycle with a genuine observer. [Parent placements](../src/parent-placements.js) · [Retirement](../src/ownership.js) · [Ownership model](../test/experiments/phase2-ownership-model.mjs) |

**The weakness is repeated interpretation of one fact.** A splice can identify its retained prefix while a bounded slice, point lookup, Error query, Unordered occurrence search and ownership calculation each decide independently what that proves. A correction in one reader then leaves a plausible wrong answer in another. The strongest existing Array code already shares the cut between prefix and suffix and transfers retained operands together. The largest remaining opportunity is to make the *meaning* of that cut authoritative across readers. The technical analysis already asks for this division between method semantics and storage. [Dependency rules](array-iteration-technical-analysis.md#2-keep-the-evaluator-separate-from-storage) · [Splice selection](../src/array-splice.js) · [Selected operand lifetimes](../src/array-sequence-layout.js)

Concretely, a captured splice has a predecessor version, normalized start and count, insertion occurrences, producing mode, and selected failure scope. From those facts its rules answer a short list of questions about whether a point exists, which predecessor placements or insertion can supply it, which range survives, which occurrence is guaranteed, and whether failure is certain. Each answer identifies the remaining prerequisite if one exists. A point reader consumes a selected placement, a length reader consumes bounds, and a Boolean observer can consume certainty while an exact-cause observer waits. The same possible sources determine what a reader must protect. This is a specification of the existing questions. A production implementation can compute only the projection requested. [Closed fact and query vocabulary](array-method-specification.md#2-closed-fact-and-query-vocabulary) · [Current sequence selection](../src/array-sequence.js) · [Occurrence traversal](../src/array-occurrences.js)

There is a real limit to consolidation. Ordered traversal owes the first obstructed position. Unordered traversal owes exactly-once eligible occurrences, bounded credit and terminal reporting. A directional search owes a qualifying first or last index. Storage may borrow a fixed prefix while another route constructs a private dense backing. Those operations can share a fact and have different completion conditions. An earlier experiment forcing one execution route lost **13 progress checks and 9 work or lifetime checks**. Another forced remap path lost a required `fill!` failure. Carry those witnesses into any proposed deletion. [Simplification trials](../simplifications.md#claude-review-follow-up-2026-11-24)

Consider one concrete boundary. Capture `[A,B,C]`, issue `splice!(start,count,Y)`, and export the first two successor slots. With both controls held, start could be zero, so publishing `[A,B]` would be wrong. Once start is two, any regional deletion or regional failure starts at position two. Both streaming modes owe `[A,B]` now. In Complete mode a count failure could still invalidate the whole capture, so the successor export waits. In every mode the older snapshot still yields `[A,B,C]`. A single cut and its enclosing validity gate explain all four observations. Issuing an extra lookup must not change them. [Range progress regression][follow]

Three scores point to different engineering decisions.

| Existing repair | Now → potential | Decision |
| --- | --- | --- |
| Iterative traversal of command history | 5 → 10 | Forwarding `selectPoint` fixed the reported tail overflow. Later valid histories still overflowed while assembling or trimming. Require iterative history edges in all three phases before declaring the family closed. [History fixtures][depth] |
| Capturing the selected placement before `at(0)` returns | 6 → 10 | The one-slot regression is fixed. Make new point consumers reuse the same selected placement, with independent expectations for status, value and repair. [Point regression][follow] |
| Shared pending splice cut and retained operands | 9 → 9 | Keep this abstraction. One decision already supplies both ranges without making length or rank depend on materializing them. Apply the same ownership test to its consumers. [Memory review][memory] |

## Source growth and rewrite decision

**Make a smaller implementation an explicit objective of the architecture work.** I would compare a fresh partial-Array selector, built in an isolated copy of the current kernel, with a consolidation of the existing selector. Both designs owe the same public behavior and work bounds.

| Source snapshot | All runtime JS | Array modules and cursor | Remaining runtime JS |
| --- | ---: | ---: | ---: |
| Before the iteration planning series, `5f94887` | 9,727 | 2,083 | 7,644 |
| Immediately before implementation, `6cb27fc` | 10,216 | 2,585 | 7,631 |
| Implementation commit, `fe6bfee` | 16,323 | 7,966 | 8,357 |
| Staged snapshot measured November 28, 2026, `src` tree `d4f5805e887b` | 18,128 | 9,557 | 8,571 |

The counts include comments and blank lines in production JavaScript under `src/`. The Array column covers `src/array-*.js` and `src/iterate.js`, including methods that predate iteration. From the immediate baseline the runtime grew **7,912 lines (77.4%)**. The Array column accounts for **6,972 (88.1%)** of them. The implementation commit added 6,107 net lines and subsequent changes added 1,805. From the earlier planning baseline the increase was 86.4%, including other kernel work. With the rest of the runtime held at 8,571 lines, returning Array code to a one-quarter share would take a reduction of 6,700 lines. The achievable reduction needs to be measured on equivalent implementations.

### What is worth rewriting

The cursor is 327 lines. Seven new modules for sequences, layout assembly, fixed layouts, regions, widths, occurrences and insertion ranks total **3,949 lines**, nearly half the net growth. A pending splice shows where to look. `spliceSides` selects the old prefix and suffix, `splicePointInputs` calculates which slots a point might still need, and `takeSequence` / `trimmedSequence` descend through selected children for a restricted read. Each answers a different question about the same coordinates. At dispatch, `array-methods.js` imports the flat-stream, interval, layout-method, search and splice modules, and all five import it back. A replacement should show which decisions and dependencies disappear. [Splice](../src/array-splice.js) · [Sequence projections](../src/array-sequence.js) · [Method dispatch](../src/array-methods.js)

One successful simplification removed the separate insertion scheduler and retry list by sharing occurrence traversal. The distinction it preserved makes a good design test. On an Unordered `["A","B"].toSpliced(p,0,"X")`, unrestricted `includes("X")` is already true while `at(0)` must wait. On the measured snapshot I checked three outcomes for p. At start 0, start 2 and a failed start, the final first item was respectively X, A and A. A replacement that waits for the whole layout would lose the early search result. [Earlier simplification trials](../simplifications.md#claude-review-follow-up-2026-11-24) · [Method publication rules](array-method-specification.md#publication-by-method-family)

### Compare a consolidation with a clean replacement

1. **Choose the host.** Preserve the full current snapshot, including the latest kernel changes and tests, as the executable baseline. Replace the selected subsystem outright in a separate copy of that snapshot. The baseline remains available for comparison and rollback. Use `6cb27fc` to study the smaller ready-Array implementation. Since that revision, 26 files outside the Array column have changed. A candidate built on the older checkout must identify and port the relevant placement, ownership, parent-index and Error-handoff changes. Try that older host if a specific dependency in the current core obstructs a clean design, and count the port in its cost. [Placement versions](../src/property-versions.js) · [Ownership](../src/ownership.js) · [Result evidence](../src/error-evidence.js)
2. **Compare the same slice of functionality.** The incremental candidate consolidates repeated cut arithmetic. The fresh candidate starts from captured occurrences, restriction, concatenation and a deferred choice. Test whether one such mapping can supply a point, a bounded range, an occurrence whose index is unknown, and each reader's required source placements. Reuse the kernel's gates, placement versions and ownership primitives. Run both candidates through `splice!`, `toSpliced`, lookup, slice, bounded iteration, a later write and repair. Extend the promising design to `fill` / `copyWithin` to test it on an independent producer with different write rules. [Selection and storage](array-iteration-technical-analysis.md#2-keep-the-evaluator-separate-from-storage) · [Pilot witnesses](#implementation-plan)
3. **Measure what can actually be removed.** For each candidate list the old functions whose last caller disappears, new production lines including adapters and shared-core changes, independently maintained decisions, and the state and release paths a maintainer must follow. Verify that each tested operation reaches the candidate. An old engine still serving a fallback remains in its cost. Use the independent reference for results, intermediate progress and effects. Compare production work, last-use release and depth on the same histories. When an internal test hook disappears, measure the equivalent work on the new path and show that its fault is still detected. [Public splice cases](../test/array-partial-splice.test.js) · [Interval cases](../test/array-interval.test.js) · [Verification requirements](../test/README.md#extending-the-tools)
4. **Choose how far to go.** Adopt the fresh design if it gives a material net reduction at equal functionality, removes an independent decision or lifetime mechanism, and keeps that advantage in the second family. Prefer consolidation if it gives comparable savings with fewer dependencies to replace. If neither wins, keep the current implementation and record the smallest case that required the extra mechanism. Expand a winning rewrite by complete families, preserving composition of earlier captures, new operations and later consumers. Delete the superseded production path at each cutover. A full Array rewrite needs a credible deletion plan for the remaining families and the full contract, work and lifetime suites before final cutover. Any proposed change to language behavior or required progress is a separate decision for the owner.

### Production requirements for both candidates

For a healthy, representable splice, let P be the captured predecessor of length n, s the normalized start and d the clipped delete count. The successor's occurrences are the concatenation of `P[0,s)`, the insertions and `P[s+d,n)`. The removed result of `splice!` selects `P[s,s+d)`. A point selects one occurrence of that mapping. A slice restricts it. Restricting it twice cannot bring an excluded occurrence back. This calculation provides a common reference for selection and ownership. The method still controls densification, direct-result identity and prescribed writes, and its producing mode supplies the specified failure outcome. Derive ready answers directly and give any stored pending fact a reader or publication that needs it. [Method families](array-method-specification.md#5-endpoint-and-copying-families)

For the consolidation, trace `spliceSides` and `SpliceRanges.read` into whole-range assembly, `splicePointInputs` into a retained point, and `restrictChoice` into a bounded slice. Prefix and suffix already share one cut. Identify where the same start, count or source-bound fact is interpreted twice, who can refine it, what each reader may publish, and what data it can release. For the fresh design, show how a single captured mapping answers those same questions. Keep the selected placement’s value, presence, status and identity until the reader applies its own projection. A range calculation can stay compact and a count-only reader can stay free of payload references. Keep an existing producer when its callers already share the decision and the alternative buys no reduction. [Splice producers](../src/array-splice.js) · [Sequence projections](../src/array-sequence.js) · [Selected operands](../src/array-sequence-layout.js) · [Placement projection](../src/property-versions.js)

Start with lookup, `at` and bounded slice. Then use a bounded Unordered pull as the independent consumer. It may know an occurrence belongs in the window before knowing its exact index. Keep that distinction and the cursor's own skip, credit and terminal rules. Exercise both `splice!` with its removed-elements result and `toSpliced` with its dense copy. Keep direct result, successor, scope validity and issued effects independently observable. Review the soundness argument in four steps. A ready cut selects the specified occurrences. Each refinement removes only impossible sources. A published fact survives every permitted continuation. The existing gate orders earlier conflicting effects. Supply a named progress witness for each early answer. [Cursor integration](integration.md) · [Selection and failure rules](array-method-specification.md#2-closed-fact-and-query-vocabulary)

Close the pilot when the reference and public-path checks agree, the faults above fail their intended assertions, possible children survive and excluded children collect, and the second consumer can use the producer's facts without another cut calculation. Also check forward, reverse and interleaved deep histories on each touched path. If the next consumer needs a materially different fact, identify it with two programs that have the same existing facts and require different answers. That distinction determines whether to keep a specialized projection or change the shared boundary. [History-depth fixture](../test/fixtures/array-history-depth.mjs)

### Acceptance, scoring and stopping

One reviewable change should carry the invariant and its code owner, the before/after decisions and consumers, the first checkpoint that distinguishes a broken variant, the measured work or lifetime where relevant, and the remaining coverage boundary. Keep this in the existing change description, tests and inventory. Run focused tests while developing. For an integrated shared-transition change, apply the repository's merge checks, including the full normal and applicable instrumented suites, scaled generated histories, publication and conflict coverage, and ownership, depth or lifetime fixtures relevant to the change. Report actual seeds, shards and failure receipts. A failed ownership, progress or effects control is grounds to revise or revert that candidate change as a unit. [Verification and scale](../test/README.md#scaling-generated-runs) · [Publication checks](../test/README.md#publication-identity-checks)

Reassess the score only when this evidence exists. Preserve the dated starting score. Record the achieved score and the specific supported routes covered. A claimed simplification should identify which decision or retained reference disappeared, or demonstrate that the existing owner already covers the family. A 10 needs a construction argument that every supported path obtains the fact from its authoritative owner, plus tests that would catch bypassing it. A fix already at its potential can close on retained controls alone. Stop a family when its scoped model, public acceptance cases, decisive faults, release/work checks and independent review pass on the same final snapshot with no outstanding actionable finding. Reopen on a counterexample, changed contract or affected implementation boundary. Bring a language choice to the owner only if two observable outcomes remain compatible with the core contracts, or if a proposed simplification explicitly requires changing one. Give the smallest distinguishing program and the cost of each choice.

## Scored runtime inventory

**Now** rates the scope of the implemented prevention. A 1–3 is a correction tied to a single route or symptom. A 4–6 closes a real path while adjacent paths still require independent care. A 7–8 establishes a shared rule with identifiable gaps in coverage or an important caller obligation. A 9 places the fact at its natural owner and has evidence from distinct callers or adverse controls. A 10 would make the same failure impossible through every supported construction and demonstrate that property across the public paths. **Potential** rates the strongest proportionate solution available under the existing contracts. A 10 is a credible target for that particular invariant. Some specialized algorithms are already as shared as they should be. The numbers are judgments about breadth of prevention, independent of severity, confidence and test volume.

Each row groups reports that ask for the same correction, gives the observable witness or cost, and identifies how to realize or retain its potential. Categories record the primary consequence. A resource failure can also terminate an execution. Historical measurements belong to their cited revisions.

## Planning and verification corrections

These tables keep earlier specification defects and faulty tests visible without counting them as observed failures of a released or working kernel. For P rows the ratings apply to the adopted rule and how thoroughly its integration can enforce it. For V rows they apply to the strength of the test mechanism.

### Language and integration rules

| # | Identified ambiguity and adopted correction | Now | Potential |

| P1 | Each producer's mode and captured version determine its fallback. Receiving mode controls its own traversal. Temporary holders inherit the language-specified mode. ## Verification for this retrospective

I ran **23 existing public-kernel regressions** selected for the distinctions in this analysis. They covered independent cursors, a trimmed bounded window, an irrelevant splice count followed by a parent push, delivered bounds, certain versus conditional deep Error, failure through a fresh Chain, whole-Array gating and observations around splice, repair and mode handoff. All passed. [Cursor cases][iter] · [Input demand][demand] · [Interaction regressions](../test/array-interaction-audit.test.js) · [Capacity regressions][capacity]

I also ran two independent scratch checks against the current public API. In **108 cases**, six sparse and dense inputs to `[].concat(P).slice(3)` crossed all three Chain modes, ready/synchronous/deferred P, and presence or absence of an extra point observer. Both exports, sparse presence, sorted results and comparator call counts agreed with native Arrays. In **12 more programs**, `splice!` and `toSpliced` on `[A,B,C]` crossed the three modes and the optional point observer. With both controls held the prefix export waited. After `start=2` the two streaming modes delivered `[A,B]` while count remained held. Complete still waited. The old snapshot stayed intact, and after count became one every successor matched the native result. The full 7,109-test runs, 5,000-command depth workloads and larger checkpoint campaigns belong to the earlier implementation verification. The fresh checks here cover these specific witnesses. [Previous full verification][follow]

The next compiler still has to demonstrate mode inheritance and expression holder elision, managed versus native iterator dispatch and finalization, body ordering across Chains, bounded pacing, loop-failure and `else` targets, and nested `break` and `return` lowering. The standalone expression handoff is already testable and row 5 covers its repaired failure. I found no new language decision to put to the owner in this retrospective.
