## New finding: cached query reception could leave a stale counter index

**Observed failure.** Two queries select the same observation-only external property whose managed data contains a pending child. The first query captures placements and lets its unheld source retire. Cached reception by the second query returns the prepared but inactive root. Query indexing then creates counters on that inactive root without restoring its maintained parent relationships. A delivered child is retained through its captured version and later retires independently, clearing its own counters. The root's surviving counter index falsely certifies that child as indexed. A later `getErrors` reaches `getRequiredRefCounter` and fails the execution with `Ref counts require a ref-indexed value`.

The minimal supported history needs neither a Proxy nor poison:

1. Create an observation-only external service exposing `{ data: { reveal: pending } }`.
2. Issue `getErrors(service, ["data"])` and `hasError(service, ["data"])` before settlement.
3. Deliver `{ child: anotherPending }`, then deliver its scalar child and await both query results.
4. Query `data` again. The correct healthy outcomes remain `null` and `false`.

The finding originally appeared in a richer B13+B14+B15 history: healthy native Error data, two poison leaves with the same cause but `-0` and `+0` source contexts, a pending external-property query, recoverable query reflection failure, then another complete query. Both native and ordered delivery failed on the candidate. Removing the reflection failure and poison reduced it to a receiving/retirement defect, also relevant to B19. It was not an authorized exception in Error reporting or a required never-settling dependency.

**Correction.** `receiveValue` now calls the existing `activateRelationships` after preparation/admission and before handing the value to its consumer. This restores only the inactive region from maintained forward state, stopping at active descendants. It performs no admission, reflection, subscription or counter rebuild. Normal retirement at the end of the graph transition now removes any optional index built by a consumer that did not retain the root. There is no additional operation state or retained lease. `buildRefIndex` remains an indexing operation and does not implicitly receive or retain data.

The change is at common reception because queries are not the only consumer permitted to inspect a prepared value without installing a new holder. Moving it into query traversal would leave the receiving invariant dependent on consumer-specific behavior. Existing preparation, placement, capture and lifetime mechanisms still determine when a value remains live.

**Retained evidence.** [phase5-boundary-intersections.test.js](../test/phase5-boundary-intersections.test.js) contains reduced cases for both query orders, native/ordered delivery, healthy/rejected nested data, and record/Array representations. `verifyLiveness` proves actual source retirement; repeated final queries check correct counter reuse and rebuilding through supported APIs. The original richer query cases remain. The `receiving-restores-retired-topology` safeguard removes this exact restoration and requires the reduced witness to fail. Initial investigation observed the supported fatal directly, before adding invariant checks or the fix.
