## Receiving and invocation trace

The sequential reference behavior is determined by the selected value's category. A Function is data except in a supported executable position; Number, Boolean, BigInt, Symbol, null and undefined have no methods or property writes. String properties and method dispatch retain their specified language behavior. An external ancestor does not turn a selected Function into an external receiver or give a scalar native properties. Declared/default External identities retain native property and method semantics under their authority and ordering.

Receiving must establish preparation before ownership can depend on the graph, preserve an existing producer, and distinguish admission from readiness and publication. The reviewed inward routes are public import and method-result import, observation-only property import, argument preparation, placement value publication, ordinary assignment, outward-only assignment preparation and entry result reception. They use `receiveValue`; `importReadyMethodResult` deliberately calls the same `prepareInput` machinery directly because native completion already supplied a ready value and needs this segment's diagnostics separately. Its output is retained by invocation work before publication. Mutable external reads instead use ready-only `captureExternalValue`, then the common assembler; mutable raw source storage is not admitted in place.

The relevant common state transitions are:

- `prepareInput`: classify/stage available fresh identities, capture each immediate shape and placement before descent, reuse failed inspections within the preparation, install pending obligations, then commit admissions/topology. `PlacementConstruction` retains the published destination authority; the preparation clears its temporary maps. Prepared references stop traversal and keep their producer/context/policy. `receiveValue` restores retired relationships before its consumer, within the receiving graph transition.
- `ManagedCapture`: capture generation, shape and exact placement versions, visiting every physical representation while grouping logical identities. Source values are dropped after available capture. Complete data/Error capture precedes method selection; only successful selection resolves identity partitions and allocates canonical native output. Discard clears success-only records without ending required Error collection.
- Managed invocation: receiver and argument captures are separate graphs; observation copies inherit captured identity while mutation copies receive new identity. `validateReceiver` stages fresh admissions and parent entries and commits only after complete successful validation. New stored native identities gain imported protection. Native completion, receiver publication and independent result admission have separate outcomes.
- External invocation: `PathOperation` reserves the statically selected external coverage before managed path waits; `ExternalEffect` captures predecessor work before publishing membership. Receiver-path selection occurs at that ordered turn; post-argument access rechecks authority. Ready-only snapshot capture completes source access before managed alias resolution. Exact native receivers retain ordering through their direct result. Independent nested result data retains its own import obligations and no longer extends native access.

The bypass inventory includes controlled Array construction/remaps, native receiver shells admitted during canonical assembly, fresh stored values found during receiver adoption, and snapshot copies. These do not acquire preparation merely from metadata existence: each must establish placements through its corresponding construction/adoption transition. Function/ordinary Error leaves stay exact and are not traversed as managed containers.

## Shared delivery and bounded work

Two earlier explicit implementation decisions remain relevant. On 2026-10-22 the user approved shared Array backing producers; on 2026-10-25 the user approved shared captured delivery. Both preserve the semantic contracts. These are completed decisions, not pending proposals or permission to share mutable placement authority.

Shared backing producers replace the per-successor pending overlay/subscription chain for bounds-only Array derivations. Physical backing, owner bounds/overlays, logical parents and optional indexed consumers remain separate. Counters must cover issuance, partial/final settlement, rejection/repair, maintained stores and required retained owners; an owner scan at settlement would move rather than remove excess work.

Shared captured delivery separates pending readiness from each placement's mutable authority. Copies reuse the captured delivery while reads/writes keep their program positions. Writes split authority; captured transitions and recovery stay tied to the selected version. Simply retaining a shared pointer to a version later modified by a pending writer is insufficient. The copied-delivery/recovery suites and deep-history probes retain these obligations.

Point fill/copyWithin captures only the selected range when storage is exclusive and writable. The complete pre-call baseline survives in a view with changed-range overlays; its lease transfers before the first write. Overlapping sources are captured before destinations change. Protected, imported, constrained or overlaid storage uses ordinary materialization. Effective in-place writes still publish a new logical identity, including equal-value/self-copy writes; empty ranges forward identity. Recovery uses the preserved baseline, never an undo log.

End extension refuses reuse when a discarded prefix exceeds the live range and uses ordinary materialization during actual growth. This bounds moving-queue storage without compacting retired host storage. Deterministic work counters, retained-view controls and actual collection matter; old heap samples and timing measurements are not work-bound acceptance thresholds.
