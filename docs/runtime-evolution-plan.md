## Implementation and verification

Use [AGENTS.md](../AGENTS.md) and the [data contract](data-limitations.md) as the existing semantic foundation. Any explicit target revision in this plan must update the runtime contract and independent test oracle when implemented. Keep representation choices local and reuse existing publication, ownership, and operation-lifetime mechanisms.

Implement in dependency order. Phases 3 and 4 are acceptance milestones, not a barrier between identity producers and their consumers: integrate complete producer-to-consumer cases across them. For each milestone, reproduce the affected public behavior, extend the relevant sequence/conflict models and storage/refcount verifiers, run the required checks and larger configurations in the [test guide](../test/README.md), and remove superseded mechanisms in the same change. A standalone model with supplied identity answers is not evidence that runtime classification, publication, or retention is correct. Measure allocation and pending-work costs before adding caches or alternative execution paths. ## Phase 1: Preserve incoming parent relationships

**Status: implemented.** Complete incoming relationships and common input preparation now publish through the shared placement/construction boundaries, independently of Promise/Error counters. Phase 1 retained the existing sharing protection during migration; Phase 2 below subsequently replaced it with bounded delivery and maintained ownership, including retirement and cycle cleanup. Section 8 records the implementation and integrated verification.

### 1. Principles and required result

A child cannot discover its outside parents by traversing its own descendants. Record each managed edge when it becomes part of the published graph, while its parent, key, and value are already known. Do not build refcounts, scan unrelated owners, or preserve source coordinates across later reads to reconstruct a missed parent.

A relationship identifies a current logical `(parent, key)` placement whose value is a managed container. It follows property versions and Array projections, not merely physical JavaScript properties. Relationships may be stored directly or represented through an Array backing record that enumerates the actual placements. Completeness concerns those logical placements, not the number of stored records. A Chain's existing `chain._state.value` is an ordinary root-holder placement; phase 1 records it even before counter indexing. No additional synthetic parent is needed for the root value. Detached historical versions, recovery captures, host variables, and exported objects are not additional current parent placements; their existing retention rules continue to apply. An empty logical parent set rules out attachment to a Chain, but does not prove absence of these other retained uses.

The required result is:

- Every current managed incoming placement in the published graph is represented, including the first placement of a uniquely held node, repeated references within one parent, and cycles.
- Attachment, replacement, removal, and shared settlement maintain that invariant at their logical publication boundaries. Lookup and refcount indexing consume established facts; neither repairs or initializes parent relationships.
- Private construction stages its new relationships until the graph is ready for managed publication or use. Import and native adoption supply those facts through their required walks; an isolated native mutation receiver stays private until native work finishes and its final topology is adopted. Maintenance of an existing source or shared backing remains immediate, even while a new destination is being constructed.
- Parent tracking neither implies nor initializes the counter index. Its correctness is independent of `shared`, leases, and whether an Error query has run.

This is a requirement on graph producers and publication, not an inference from `shared === false`. Recording an edge when it is first known is the minimal reliable source of a reverse relationship: it cannot generally be derived from the child later. Refcount summaries can still wait until needed. The extra collections for uniquely held children are an accepted cost of removing deferred first-parent tracking; measure that cost before considering another representation.

### 2. Minimal representation

Keep the complete incoming occurrences in one optional execution-local metadata field, using a compact first entry:

```js
incomingParents: undefined | { source, key } | Map<source, Set<key>>
```

An absent field means no recorded incoming sources; there is no uninitialized published incoming state. The first occurrence stores its exact source and key. Repeating that pair is idempotent; a second distinct occurrence promotes it to Map/Set, including when the source is the same but the key differs. Removal deletes only the specified pair and drops empty source sets; removal of the final occurrence clears the field. Initially, a promoted map stays a map until empty, avoiding allocation churn on repeated one-to-two transitions. All encoding decisions stay inside the parent helper. No consumer sees the pair or needs a second bookkeeping path.

An unattached root needs no entry merely for being a root, although internal edges back to it must be recorded. A stored Array backing occurrence may currently expand to no logical placements because all owners mask or exclude it. Keep current property versions on their owning containers; the reverse index needs no duplicate version, mutation counter, original pointer, or operation history. Section 4.3 defines a separate outgoing-placement completion fact so classification is not mistaken for completed input preparation. This phase uses ordinary strong parent references; section 6 identifies the phase 2 retirement dependency.

For ordinary placements, `source` is the logical parent and the key is its normalized string key. For shared Array storage, it is an internal backing record and the key is a canonical physical index stored as a Number; section 4 defines expansion into logical parent/index pairs. A backing entry can represent many logical placements, so even a single stored pair does not prove unique ownership. Neither map size nor key-set size is a sharing count. This compact encoding retains the first relationship in full; it does not revive the rejected approach of omitting a default parent and attempting to reconstruct it later. A pair of a node with itself works like any other occurrence.

For multiple occurrences, use `Map` because parents and backing records are object identities. A plain object would require separate identity keys; a `WeakMap` cannot enumerate the parents. Use `Set` for each source's keys because membership is the complete stored fact. A `Map<key, placement>` would duplicate placement state already owned by the parent. A null-prototype object could store string-key membership, but has no constant-time emptiness or size operation without another maintained count. Keeping every occurrence in a flat pair array would require scanning the child's parent fanout for idempotent insertion and removal; promotion preserves expected constant update work as retained parents accumulate.

`[source, key]` is also a lossless first-entry encoding, with the same promotion/removal rules. Prefer `{ source, key }`: it makes the fields explicit and uses less retained heap in the local measurement. With Node 24.14.1, 100,000 entries, preallocated metadata slots and keys, three fresh processes per case and forced GC, incremental retained bytes per entry were approximately 416 for Map/Set, 64 for an Array pair, and 40 for an object pair. Adding an optional field to the tested metadata shape cost another 40 bytes in each case. Two fields placed directly on metadata avoided a pair allocation, but require a wider metadata representation for the promoted case; keep the one-field object pair unless integrated measurements justify that extra encoding. These are representation measurements, not whole-runtime heap or throughput claims. The earlier audit's 32-byte "inline object" result actually measured two metadata fields, with different allocation accounting; it was not a stored `{ source, key }` object.

Retain `meta.parents` as the counter index's maintained acyclic projection: indexed, non-cycle-cut parent multiplicities. It is not the complete incoming index and cannot serve complete ownership queries. The complete index has every source/key occurrence; the counter projection records only dependencies used by Promise/Error propagation and prospective-edge cycle detection. Maintain both through the same prepared transition, without a separate producer protocol. Counter initialization still derives its projection from its required forward walk, and publication keeps both representations consistent.

Repeated derivation has a demonstrated cost: a retained-generation fixture and an Array-owner fixture each have 1,001 complete incoming candidates but only one indexed counter parent. Filtering before key expansion still inspects those sources or owners on every propagation. Keep the existing counter map to preserve dependency-bounded propagation without allocating a grouping map each time. This supersedes the earlier proposal to remove it. The independent verifier must compare it with the complete incoming projection, grouping counter-indexed logical parents (`meta.parents`), not merely placement-initialized parents, and excluding their cycle-cut keys; Array backing records are never counter parents. That comparison detects missing placements without making production queries rely on an unverified derived projection.

Publish a discovered region's counters, counter-parent map, and cut facts together after fallible discovery. During a later edge commit, update complete incoming relationships and the counter projection before propagating deltas, with no callbacks between these steps. Store `incomingParents` in the existing execution-local metadata. Metadata presence already means admission, not counter initialization. Existing counter-initialization checks may continue to use `meta.parents`; neither the complete incoming field nor the container's completion fact initializes counters.

For example, publishing `P.x = C` records `(P, "x")` on `C`. Copying `P` to `Q` adds `(Q, "x")`; the source entry is already present. Replacing `Q.x` removes only that entry from `C`. No lookup, sharing transition, or refcount query is required to discover either parent.

Record relationships only for managed container values: records, logical Arrays, and managed class instances. Primitive values, Functions, Errors, and external identities have no managed child relationships. Pending values acquire the appropriate relationship when their managed value is published; retaining a pending capture does not invent its eventual parent in advance.

### 3. One publication rule for every producer

**Prepare incoming changes with the placement transition and commit them with successful logical publication.** Initial attachment and later replacement use the same rule. Private construction initializes relationships from its completed topology at publication. Physical Array backing facts follow each successful storage write; bounds and overlays determine which logical placements they represent. Failure or abandonment discards only the failing destination's uncommitted facts, not maintenance owed to an existing representation or an earlier completed construction.

| Runtime event | Required behavior |
| --- | --- |
| Initial import, including Promise-delivered imports | Prepare every managed internal edge during the existing staged walk and publish those facts with successful admission. A repeated child skips recursive inspection, not registration of the new parent/key occurrence. |
| Lookup, another retained read, or counter indexing | Use the already complete incoming relationships. Keep ordinary retention and counter work; add no first-parent bootstrap or relationship-repair walk. |
| Assignment or Chain construction | Prepare previously uninitialized Cascada-created containers through the shared input preparation boundary, preserving their unimported ownership. Skip prepared subtrees, then add the destination edge and remove its old managed child's entry on replacement. |
| Call-input retention and controlled Array payload reception | Prepare every fresh managed input consumed or provisionally retained by a call before a receiver wait or selected processing, whether the boundary is native or controlled. Reuse preparation for `push`, `unshift`, `splice`/`toSpliced` insertion, `fill`, `with`, and Array/non-Array `concat` inputs. The argument list supplies no parent; internal properties and published elements supply actual placements. |
| External assignment or host-call export | Receive fresh managed inputs through common preparation before export, including outward-only writes. Preparation records source-container relationships; detached output copies create no managed parent entries. Establish known external ordering claims and capture outward-write inputs at issuance before target or predecessor waits, as specified in section 4.3. |
| Parent COW, Array copying/remapping, or an entered/private Chain | Register the new holder and copied child placements at publication. Existing source edges stay recorded without another source-retention protocol. |
| Managed native receiver/result adoption | Keep the isolated working graph private during native writes. Required finalization/adoption walks prepare its surviving receiver and result edges before their respective publications. |
| External-property snapshot adoption | Prepare copy edges during the existing snapshot walk and publish them with successful managed admission. A snapshot sent directly to native code without admission stays outside the incoming index. |
| Delete, overwrite, truncate, or move | Remove each location that ceases to hold its old value and add the new location if present. Replacing a branch root changes that direct edge, not every descendant's immediate parent. |
| Promise settlement, gate installation, or gate completion | Apply the same logical edge transition, including removal of a ready child replaced by a pending gate. A detached version cannot register its former live parent. Maintain current placement facts before exposing completion to consumers. |

Import covers every newly traversed managed container, not only its top-level root. Importing `{a: x}` records that edge even if host-held `x` is later imported separately without a lookup. Reimport merges any new attachment facts without clearing existing parents or repeating preparation of an initialized subtree. Identity classification alone is not proof of that initialization. Array occurrences use the compressed backing representation below.

Keep `markShared` as the ownership operation until phase 2, including its existing lookup call. Its calls neither initialize nor maintain incoming relationships, and parent tracking adds no new lookup bookkeeping. Phase 2 removes the flag and lookup's marking effect together. Do not make parent-map size an ownership test, clear sharing on deletion, or force COW merely because parent metadata exists.

### 4. Publication and representation details

#### 4.1 Prepared logical edge transitions

Use one prepared edge transition beneath the existing placement machinery. It receives the logical owner, normalized key, and current old/new placement facts; prepares incoming changes and any required counter changes; and commits them with the accepted storage, overlay, and structural transition. Complete fallible preparation before committing that destination's new logical relationships. An individual failed storage write retains that target's previous physical facts. Successful earlier storage writes and shared settlement keep their required bookkeeping even if the enclosing operation later fails. Synchronous logical publication invokes no user callback between committing the value and its bookkeeping.

Capture the previous logical placement without consuming it: use its installed version when present, otherwise the own data descriptor already obtained by mutation preflight or a non-consuming `capturePlacement`. Return and carry descriptor facts from `assertCanSetLanguageProperty` and `assertCanDeleteLanguageProperty`; carry the actual physical target/index and old value separately when Array projection or an overlay makes them differ. Do not call `readLanguageProperty` merely to remove an old incoming edge, classify an unused raw value, or subscribe to a replaced thenable. A metadata-only transition with no physical write needs no physical-value read solely for parent bookkeeping.

Finish input reception and callback-capable work before preparing publication. Inspecting an already prepared graph does not consume values or subscribe; counter indexing, storage preflight, and structure preparation therefore cannot deliver earlier callbacks. Capture the current logical edge once and use it through synchronous commit. Physical descriptor facts remain separate because an overlay can mask a different stored value. After suspension, resume through the captured version's ordinary publication authority before preparing its update.

A detached captured version advances only its retained value and required captured structure, without writing current storage or changing the replacement's incoming edge. Check this authority at publication entry. No second authority check or edge capture is needed after non-consuming preparation. This ordering belongs to the common placement transition, not to individual mutators.

Incoming maintenance runs whether or not the owner has a refcount index. Property-version publication owns the common edge transition: commit storage, version, and structure; maintain incoming parents; then apply optional counter changes prepared by `refcounts.prepareCounterUpdate`. Refcounts owns only its counter projection and has no dependency on parent or property-version modules. Both `preparePropertyCommit` and `installPlacementGate` use this transition. Direct version installation must either belong to private construction, be edge-neutral, or use this boundary when changing a published logical edge.

One direct installation is deliberately edge-neutral: `installMutationVersion` replaces an already pending logical version with another pending version before registering its continuation. Neither version holds a ready managed child, and any physical child remains masked, so this installation needs no incoming-edge delta. Its later delivery uses ordinary publication and may add an edge. Name this route in instrumentation and verification rather than treating every version installation as a ready-edge change or inventing a separate parent protocol.

Admission alone does not imply input preparation: control inputs can be classified without being retained as graph data. Their conversion still uses `normalizeRawPropertyValue` when it consumes a raw property. Published managed graphs instead already have normalized placements and pending-delivery obligations; their ordinary inspection never starts fresh reception.

Shared Promise publication maintains relationships before exposing completion, even if the initiating operation's local consumer has closed. Add the delivered child's parent only if that version still owns the current placement. Detached versions and recovery captures retain their values under existing lifetime rules without claiming former live locations. Gate installation removes the old logical child relationship when it replaces that placement with pending state; later publication adds the current child. For Arrays, masking a backing occurrence implements that removal without erasing the physical backing fact.

#### 4.2 Staged construction, import, and native adoption

Commit staged construction from already prepared identity, placement, and shape facts. Finish every fallible source read, Array shape capture, subscription, and allocation required to assemble copies before publishing admissions, completion facts, or incoming registrations. Split the existing container-structure copy helper into preparation and application: capture record order and Array shape, including forked pending growth dependencies, before admission; apply only those captured facts at commit. Route import and ordinary COW through the same helper. A source Proxy length failure must remain the boundary's ordinary preparation Error, with no partial segment publication. Release construction-only shape captures on completion or discard. Existing published source settlement and writes to shared backing remain separate accepted transitions.

During import, retain the managed edge facts discovered by the required staged walk, including unchanged ready properties. Staging retains unchanged ready placements as well as converted or pending values, so it can establish every incoming occurrence. Preserve the minimal parent/key/child and representation facts separately or alongside retained staging records, without retaining a property version merely for bookkeeping. At commit, map sources and children to their final adopted/copied identities and publish their relationships with successful admission. Record each occurrence before skipping repeated recursive inspection, so aliases and cycles remain complete. A failed segment or abandoned callback installs no partial relationships from that segment. Pending delivery uses the same staged import and current-version publication rules.

Reuse the preparation walk's staged key/version records for incoming occurrences, including children admitted before the segment. `connectChild` retains its smaller identity-only dependency set for propagating borrowed-container copies; it is not a second edge-discovery pass or the complete incoming index. Keep source identities used during staging distinct from final targets used at commit.

Private construction has a precise boundary: until its topology is ready for adoption, it is not queried or used as a published managed graph. Its required construction or validation walk supplies edge facts before managed publication. A native mutation receives its isolated working graph under the existing invocation boundary; that graph remains outside the incoming index during native writes. Construction that borrows existing managed children still requires ordinary source protection throughout construction and destination handoff; deferring new parent entries is not permission to release that protection early. Both native receiver modes now copy the complete canonical graph under Phase 3 section 8; their source protection ends at capture.

`initializePlacements(owner, operationContext, entries?)` is the common initialization boundary. Fresh private containers supply their final own storage and overlays; import and receiver validation supply entries captured by their required preparation. Reuse raw placement reads. An Array received after control conversion may already have overlays; capture the physical descriptors beneath those overlays after subscriptions and before admission, including slots masked as absent. Logical captures cannot initialize those backing occurrences. This requires no second graph walk or maintained construction edge index. An ArrayView registers its owner and overlays without scanning inherited backing elements. All managed shells are admitted before registering cyclic or aliased edges. Ordinary shallow COW completes this boundary before indexing, path use, or return. Failure atomicity belongs to each construction, not to an entire mutation path: an earlier completed copy retains its valid topology even if a later copy fails.

Private outputs that can receive pending delivery attach a `PlacementConstruction` authority before population or derivation callbacks can run. Its staged/published/discarded disposition controls those deliveries; it stores no logical or physical edge maps. Placement writes skip incoming maintenance while their owner is uninitialized, and completion initializes relationships from final storage and overlays. Physical writes independently skip maintenance only while their backing is uninitialized: successful changes to an existing shared backing remain immediate, even when the new view later fails. This covers shallow COW, remapping, derived views, extension, and controlled Array outputs without separate bookkeeping modes. Successful completion removes the metadata link; callbacks retain only their record/version authority.

Use the per-container staged/published/discarded record as pending delivery's publication authority. The batch coordinates commit/discard and releases staging collections; it adds no second persistent state machine. Private outputs may link the same record from metadata; input preparation keeps its records local.

This temporary construction link belongs only to a privately allocated output with one construction owner. It is not an in-flight initialization registry for arbitrary received identities. Input preparation uses its local staging identity map, as specified in section 4.3.

Delivery into unfinished construction updates its destination storage or staged versions. After publication it uses ordinary current-version authority; after discard it performs no destination work. Final-state initialization includes synchronous deliveries that arrived while a later property was being copied. Ready-only complete-graph copies and external snapshots need no delivery record. Receiver validation retains its inspected entries until successful adoption, while isolated native working graphs remain uninitialized throughout native mutation. Existing published sources always keep their own settlement and bookkeeping authority.

Keep that isolated receiver outside the published incoming index while arbitrary native code runs. Do not index its initial copied edges and then try to repair them by walking only the final receiver: native code can save `this.child`, delete that property, and return the child. The returned child survives, but its deleted receiver edge is no longer discoverable from the receiver. Instead, the existing required receiver-validation and result-adoption walks prepare the final topology of each graph that survives. Register edges per placement occurrence even when recursion has already visited that child. Publish the prepared relationships before exposing the corresponding receiver or result; merge overlapping adopted graphs idempotently.

Preserve the existing, asymmetric failure rules. A valid receiver mutation survives an independent result-import failure. Receiver validation or required receiver-publication failure instead poisons the mutation scope and the operation result, retaining any independently discovered result Errors; a valid returned child is not delivered as successful output in that case. A direct native result Promise still belongs to invocation completion, whereas a Promise nested in its returned data does not postpone an otherwise completed receiver transition. Parent preparation changes none of these boundaries.

A failed private validation or preparation batch publishes no relationships from that batch. A successfully completed local adoption is different: its final internal relationships can remain if a later receiver or destination publication fails, just as for a completed COW container. Do not undo correct adopted topology merely because a later operation outcome discards that graph. This keeps construction failure atomic without adding a transaction across receiver validation, result admission, and scope publication. It requires no native-write interception, undo log, global construction registry, or rescan to repair a previously published index. Arbitrary native no-op comparison remains deferred; maintaining final adopted topology is required in this phase.

External-property snapshots use the same private-construction rule. `snapshotExternalValue` admits all ready copy shells only after the snapshot succeeds, then initializes relationships from their private storage. Its direct-to-native export route skips admission and managed incoming registration. Failed snapshots register no relationships and leave source metadata unchanged.

#### 4.3 Shared preparation for Cascada-created and imported data

Input preparation and imported ownership are separate responsibilities. A Cascada expression such as `var x = {a: 1, b: 2, c: getC()}` creates an unimported outer container. A value returned across the host boundary by `getC()` or `api.getCoordinate()` goes through import processing. Embedding an imported child does not make its Cascada-created parent imported, and attaching that parent does not remove the child's existing protection.

Import, managed assignment, Chain initialization, and call-input reception are the preparation boundaries. Share one staged input preparation mechanism beneath their ordinary value reception, reusing the existing import traversal and publication machinery. A ready managed value must be prepared before publication or retention that relies on its internal relationships; a pending captured input carries the same obligation into delivery. An initialized value requires only its completion check. The receiving boundary supplies ownership, validation, and Error-attribution rules; parent registration does not choose them. Import records parent facts during its required walk, while other receivers prepare only previously uninitialized containers. A Chain root uses ordinary assignment/value delivery, so constructor and assignment must not each walk it. Controlled Array payload publication reuses call-input preparation. No explicit import or imported/shared marking is added for a Cascada-created literal merely because it was prepared.

Preparation reads must use the category already known to that attempt, whether staged or committed. Pass that category to the common key reader, currently `enumerableLanguageKeyCandidates`, so it filters non-index Array keys before descriptor reads or value consumption. The shared preparer supplies this staged fact before admission. Readers must not infer record semantics merely because Array metadata has not committed yet. Do not publish metadata early to make ordinary readers classify the source correctly, reclassify the identity, or introduce a second Array traversal. Existing initialized containers continue to use their authoritative versions and category.

Use one execution-local completion fact on each managed identity, conceptually `placementsInitialized`. It means the container's available logical placements and their managed edges have been prepared and committed, with later pending delivery covered by ordinary version publication. It does not mean all values have settled. Existing type metadata, `imported`, incoming-map presence, and refcount initialization are not substitutes: classification can precede preparation, and a fully prepared root can have no incoming parents. Set this fact only with successful preparation, never when a fallible walk merely starts. Keep it separate from admission: current control-input consumption can fix an identity's category and prototype without preparing its graph. Eliminating that distinction by introducing non-admitting conversion/search paths would change more than metadata layout; Array conversion itself uses logical placements and captured versions. Do not add such parallel consumption paths merely to remove this field. Reconsider derivation only if the integrated admission inventory proves equivalence under the same semantics.

Reuse admission's conservative category probe: an identity whose structure cannot be established stays an exact external leaf, rather than becoming a whole-segment structural Error. Once managed structure is established, failure to enumerate or inspect its required placements follows the preparation-failure policy below. Thenable recognition retains its own causal kinds and Error/Function precedence; it is not ordinary managed-property enumeration.

The common preparation rules are:

- At an initialized node, skip descendant preparation and still register the new incoming occurrence supplied by its parent or destination. Reusing a subtree does not omit a new edge to its root.
- At an uninitialized node, stage its logical placements and visit each newly encountered managed identity once. The staging identity map also bounds cycles; record every parent/key occurrence even when recursion is skipped for an alias or cycle. Use this same algorithm for imported and Cascada-created data, without a separate acyclic-literal path or cycle-analysis pass. Commit completion facts and relationship facts together after successful preparation.
- Walk only the newly available portion of the input. Establish pending placement publication at the current receiving boundary and return without awaiting unresolved data. When a value arrives, prepare any newly revealed uninitialized containers before publishing their relationships. An imported result delivered into a literal will already have passed its import boundary; the destination adds its edge without walking that result again.
- Preserve imported ownership on existing children, and use ordinary runtime ownership for newly created Cascada containers. Functions, Errors, and external identities retain their existing boundary rules; they acquire no managed outgoing graph walk.
- Maintain initialized containers incrementally through common publication. COW copies, Array materializations, and adopted snapshots establish completion through their existing construction batches; they do not run another discovery walk after copying or inherit the source's completion flag before their own construction finishes. Isolated native mutation graphs become initialized only when their final topology is adopted.
- Failed staging commits none of its uncommitted destination relationships or completion facts. Another boundary's completed initialization, shared source settlement, and successful writes to existing backing retain their own maintenance obligations. Pending continuations retain only their exact publication obligations; abandoning a private construction does not create a second preparation task or global registry.

Ownership follows the existing inward boundary and admitted identity facts, not the order in which later holders receive the value. Completion reuse must neither mark a runtime-owned child imported nor clear imported protection. An imported wrapper may legitimately reference an already admitted runtime-owned child, including through pending delivery; preserve that supported case. Host roots require import before ordinary managed reception. Passing one unadmitted raw host identity concurrently to import and ordinary reception violates that contract; the runtime need not assign competing origins independently of first commit for that unsupported case. Do not invent a blanket prohibition on identities reaching both import and ordinary reception as a shortcut for sharing topology.

Each evaluation of a Cascada object or Array literal allocates its newly constructed containers afresh. Do not reuse mutable literal templates between evaluations or executions. This is not a fresh-graph requirement for every reception: a new wrapper may borrow already prepared children, and repeated handoff of one managed value within an execution intentionally preserves identity and aliases. Host-owned cached graphs cross import; managed values crossing executions use export then import. The compiler allocation obligation requires no runtime provenance registry or defensive cloning.

Runtime-created Chain state objects and entered/mutation holders are known empty containers before their first `value` publication. Their common holder construction establishes placement completion without an input scan; ordinary publication then maintains the root edge. Do not leave these owners uninitialized, infer their completion from admission metadata, or make later lookup/query bootstrap them. Recognizing a retained root for retirement is a separate phase 2 fact, not part of this completion marker.

For the literal example above, preparation visits the new outer object and its properties once. If `getC()` has returned a prepared managed object, only the `x.c` relationship is added; if its result is pending, that relationship is added on delivery. Passing the prepared `x` through another assignment or Chain adds the new holder edge without repeating its internal walk. Likewise, `var x = api.getCoordinate()` uses the import walk for the returned graph and only a holder attachment during assignment. Distinct properties and holders always retain their own publication/version semantics even when input preparation of their shared child is reused.

Import remains necessary at the host boundary for validation, protection, and causal attribution, including results used before any assignment or Chain construction. Record parent relationships in that existing walk rather than defer them until attachment. Deferral would require another traversal or retaining the discovered edges for later, and preparing only a subsequently selected descendant cannot recover its outside parent. This choice accepts parent-index allocation for imported graphs that are later discarded, in exchange for complete relationships and no repeat discovery. Required method-result validation and native-receiver finalization still run when their contracts demand them; the completion fact skips repeated graph initialization, not distinct validation obligations.

##### Reception timing and boundary selection

Separate the responsibilities by the fact they establish, without adding separate graph walkers:

| Responsibility | Required timing |
| --- | --- |
| Capture a value or property version and claim known conflicting-effect order | Before later operations can replace that input or overtake the selected effect. A later continuation must use that capture, not look up the current value again. |
| Protect a captured managed generation | Before suspension or callback delivery can expose it to a later writer, through actual last use or a completed handoff. A pending capture protects its delivered identity at the producer/consumer transfer, not merely when an outward Promise callback eventually runs. |
| Establish a new container's outgoing relationships | Before relying on those relationships for ownership of its borrowed descendants. Initializing a fresh wrapper can be necessary for protection even though no destination is ready yet. |
| Perform boundary-specific preparation | Once its consumer is known: managed publication, controlled payload reception, native argument export, or receiver validation. Existing completed initialization is reused; no full walk is added merely to acquire a root lease. |

Subscribing earlier does not accelerate an ordinary Promise's underlying work. The reasons for early work are capturing the correct logical generation, preserving ordering, and protecting borrowed identities. Error-segment size alone is not an ownership reason to walk a graph early. An already initialized graph can wait under root/capture protection and use its existing relationships; ordinary preparation remains a completion check. Imported inputs also retain their independent host protection.

**Selected handoff rule:** issuing a consumer synchronously transfers responsibility for preserving its inputs, including pending inputs. The [integration contract](integration.md#managed-value-reception-and-delivery) defines direct reception, temporary Chain release, and pending delivery. Phase 2 implements that contract; this section supplies its preparation prerequisite.

Establish fresh retained input graphs through common preparation at their first runtime handoff, before a wait can expose borrowed descendants to later operations. For `argument = { child: source.lookup(["child"]) }`, leasing `argument` alone neither leases the child nor records `(argument, "child")`; a later writer through `source` cannot see that off-path lease. Preparing the wrapper records its actual edge, after which ordinary parent relationships and root retention preserve the borrowed child. A directly passed prepared child instead needs only receiving retention. Prior Chain initialization supplies preparation when the compiler already created that holder; passing a raw literal uses the receiving boundary. Do not require a synthetic Chain for every literal, compiler-written metadata, a second recursive leasing walk, or another permanent-sharing flag.

For an ordinary Chain initialization or a known managed assignment, start input preparation at operation issuance, before waiting for the target. Establish the operation's required routing, capture, and known conflicting-effect order first; protect the input before callback-capable preparation. Feed the prepared value or captured input version into target work and retention, rather than returning to the raw input after a target wait. One receiving boundary owns its subscriptions, failure context, and later delivery. Do not layer a second raw-input consumption in the lease path on top of preparation. Target publication only attaches the prepared value and maintains its destination edges.

For example, issue `x.a = { good: 1, bad: T }` while `T` is pending. Preparing this input must establish the same nested pending boundary whether `x` is ready or still waiting. If `T` later delivers a managed container whose required inspection fails, `bad` receives the Error in both executions. Waiting for `x` before starting preparation could instead consume an already-ready `T` within the outer segment and fail the whole payload. That difference is avoidable for a known managed assignment and is not permitted.

An outward-only assignment uses the same fresh-input preparation as other receiving boundaries. Establish its known external ordering claims, capture and protect the input, and prepare available managed structure at issuance before target or predecessor waits. Export the prepared value or captured input outcome and carry the detached export to the write; never return to the raw input after a wait. Pending delivery prepares newly available structure before export consumes it. Source containers acquire complete internal relationships even when export is their only consumer; output copies and the argument list acquire no managed parent registrations. This replaces the former preparation exemption: the current exporter admits and normalizes fresh sources, so bypassing preparation would leave partial relationships. Keep one managed copier, not a separate non-admitting export walk. Ready rejected routes and unused inputs retain their existing consumption rules.

Calls retain receiver-first method selection, conversion, and native export. Common reception prepares fresh managed arguments that invocation must retain or consume, before a receiver wait, mutation-path traversal, or selected argument processing. Already prepared roots require only the completion check and their ordinary retention. This ownership work may inspect a fresh literal even if selection later rejects the call or leaves that argument unused; it is not speculative export or method-specific payload processing. Mutating calls prepare inputs before receiver traversal even when dispatch later rejects: their arguments may borrow a path ancestor directly or inside a fresh wrapper. Ready rejected observations leave arguments unconsumed. Preparation records input outcomes independently: an unused argument's pending value or data Error does not become a required call wait or failure merely because invocation provisionally retained it.

Selected controlled Array processing reuses the received payloads before remap/view construction stores them. For `concat`, prepare a new source Array once before capturing its elements; copied elements reuse their captured prepared versions. This records source element edges and new result edges without a fictitious argument parent. Selected native calls export those received values into independent copies. Release input retention only after capture or publication has taken responsibility for every remaining source access, not merely because receiver classification finished.

This decision supersedes the earlier proposal to delay all call-input preparation until receiver selection and accept the resulting structural Error-segment difference. For the same consumed input, receiver delay alone must not postpone its first required preparation. Whole-segment structural failure still depends on which nested values are available within each preparation segment, as specified below; no partial-admission mechanism is added. Ready rejected observations can still leave arguments untouched while pending selection provisionally consumes them. Mutation calls provisionally prepare arguments before any receiver-path mutation in both ready and pending cases. Update the authoritative consumption contract to describe the added fresh-structure preparation, without weakening successful value/effect ordering or turning provisionally inspected unused data into required Error collection.

##### Preparation and publication authority

A supported thenable may synchronously invoke only its newly supplied callback. It cannot drain older subscriptions or interleave another preparation into the current walk. Prepare each available segment in one synchronous identity walk, consuming its placements in order. Synchronous delivery continues that walk; later delivery starts a new segment after the current one has committed or discarded. No capture-then-subscribe pass, subscription queue, initialization reconciliation, or pending-frontier polling is needed.

Follow a borrowed version's existing publication dependency before consuming its value; source-Promise readiness alone does not prove publication complete. Method-result validation retains its independent Error and capability rules. Copy containers with borrowed pending placements that require result-specific validation, and propagate copying through their borrowed ancestors while preserving aliases and cycles.

Each prepared container has one staged/published/discarded publication record. Commit publishes its captured versions, complete relationships, and preparation completion together. Discarded callbacks perform no later destination work. Published callbacks continue ordinary version settlement, including after detachment; being replaced does not turn a published version into abandoned construction. Clear staging references on success or failure, keeping observed sources handled.

The staging map bounds aliases and cycles. Ordinary later reception of a completed identity skips subtree preparation. Required method-result validation remains separate from that completion fact. Final commit starts no discovery, subscription, or host action.

##### Input outcomes and preparation failures

This deliberately moves inspection of a newly received Cascada-created container's available structure from later lookup to its assignment, initialization, or retaining call-input boundary. Preserve nonblocking issuance: a prepared segment may contain pending placements whose delivered values undergo their own preparation. Ordinary Error data, failed input preparation, and failed destination publication are distinct outcomes. Do not infer which occurred from `isPoisonError(value)` alone; keep the distinction at the receiving boundary using its existing outcome conventions, without introducing a new public result type or Error framework.

Shared preparation must preserve placement-value validation as well as graph discovery. In particular, publishing a Function at an ordinary `then` placement produces the existing `PropertyValidation` Error before the value can be exposed or assimilated. Factor the existing assignment and ordinary Promise-publication checks into one placement-value validator, and use it for synchronous staged delivery and later import/input delivery before admission or version commit. The common preparer applies this validator before staged or deferred publication. Managed receiver finalization uses the same rule with its `InvalidManagedReceiver` kind. The validated Error follows the receiving boundary's existing Error-data or clean-result rules; do not invoke the Function, relabel it as structural reflection failure, or add an export-only workaround. An already callable root `then` still follows supported-thenable recognition; Array non-index fields remain outside the graph.

The following rules are fixed. Ordinary value reception accepts Error data; method-result validation retains its separate clean-result requirements and Error collection.

| Event | Attribution and outcome | Parent and recovery effect |
| --- | --- | --- |
| Raw Error or rejected value at an ordinary input boundary, including a newly prepared literal's nested placement | Contextualize at the receiving operation: `ChainValueFailed` for ordinary Chain initialization, `AssignmentValueFailed` for managed assignment, `OperationInputFailed` for call inputs including controlled Array payloads and outward-write inputs, and the import policy's existing value kind for imports. Preserve already contextualized Errors unchanged. Errors remain graph data at their receiving placements; preparation continues around them. | Commit the valid container topology. The Error has no managed parent entry. An Error-valued assignment is a data write, not failed-mutation rollback; successful assignment still returns `undefined`. A Chain constructor stores its logical root outcome in its holder. |
| Supported structural inspection failure while preparing a new input segment | Publish an Error-valued input for that segment: `ImportReflectionFailed` at import, `ChainValueFailed` at ordinary Chain initialization, `AssignmentValueFailed` at managed assignment, or `OperationInputFailed` at call-input or outward-write reception, with the receiving operation's context. Method-result Error collection keeps its existing obligations. | Discard that segment's uncommitted initialization; already completed preparation elsewhere remains valid. Publish the Error through the receiving input version. If the destination write succeeds, managed assignment returns `undefined` and creates no repair baseline for this input failure. |
| Controlled Array use of a prepared payload | `push`, `unshift`, inserted `splice`/`toSpliced` values, `fill`, and `with` treat a payload Error as data at each actually written element. A nested Error stays inside its prepared payload. A failed required `concat` argument produces its operation Error rather than inventing an element for an Array it could not inspect. Delayed element delivery updates only its captured versions. Payload data alone does not create a receiver rollback baseline; independent required mutation failures retain ordinary recovery. |
| External assignment or arguments selected for a host call | Keep existing export attribution: raw inputs use `OperationInputFailed`, supported export reflection uses `ExportReflectionFailed`, and already contextualized input-preparation Errors keep their source and kind. Required clean-input export failure prevents the host action and follows its existing selected-operation failure effect; it is not ordinary managed Error-data assignment. |

**Selected policy: preparation failure produces Error-valued input.** Keep ordinary input Errors at the placement receiving them, leaving healthy siblings usable. For `{ good: 1, bad: error }`, only `bad` holds Error data; the outer container is prepared normally. The same applies when `bad` rejects, or when `getC()` independently returns an import Error inside a Cascada-created literal. A later whole-graph consumer may collect and return those Errors, but that does not replace healthy graph branches with poison.

Structural inspection failure keeps the existing import transaction boundary. One available segment consists of the newly reached containers prepared together at a receiving boundary; unresolved placements get their own preparation on later delivery, while synchronous thenable delivery remains in the current segment. If inspecting any container in that segment fails, abandon its uncommitted preparation and publish one Error at the segment's receiving root. Thus a ready input `{ good: 1, bad: managedContainerWhoseOwnKeysThrow }` becomes an Error as a whole. If the outer container was already committed with a pending `bad` and that value later reveals a managed container whose required inspection fails, only `bad` becomes Error data. No completed ancestor is retroactively failed. A ready root and a Promise-delivered root use the same segment rule; delaying a nested value can change segment boundaries, as it already does in import.

Localizing structural inspection failures further is feasible, but requires more than a catch around each recursive call. A failing container may already participate in staged aliases or cycles, have children also reachable through healthy branches, or own pending subscriptions. Preserving the rest would require rules for redirecting all affected occurrences and deciding which staged admissions, outgoing edges, and callbacks survive; context import must also preserve atomic authority registration. Phase 1 retains whole-segment failure for these structural cases and branch-local Error data for ordinary input failures. Use the same staged preparation algorithm for import and ordinary reception, without a separate partial-admission path or keeping mutations open until all nested inputs settle.

The selected compiler handoff is recorded in [AGENTS.md](../AGENTS.md#cascada-value-handoff-and-temporary-chains) and [integration.md](integration.md#managed-value-reception-and-delivery). The companion input/import/Error documents and timing-sensitive fixtures describe and verify the implemented preparation policy. Phase 2 subsequently implemented bounded delivery and removed permanent sharing. Initialization now prepares newly received graphs at the stated boundary; ordinary reads continue to consume pending versions and perform their required normalization rather than becoming a fallback for missing parents. Keep shared preparation consistent with those documents without conflating ownership, and retain receiver-first dispatch and export. Preserve separate tests for unimported Cascada-created inputs and protected imported inputs rather than converting ordinary `Chain` fixtures to `ContextChain`.

#### 4.4 Array backing facts and logical owners

ArrayViews share physical storage but own distinct logical placements. If `A[5] === child` and a view starts at index 5, the child's parents include `(A, "5")` and `(view, "0")`. The representation records the shared storage occurrence once and derives those placements when needed, avoiding a ready overlay and reverse entry for every child in every view.

An execution-local **Array backing record** holds the physical Array and a registry of its logical owners. Each owner supplies its existing projection, offset, and logical bounds; do not duplicate those shape facts. A native Array is one logical owner. Its attached internal projection is not an additional owner. A separately published ArrayView is another owner. The record is runtime metadata, never a language graph node or exported value. It can be associated with the Array's execution metadata; wrapping every storage access is not necessary merely to retain the registry.

For a native Array `A`, direct overlay entries and returned parent placements use `A`, even when `metaOf(A).arrayView` supplies its projection. If `A` is itself a managed child, record its incoming entries on `A` too. For a separately published ArrayView `V`, use `V`. The backing record represents physical storage only. Keeping it distinct from the native owner's logical identity avoids tagging a single `(A, index)` entry as physical, logical, or both when an overlay holds the same child as its backing slot. This small lazy allocation is preferred to another tagged update protocol; imported Arrays can use the same representation even though they cannot become mutable view backing.

Use two existing sources of a logical slot's value:

- **Backing storage:** the child's incoming map records the backing record and every physical index containing it. Repeated occurrences of one child need all their indexes. Create the backing record lazily when the first such relationship or view registration needs it. Use this representation for tracked physical Array slots before the first view too, so adding views does not require migrating old child entries or rescanning the Array.
- **An owner's placement overlay:** the child has an ordinary direct `(owner, logicalKey)` incoming entry. Copying or settling that overlay uses ordinary placement publication. A pending overlay, absence overlay, or ready override masks the backing occurrence for that owner, even when its eventual or current value equals the backing value.

To enumerate a child's parents, expand its known backing indexes through the registered owners. Translate `logicalIndex = physicalIndex - start`, check the owner's current logical range, and exclude locations with an overlay. Direct entries supply the overlay-held occurrences. This yields each placement once, including when the same child appears in several backing slots or in both backing and overlays. Use the existing ordered shape/presence facts; neither physical length nor a pending maximum proves that a logical placement exists. Merely enumerating candidates must not consume unrelated pending values or reinterpret a detached version as current.

This range check needs no host read. For an unprojected native Array, a maintained present physical index already proves range membership. For an owner with a projection, use its stored start and committed length. Array backing expansion must not call the ordinary native-Array length reader or create shape metadata solely to answer this query.

Import and construction establish backing relationships from the physical placement facts they already inspect or create. Later physical writes maintain those facts at their common storage boundary. View derivation registers one new logical owner, transfers only the overlays already required for logical values, and retains its ordinary capture or unretained-suffix work. It adds no overlay or per-child incoming entry solely for an inherited ready backing child.

Only own enumerable canonical-index data slots contribute physical managed-child facts. Hidden properties, accessors, Symbols, and non-index Array fields do not become incoming occurrences merely because reflection lists them. Logical keys are normalized Strings; backing positions are canonical numeric indexes. Preserve this distinction at the storage boundary so `5` and `"5"` cannot become two encodings of one physical occurrence.

Logical and physical changes are related but distinct:

| Representation event | Required parent update |
| --- | --- |
| Install or replace an overlay | Update its direct logical child edge. The overlay masks the owner's backing occurrence; preserve that physical occurrence for other owners and later fallback. |
| Remove an overlay | Remove its direct edge. Backing expansion then exposes any in-range occurrence allowed by the committed placement and shape rules. |
| Successfully write or delete a physical slot | Update the backing occurrence from the actual old and new physical values, using facts captured by the storage writer's existing reads or preflight. |
| Publish a view or change its committed projection | Register its logical owner or update the existing projection facts. Expansion uses the new bounds and masks without walking inherited children. |

An old logical value is not evidence of the old physical value: an absence or ready overlay can hide a different managed child in the backing slot. Never derive a backing removal from the logical transition alone. If an optional physical cache write is omitted or fails under its existing contract, retain the old backing fact and publish the accepted logical overlay through the ordinary boundary. Keep a managed-child backing occurrence while that physical slot holds it, even if current owner bounds or overlays mask every use.

One logical write can have more than one storage target. In particular, `preparePlacementStorage` prepares an entered holder's write through its still-current source gate before writing the holder itself. Maintain physical backing facts for each actual storage write, with that target's own old value and physical index. The pending source gate continues to mask its physical slot until logical publication; mirroring storage does not create a ready logical source edge. Logical parent transitions remain attached to their respective holders and gates. A hook only on the outer holder commit would miss the source backing change.

Materialization constructs a fresh Array with its own backing facts. The old view remains registered while it still represents its old storage; replacing a Chain root alone is not disposal. Failed construction must not expose a partially prepared logical owner.

A private view does not imply private backing storage. Endpoint extension can grow an existing backing and write some appended slots before a later slot fails. Stage the new owner's registration and direct overlay edges until the view is complete, but maintain every successful write to the already published backing immediately through the storage boundary. Abandoning the view discards its staged relationships, not those real backing changes. They may expand to no logical parents because existing owners exclude the appended range. Do not register the failed owner, fabricate a parent for an excluded slot, or add physical rollback merely for indexing. This is the same distinction as shared source settlement during private construction: abandoning the destination cannot discard maintenance owed to an existing representation.

Enumerated logical `(parent, key)` placements carry no authority for raw shared-slot replacement. Logical publication must preserve overlays, captured versions, and per-owner counter updates through the common boundary. Physical backing maintenance and logical placement publication retain their separate responsibilities.

This phase records native-created aliases but does not by itself fix the previously identified mutation-through-unshared-alias behavior. Import protection already works; native alias protection and the chosen effective-write semantics remain separate work. Parent indexing must not silently change them.

### 5. Encapsulation and implementation sequence

Keep one internal parent-relation helper beneath the existing placement machinery. Its small responsibility is to prepare and apply idempotent source/key additions and removals, and enumerate current logical parent placements. Construction batches and live transitions use those same primitives. The Array module owns backing membership and projection into logical placements. The helper does not read host properties, classify values, traverse a graph, decide sharing, or build refcounts. Callers supply already admitted identities, normalized keys, and captured placement facts. Consumers see logical placements through this surface rather than inspecting backing registries themselves.

Shared boundary preparation owns the outgoing-placement completion check and staged traversal. Internal graph producers establish completion through their construction commit. Chain constructors and individual mutators must not each manage the flag, select a graph-walking mode, or duplicate import logic; they use ordinary value reception with the receiving boundary's Error kind. Common call-input reception uses that preparation before retaining fresh structure, and controlled payload processing reuses it, including custom `with` and `concat` routes. Factor it below input boundaries rather than calling import from placement commits; the importer keeps its import-specific policy, and placement commits consume prepared facts. The private-construction helper owns its temporary metadata link and staged facts. This keeps discovery at input or construction and incoming maintenance at placement commit.

Use one internal enumeration primitive and a snapshot wrapper over it:

```js
visitParentPlacements(node, operationContext, visit)
getParentPlacements(node, operationContext) // Array<{ parent, key }>
```

The visitor calls `visit(parent, key)` for each placement; returning `false` stops enumeration. This synchronous runtime callback neither suspends, invokes host code, publishes graph changes, nor mutates the index being enumerated. It is a narrow traversal primitive, not a second interpretation of parent storage.

The snapshot wrapper collects all placements; consumers that update them use this wrapper. The counter verifier filters indexed parents and cycle-cut keys in its own comparison, while production counter propagation uses the maintained projection directly. Keep ownership policy and counter interpretation in those consumers.

Both forms share this contract; the snapshot additionally owns its result collection:

- Enumerate current logical placements holding the supplied managed node, with normalized string keys and each `(parent, key)` appearing once. Order has no semantic meaning. The snapshot wrapper returns a separate result collection, not a mutable reference to the stored index.
- Read ordinary direct entries as placements. Expand Array backing entries through their registered owners, current bounds, and overlay masks. Array overlay entries are direct entries too; the distinction is where the slot's value comes from, not merely whether its parent is an Array.
- Use maintained identity, location, overlay, and shape facts. Do not scan backing elements, perform host reflection, initialize refcounts, or resolve pending payloads. A pending placement does not yet hold its eventual managed child; common publication adds that child's relationship when available. In-range backing membership relies on committed bounds, never a speculative maximum; pending transitions remain governed by their overlays.
- Trust the publication invariant for the supplied managed node. An absent incoming collection yields no placements; it never requests initialization or source discovery. Do not query an unfinished private construction as though it were a published graph, or add a runtime flag solely to check this trusted internal boundary.
- Treat results as locations observed at the call, not as authority to overwrite them later. Consumers use normal placement/version capture and publication checks. After suspension or preparation that can synchronously deliver callbacks, revalidate the captured authority and current edge before updating a location.

A snapshot lets a transition update placements without mutating the collections it is still enumerating. No lease is needed merely to assemble it: enumeration uses internal facts synchronously and invokes no user callbacks. Read-only consumers can stop without allocating a full snapshot; counter propagation needs no complete-parent enumeration. Later comparison, waiting, and publication retain their own ordering and protection responsibilities. Keep this API internal; it does not expose backing records, stored key sets, the compact encoding, or another public graph query.

Implement at common boundaries rather than adding parent protocols to individual mutators:

1. **Define the publication invariant and small parent API.** Add the incoming representation, outgoing-placement completion fact, idempotent update primitives, synchronous placement enumeration, and an independent verifier. Keep counter initialization independent of incoming metadata. Audit producer call sites and fixture setup against section 4.3 before relying on complete incoming data; update each producer's fixtures alongside its integration rather than postponing all updates until final verification.
2. **Connect the common prepared logical edge transition.** Cover ready writes, pending publication, gate installation/completion, Chain and entered holders, COW child reuse, transfer, and removal, including owners without refcounts. Finalize old-edge facts and recheck captured authority after callback-capable preparation. Audit direct version installation as well as physical writes, including every storage target reached through entry mirroring; readers need no parent bootstrap.
3. **Unify input preparation and complete private construction boundaries.** Share staged preparation between import, managed assignment/Chain reception, and retained call inputs; controlled Array payloads including `concat` reuse it. Integrate all three reproduced fixes here: staged category-aware key filtering, common callable-`then` placement validation, and structure-copy preparation before admission commits. Prepare fresh retained structure at issuance and reuse its captured versions after target waits. Keep receiver-first method selection and export; outward-only input uses that same preparation before its export capture and target waits. Preserve unchanged ready edges and skip initialized subtrees without changing ownership. Route delivery through each staged record's disposition, and attach the common construction record before any private copy/remap/view write can run. Let existing delivery continuations drive newly available preparation, without polling pending captures. Discard unfinished initialization on preparation failure while keeping boundary validation independent. Keep isolated native working graphs unindexed until final adoption. Include admitted external snapshots and protect borrowed children through handoff. Verify asymmetric receiver/result failures and distinguish discarded batches from completed adoption followed by publication failure.
4. **Integrate Array backing representation.** Connect physical slot facts to each successful storage write, register logical owners at view publication, and maintain direct overlay edges and masks. Preserve successful backing updates when a later slot fails, while discarding the unfinished view's staged registrations. Verify entry mirroring, logical/physical disagreement, first view creation, projection changes, and fallback without per-child view bookkeeping.
5. **Verify the counter projection against complete placements.** Keep the existing counter-parent map, initialization checks, propagation, and cycle detection. Maintain complete relationships in the same transition and extend the independent verifier to compare both projections. Preserve existing counter tests and add missing-edge sensitivity checks and propagation work counts with many unindexed owners. Use the shared Array expansion only for complete-parent consumers and verification.
6. **Verify input semantics and run the connected checks.** Cover direct `Chain` construction, assignment payloads, mixed imported/runtime-owned graphs, and Promise delivery. Count preparation visits across boundary handoffs to prove initialized subtrees are skipped while every new placement is recorded. Compare against an independent logical graph oracle before any lookup or query can alter the scenario. Parent tracking must work before a refcount index exists and remain consistent when refcounts are added later.

### 6. Work bounds and retirement dependency

Before counter initialization, parent tracking retains only complete incoming source/key facts, the Array backing-owner representation needed to expand them, and the outgoing-placement completion fact needed to avoid repeat initialization. Active construction keeps its temporary state separately as specified above. Add no Promise/Error summaries, cycle-cut projection, equality state, or mutation history merely for parent tracking. Allocate the compact entry at the first incoming occurrence and collections only on promotion; do not allocate empty maps for unattached roots. All metadata is execution-local.

Tracking adds constant pair checks or expected constant map/set work per stored source/key change; promotion copies only the existing first occurrence. Import, initial preparation of Cascada-created inputs, copy, and adoption supply edges; parent bookkeeping neither repeats completed preparation nor adds a graph walk to lookup or refcount indexing. Processing a fresh literal visits its new containers and placements once per preparation attempt, skipping initialized subtrees; attaching an initialized root requires no subtree walk. Readiness discovery is bounded by captured versions and their actual delivery/publication events, not the product of pending versions and preparation passes. Count graph discovery and required dependency work separately. Synchronously overlapping attempts can incur work already begun before completion becomes visible, as bounded in section 4.3. Construction staging retains only facts needed for its pending commit or required validation and releases initialization-only state on commit, failure, or supersession. For one backing, the added storage is proportional to tracked managed physical occurrences, registered logical owners, and overlay-held managed occurrences, rather than the product of backing children and views.

Registering a new view adds one backing-owner entry. Its existing overlay transfers, first capture or unretained-suffix scan, and any required counter indexing still have their ordinary costs. This is not a constant-time guarantee for every `push`. The current Array method dispatch tries endpoint view derivation without a `shared` condition, so repeated view creation is not limited to programs that explicitly retain the Array after every push.

Expanding a child's backing relationships moves work to the consumer that needs actual placements. With `k` occurrences of that child and `v` registered owners on one backing, simple enumeration can examine `k * v` candidates and filter by bounds and overlays. It does not scan other element values, but it is not necessarily proportional only to the resulting placements. Start with the registry and existing range facts; add an interval index only if measurement justifies it. Publication updates each affected logical placement and its counter bookkeeping. Counter propagation and cycle detection retain their maintained indexed-parent projection, avoiding this complete-owner scan on each counter transition.

Allocating a ready overlay solely to track every inherited managed child is unnecessary when one shared storage occurrence can represent the same relationships. The integrated backing representation and relationship oracle verify this without per-child view overlays.

Phase 1 keeps strong incoming relationships and removes the entry for each deleted or replaced placement immediately. Recursive retirement belongs to phase 2 because it requires complete accounting for leases, captures, pending publication, and imported host obligations. This is an implementation order, not acceptance of permanently accumulated temporary parents in the completed ownership design.

Direct temporary-holder release is implemented in Phase 1. A private mutation holder removes its root placement after the selected scope publishes; an entered holder waits for its captured publication and contained external effects, detaches its mirror, then removes the root. Pending versions already captured elsewhere continue independently and cannot recreate that placement. This uses ordinary placement deletion, without a collector or holder registry. Observation materialization remains unindexed unless result admission publishes an escaping copy.

Clearing a Chain root supplies the release event. For `holder -> P -> U -> X`, retirement of otherwise unused `P` and `U` must remove `U -> X`, even if `X` remains held elsewhere. Prepared argument wrappers, failed inputs, compiler temporaries, old COW parents, descendants of released holders, and Array owners all require this handling. Phase 2 section 2.3 specifies the common liveness rule, cyclic-group proof, metadata limits, and remaining outgoing/Array storage decisions.

Until retirement is implemented, strong reverse links can retain history through a surviving child; bounds in this phase are over retained representations. A wholly unreachable component can still be collected by JavaScript because the execution's WeakMap does not root its keys. That does not remove stale parents from a surviving node. Phase 1 alone does not restore reuse after ancestor deletion.

The [import retention fixture](../test/fixtures/import-retention.js) records the Phase 1 limitation: strong incoming relationships retain an imported ancestor while its child survives. Phase 2 must replace that expectation with collection after the ancestor's last actual retained use ends, while preserving its independently held child. ### 1. Purpose and governing rule

The former sharing flag remembered that a value had been retained elsewhere, without recording whether that use still existed. Parent relationships provide more precise information about current placements, but do not account for bare lookup results, detached captures, recovery baselines, or borrowed host storage. Replacing the flag therefore requires accounting for those protections as well as graph edges.

The governing rule is: **reuse storage only when the proposed write preserves every other logical value that can still be observed.** A protection acquired for one use ends when that use releases or transfers it, not when an unrelated operation finishes. Removing a graph edge changes graph ownership; it does not release a separately retained result.

Keep three questions separate: liveness asks whether a holder or unfinished consumer still needs a value; mutation permission asks whether changing storage preserves every other observable value; publication authority asks whether a particular version may still update a destination. Imported protection constrains mutation without making an identity an immortal liveness root. A detached version may still settle without retaining or updating its former destination. Derive COW and retirement from these facts instead of replacing `shared` with another aggregate protection flag.

This phase establishes **path-local replacement for effective controlled writes**, including cases where current ready runtime-owned data still follows JavaScript aliases. If `root.a` and `root.b` reference the same `{ k: 1 }`, assigning `root.a.k = 2` must leave `root.b.k === 1`. For `O.self === O`, an effective write to `O.k` produces successor `C` whose off-path `self` still denotes `O`: `C.self !== C` and `C.self.self === C.self`. Finite repeated path occurrences remain distinct mutation steps. These outcomes must not depend on import status, lease timing, readiness, or storage reuse. Phase 2 owns this contract and its tests; phase 3 adds restoration of identity after no-op mutations.

Assignment links its captured right-hand value; a managed native method instead mutates its completely isolated receiver graph using ordinary JavaScript alias semantics. Preserve that distinction and the existing external mutation authority. A uniqueness result cannot authorize overwriting a generation still needed for comparison, rollback, or earlier publication. Do not introduce later identity proofs or optional physical-reuse accounting to establish Phase 2 ownership.

### 2. Ownership facts and their lifetimes

Keep facts at their existing scopes. Graph edges belong to placements, retained uses belong to their holders, and imported-data protection belongs to the admitted identity. Do not flatten them into a second aggregate sharing flag or use the Promise/Error counter projection as an ownership graph.

#### 2.1 Graph placements and Chain holders

Use phase 1's complete incoming relationships for graph ownership, including Array backing expansion. A Chain root is already a placement and needs no additional ownership count for the same reference. Additions, replacement, and deletion change these facts through common publication.

An ordinary Chain keeps its root placement until replacement or deletion. Dropping a JavaScript variable is not a runtime release signal. Cascada clears compiler-owned named, temporary, and result Chains at their last-use boundary, including scope exit when the Chain itself does not escape, after uses finish or transfer preservation and required publication. Ordinary root assignment to `null` can therefore precede completion of a receiving call. Phase 8 owns compiler integration; Phase 2 verifies the kernel sequences it requires. Until that integration exists, an uncleared Chain remains a holder even when its JavaScript variable has gone out of scope. Closing entered-Chain issuance alone does not release an unfinished writer's holder or cancel promised effects.

Keep ordinary root clearing at the final live scope exit too. Render completion does not prove the execution and its metadata are unreachable: a pending host callback can retain the operation context, and a host-retained child can then keep obsolete ancestors alive through reverse links. Skipping final cleanup requires a separate terminal-lifetime proof covering pending work and surviving host identities; it is not selected for Phase 2 or assumed by Phase 8.

Parent records describe locations, not independent root owners. Cycles and several paths within one retained graph must not multiply root ownership by path count. Conversely, a child with one immediate parent may still sit below a protected ancestor. The COW decision in section 3 uses the selected mutation path as well as local incoming facts.

#### 2.2 Retained values outside current placements

Account explicitly for every managed value whose logical state must survive independently of its current graph placement. Reuse the existing counted lease machinery for retention where its protection semantics match; keep different release points on their actual holders. Do not add parallel lease and capture mechanisms that represent the same obligation twice.

| Retaining use | Acquisition and release responsibility |
| --- | --- |
| Ready lookup still held by its managed source | No separate lookup lease or parent entry. Chain initialization or assignment installs the destination placement; receiving work protects any interval before attachment or consumption. Independent continued use requires a Chain or another explicit holder. |
| Produced or removed managed values, including external snapshot lookups | Apply the same immediate reception rule to fresh snapshots, Array elements, mutation results, and other managed outputs. A ready output with no surviving producer protection keeps a lease until the next receiving transition begins, with a queued microtask as fallback. Continued use requires a Chain or explicit holder; host delivery uses detached export. A raw value or Promise is not an independent lifetime holder. |
| Captured property version or pending input | Record the obligation at capture, before suspension. Protection follows delivery even after the source placement detaches, and ends after the capture's last use or an explicit handoff. |
| Export capture | Public export captures a Chain/path; internal argument/write export receives already protected input. Copy ready data synchronously and retain exact pending versions. A caller owns any lease needed before export starts. Exported copies are not managed parents. |
| Unfinished mutation's rollback baseline | The mutation independently retains its baseline until completion, discard, or transfer into installed recovery state. |
| Installed recovery baseline | The exact placement owns a preservation dependency on its baseline. Replacement, successful repair, or owner retirement removes that dependency; a copied placement or independent capture owns its own use. |
| Read lease or other temporary consumer | Preserve its existing last-access release point. A reader finishing does not release another consumer's capture of the same value. |
| Future identity comparison | Phase 3 retains source-free captured tokens and actual pending publication dependencies through their last use; it adds no value-comparison evidence or whole-original liveness edge. Identity retention never extends unrelated publication. |

Each bounded internal acquisition has one matching release or transfer, implemented at the holder rather than by a mutable operation context or an execution-wide owner registry. Count protection at the retained root; the mutation path carries ancestor protection to descendants without eagerly marking an entire graph.

Container-owned preservation dependencies constrain mutation but are not independent liveness roots. Installed recovery participates in the same maintained dependency graph as placements and backing storage, without becoming an ordinary logical property or a public parent placement. For example, a baseline referring back to its poisoned container must not keep that detached group alive. Keeping a baseline as a root and promising to release it only after its container retires would make that retirement impossible. Prepare the receiving dependency before releasing the previous use, including during repair and copied recovery publication.

A baseline may still be pending: failed replacement captures the old placement without consuming its value. Its owning placement keeps a dependency on that exact version. Settlement establishes the delivered managed value's preservation dependency before later writers can use it, but only while that owning use remains active. Replacement, successful repair, or retirement detaches the use even if settlement has not occurred; a late callback must not recreate it or retain the old destination. Copies and independent captures retain their own obligations. Ending the active dependency does not erase the captured version or recovery state needed for supported re-entry.

Audit and wire these concrete routes:

- `lookupPath`, managed outputs of `run` (including Array and mutation results), `enter` results, and higher-runtime managed-value forwarding carry delivery retention when needed. Initialize internal work before callback-capable production; the release handle is not part of the language return value or immutable operation context.
- Public `import` and `importMethodResult` participate in the same managed-result boundary, including fresh validation copies and borrowed already admitted runtime-owned identities. Imported write protection does not supply a liveness root. Internal import helpers join their enclosing operation and preserve its actual handoff; they are not new outward deliveries. Detached export results, primitive expressions, and Error queries need no managed-result delivery lease merely because they are pending.
- Each input's direct callback establishes protection before generic composition. `collectInputs` and `Promise.all` joining readiness cannot substitute for per-input reception. Async return/adoption and extra `.then` stages must act as receiving/producing boundaries under the integration document's registration table. Generic control-record continuations gain no graph admission.
- Balance synchronous ready completion after internal synchronous delivery acquired retention, as well as synchronous failure, outward success, rejection, and fatal result. Producer closure cannot suppress delivery cleanup; closed consumers cannot admit or lease late inputs.
- Repeated inputs and multiple consumers own independent uses. One operation may retain a value once through several publications; another operation cannot release that hold. Completed ignored results release without a discovery scan. Copied or overwritten pending versions retain their own capture/publication obligations.
- Compiler temporaries clear roots after all uses finish or transfer preservation and required publication. A child argument need not retain unrelated siblings. An earlier argument held across evaluation of another command needs an explicit holder. The integration example's `getData()` result has already crossed import if it came from host code.

Reception prepares fresh assignment inputs before target waits. Calls use the same reception protocol for consumed or provisionally retained inputs, including borrowed descendants inside fresh wrappers. Mutation calls provisionally prepare every explicit argument before receiver-path traversal can change an argument's receiver or ancestor. Observations prepare provisional inputs before waiting for receiver selection. Selected argument processing reuses those prepared outcomes; an already prepared root needs only its completion check and retention. Do not consume raw input again in a separate leasing pass.

Calls keep receiver-first method selection, boundary-specific conversion, and native export. Ready rejected observations leave arguments unconsumed, and a ready controlled observation prepares only its selected input positions. Mutation calls may already have inspected fresh surplus arguments or subscribed to pending roots before dispatch rejects or identifies unused positions; observations waiting for a receiver may do the same. Provisional ownership preparation must not make ultimately unused inputs required waits or contributors to the call's Errors. Transfer each required preparation once to its selected consumer and close unused preparations at selection or failure. Existing installed child settlement retains its independent responsibility. Controlled Array publication records actual destination keys without an argument-list parent; `concat` prepares its source once and reuses captured elements.

Receiver-first selection must also protect the selected receiver before argument preparation can deliver callbacks. Acquire the method description's existing receiver lease before `prepareArguments`, through the common invocation boundary. Argument preparation can remain pending while later commands mutate that receiver; the observation must preserve the receiver it already selected. Keep each method's existing receiver requirement and last-access release point, including mutation routes with separate isolation/publication ownership. This fixes current Array observations without adding per-method protection rules or exporting arguments before dispatch.

Public script-result export uses an existing Chain/path or a result Chain received immediately from the returned value. Internal raw export helpers serve arguments and outward writes. A caller waiting before export starts retains its input. Export copies ready state synchronously and captures exact pending versions, with no blanket identity lease over traversal or final assembly. Error collection and phase 4 identity work can continue after ready source storage is no longer needed. Issue capture before clearing the result holder and deliver only completed detached output.

The queued producer release ends only its hold and can trigger the common metadata-only retirement transition below. It consumes no pending data and releases no other capture. Release invokes no application code. Both pending-delivery release and ready fallback check execution failure before entering a graph transition: after fatality, clear their release-record payloads/context and queued bookkeeping without graph work or a failed guarded entry. This is local reference release, not a failed-execution sweep. At these detached callbacks, catch any fatal propagated by live cleanup after the common guard records/reports it; do not let it escape as an uncaught microtask exception or unhandled observer rejection. Preserve the authoritative execution fatal and pending outward rejection contract.

##### Brief leases for ready outputs

A ready lookup still held by its source needs no new delivery lease. A newly produced or removed ready value can have a different lifetime: `slice` returns a prepared view before its receiving Chain exists, and an ignored result never acquires that Chain parent. A lookup into mutable external state can likewise return a fresh managed snapshot with no source placement; establish its producer hold before the lookup's own graph flush and expose it through the common ready-result boundary. The source-held exemption follows actual retention, not the operation's name. Neither a construction reference nor completed preparation alone proves a retained root.

**Release exposed ready-result holds at the start of the next receiving graph transition.** Establish or transfer the producer's lease before releasing its previous protection or flushing its own graph work. At the common outward boundary, register its clearable release record in a lazy execution-local collection. Queue one fallback microtask for that execution only if none is already queued; the callback services the collection, without capturing individual records or result values. Return the ordinary ready value immediately. Internal results do not enter this collection merely because an internal helper returns; their consuming work retains them explicitly.

The next command opens its graph transition before detaching and releasing the collection of previously exposed ready holds. Releases enqueue retirement candidates inside that transition; they do not flush a separate retirement batch. The consumer then attaches its placement, acquires its own lease, or captures export input before that transition can commit or suspend. Nested graph helpers join the transition and do not expire another set. Records registered by its new producer survive until the following receiving transition or the queued fallback. Entry or language-call finalization is likewise a receiving transition for the callback's returned value, and must establish onward protection before its final flush. A producer's own return boundary is never the next receiving transition.

This rule follows the immediate-handoff contract. Protection must be acquired before the receiving command changes a borrowed source or waits for its target; releasing the old hold does not relax input-capture ordering. Returned values can contain borrowed descendants or be existing identities, so absence of other aliases is not the proof. An intervening unrelated command ends the raw result's supported handoff interval; continued use requires an explicit holder. The same execution's command advances the interval; a different execution does not.

Receiver selection and receiving preparation process available inputs before waiting. Supported subscriptions cannot drain older work into that synchronous transition, so the common reception walk can consume and retain each input in order. Keep protection until destination attachment, independent capture, or failure. Fresh topology stays private until successful preparation; no separate capture pass or result wrapper is needed.

When the fallback runs, clear the queued fact, detach the currently exposed ready collection, and release it in one metadata-only transition if the execution is live; otherwise clear those records under the detached-cleanup rule above. A command that drains the collection does not reset the queued fact: its already scheduled callback remains available for later ready production before it runs. With no remaining records, that callback does no graph work. This bounds queued ready-cleanup callbacks to one per execution instead of one per historical result. A later producer after the callback runs schedules a fresh fallback.

The coalesced fallback may have been queued by an earlier producer. It still runs after synchronous immediate reception has had its opportunity; a ready value must be received before adding an asynchronous forwarding stage. Each record's release remains idempotent, removes only that record, and clears its payload/context immediately. Releasing an old record cannot release a newer record for the same identity; the execution's fallback intentionally drains the current collection rather than representing one producer generation. Failed consumers also end the previous interval, without waiting for fallback. No per-node ready slot, placement/lease/export acknowledgement hook, result wrapper, or subscriber discovery is needed. The collection and one queued fact concern only exposed ready delivery resources, never pending operations, arbitrary owners, or cleanup callbacks for the execution.

Only ready delivery uses this rule. Pending outward-Promise protection remains operation-owned and survives every direct receiving reaction under the existing observer protocol. An internal synchronous delivery that produces a ready public return follows the ready rule; a ready value arriving later through an outward Promise follows the pending rule. Primitive values, Errors, detached exports, and ready lookups independently held by their source need no additional ready hold. Non-delivery retention keeps its actual last-use boundary.

Silently ignored ready results now retire at the next command's commit, or at fallback if no command follows. Ordinary result and Error/completion semantics stay unchanged. Do not add a compiler unused-result argument, payload-suppression path, temporary discard Chain, or separate disposal API. The earlier `resultUsed` proposal and reception-acknowledgement prototype are superseded; no measured independent need justifies their public surface. Pending ignored results keep their existing bounded delivery protocol.

Experiments A and B compare immediate reception and silent discard, including failed consumers, nested producers/helpers, callback-result forwarding, borrowed children, cycles, Array backing, synchronous custom delivery, and independent pending holds on the same identity. Measure owners, copied volume, leases, index work, and queued fallback callbacks/records both within a synchronous turn and after release. Count the transient producer/consumer overlap separately from required aliases and imported protection. Immediate reception must not retire and rebuild the result's relationships, and an actual wait must have an independent consumer hold. Reactivation cannot conceal missing retention, and bounded graph ownership alone does not prove bounded queued cleanup.

#### 2.3 Retirement and relationship lifetime

**Required in this phase.** Removing a parent placement makes its former child a retirement candidate through the common ownership transition. Root replacement, property/element replacement or deletion, and recursive removal of a retired parent's outgoing relationships all use this rule. Ending a lease or capture likewise reconsiders the affected value. Compiler analysis only determines last use and issues ordinary commands; no root-specific cleanup path or separate disposal API is required. Section 4.1 validates the concrete representation and work bounds.

Activation is also a candidate-producing transition. A newly initialized or reactivated container may never receive a parent or lease: a completed input can have outgoing relationships even when its consumer fails before retaining it, leaving no hold to release. Add activated identities to the current batch at common topology publication. At commit, ordinary holders, required internal uses, and outgoing delivery protection determine which survive. Apply the same rule to late preparation into a detached version and completed preparation whose consumer fails. Staged, unpublished construction keeps its existing discard path. Do not manufacture a temporary lease solely to trigger cleanup or add producer-specific disposal. Candidate completeness includes activations, removed dependencies, and ended independent holds.

Retirement removes outgoing parent relationships and unused representation/index state, without deleting language properties from an observable object. The common sequence is: prepare the transition; commit values, structure, and both directions of relationships; release completed holds; process one retirement batch. Finish required fallible storage work before committing its index changes, and expose no intermediate ownership state to retirement. A transient zero during transfer must not retire a value about to receive its destination. Independent captures, unfinished mutations' baselines, producer delivery, and unfinished writers retain their own roots until last access or handoff. Installed recovery is instead a dependency of its owning placement, as specified above; a property subscription alone is not a root. Exposed ready delivery keeps its hold until the next receiving transition or fallback, without discovering consumers or changing the result payload.

A batch spans one uninterrupted synchronous graph transition, including synchronous delivery of the current subscription, nested publication, path reconstruction, and release work. It does not span an explicitly entered language body or a Promise wait. Individual placement helpers finish storage, versions, and reciprocal indexes without callbacks; they enqueue candidates rather than flushing after every edge. Before a trusted body runs, establish all required protection, drain completed work, and suspend nesting so its commands commit independently.

**Lease unpublished working roots.** A completed copy or other prepared working container that an operation still needs must have an ordinary read lease or an existing independent holder before its transition can drain, even while it has no destination parent. Establish that hold at completed construction/publication; one leased root preserves its recorded descendants and cycles. Disconnected working roots need separate holds until connected beneath a retained root. Before those relationships exist, retain the source or captured borrowed inputs through the existing preparation lifetime; leasing an incomplete shell does not protect unrecorded children. Keep incomplete topology staged, without partial incoming publication. Destination attachment or onward retention precedes release of the working hold in the same transition; abandonment releases the hold and uses ordinary retirement. Reuse operation-owned lease/release machinery, not a new kind of parent or a registry of unfinished copies.

Copies attached within one synchronous graph transition need no intermediate working lease. Mutation-path reconstruction and entry capture use this rule; an attached copy is retained by its destination, and unfinished publication has its own writer pin. Keeping a construction read lease until the whole path finishes would force unnecessary COW on later writes to the already attached copy. Mutation outcomes crossing a producer boundary still need their separate receiver-publication hold.

Choose the working container through ordinary COW before acquiring its construction lease. Private initialization and the already selected write use their existing authority; the lease must not cause that work to copy its own copy again. If resumed work needs another ordinary COW decision, it can release only its own temporary hold inside the resumed transition before that decision, restoring required protection before the next callback or suspension. Other holders and leases still constrain the write. Verify the lifetime through common construction/mutation work; add no general lease-bypass flag or special COW predicate.

Publication-only continuations release their captured input after transferring it to the destination. A resumed mutation makes that transfer and releases its own capture before choosing whether to copy the delivered container. Keeping either hold until a later microtask copies the entire pending descent unnecessarily. Continuations forwarding a value through another Promise reaction retain their existing delivery window. The work fixture pairs ready and pending descent at depth/width 1/8, 16/8, and 4/64: unheld runtime-owned paths copy zero placements, while independently held and imported controls still preserve their baselines.

Keep fatal-on-escape guarding separate from this commit boundary:

| Boundary | Retirement responsibility |
| --- | --- |
| Higher-runtime semantic body entered by `runInternalStep`, or resumed by `continueOperation` | The body keeps its fatal guard, but its commands commit and retire separately. A synchronous loop must not accumulate all retired generations until the body returns. |
| Kernel command, resumed graph publication, or queued release | Open or join the current graph transition; finish its complete graph changes and delivery protection before draining. A continuation containing a language body follows the body rule instead. |
| Public `Chain` or `ContextChain` construction | One receiving command covers base initialization, context import/tree setup, and root attachment. Expire previous ready holds once. Synchronous subscriptions remain within this transition; pending inputs establish preservation obligations before returning. |
| Internal Chain creation and import helpers | Base constructors and other internal helpers join the enclosing transition. Current nested sites include private Chain creation in `enter.js` and `path-operation.js`, method-result import in `invocation.js` and `managed-invocation.js`, and context import in `chain.js`. Their guard exits are not independent commit points. |
| Trusted `enter` callback or compiler-controlled language call | Establish selection, gates, and all protection required by enclosing work, then use the common suspension boundary below. Commands in the body get independent transitions. Enclosing finalization resumes graph work after the body returns or settles. |
| Supported thenable subscription, including rejection observation | Only its newly supplied callback may run synchronously, joining the enclosing graph transition. Older callbacks run separately. No subscription suspension or exit check is required. |

Make the boundaries explicit in ownership. Keep public `runInternalStep` and `continueOperation` as fatal/owner guards. Internal graph work uses `runGraphTransition` and `continueGraphTransition`. Ordinary synchronous helpers join the current transition. `runOutsideGraphTransition` is reserved for explicit trusted-body invocation: drain completed graph work, suspend nesting, invoke the body, and restore nesting for finalization. The caller already holds all state it still needs; the helper scans no graph and keeps no suspended candidate/proof set.

Keep suspension at the explicit trusted-body invocation site; supported subscriptions need no separate boundary. Internal graph continuations use the graph continuation helper, including current synchronous delivery. Callback failures unwind through ordinary guards, while pending failures reject their own chains. Body suspension/resumption is not a new receiving command and does not expire ready holds; commands issued inside the body do start their own receiving intervals.

Common construction, operation, and trusted-body boundaries own these rules; commands add no local cleanup policy. Verify unpublished working roots, incomplete staging, ready delivery, nested helpers, and loops inside guarded continuations and entered callbacks. Atomic publication invokes no user callback, temporary nesting never spans a Promise wait, and ready output protection precedes producer retirement.

**Every prepared mutation outcome has two independent uses: receiver publication and result delivery.** Establish the required holds before the producer's transition drains, not in a later normalization or outward-result reaction. This applies both to an isolated native receiver adopted by `managed-invocation.js` and to replacement Arrays and removed-element results produced by `array-invocation.js`. The common trusted outcome boundary protects its known `mutatedValue` and `result` fields; do not admit or traverse the control record itself or add an Array-only lifetime protocol. An existing hold may transfer instead of being duplicated.

Keep the receiver publication hold through normalization and destination commit or failed-publication cleanup. Its borrowed children must remain protected after argument leases end. The result retains its own delivery obligation, including when it aliases the receiver or is independently pending; an unrelated pending result must not extend completed receiver publication. If the result is not yet available, preserve its capture/delivery obligation and acquire the managed-value hold at its producer. Release only the use that has ended on success, failure, superseded publication, or ignored output. Neither graph may retire and reactivate merely because these internal stages run in different reactions.

Assigning `null` to a Chain root removes that root's parent placement; `null` itself has no cleanup significance. Another Chain or live placement retaining the same data prevents its retirement. The same applies when replacing or deleting any nested property or element: cleanup follows loss of ownership, not the command name or location. Once no surviving ownership or independent retention remains, obsolete runtime references must not keep the detached graph alive. Retirement makes otherwise unreachable data eligible for JavaScript GC; it does not promise when collection runs or reclaim data still held by a host reference or required capture. This cleanup is a Phase 2 acceptance condition, not work deferred to a later lifetime phase.

##### Acyclic graphs and cycles

For an unretained node with no incoming placement, remove its outgoing relationships and reconsider affected children. A surviving lease, holder, or required backing dependency stops that cascade. Follow single-parent intermediates too; otherwise dead ancestors remain registered on shared descendants. Temporary arguments, failed inputs, compiler temporaries, concat sources, and discarded COW copies use the same rule. Already initialized children are not automatically live, and fresh input is not assumed private or acyclic.

The existing `chain._state` object supplies the root-holder identity, but current construction admits it as an ordinary record: incoming edges alone cannot identify its root role. Record that retained-holder role in its execution-local metadata when creating a Chain or internal holder, and end it at the holder's actual release boundary. This adds no synthetic parent and no root flag on every managed value. Clearing `holder.value` removes the root edge even if the empty Chain holder remains usable. A cycle with exactly one incoming placement per node and no independently retained member is a safe special case, but the single-parent restriction is unnecessary: multiple internal keys or parents do not make a detached component live.

Internal parents do not keep a detached cycle alive. Parent removal must therefore consider the affected candidate even when its remaining parent count is nonzero; waiting only for zero parents would miss cycles. The criterion is absence of an incoming path from any independently retained root. Thus `root -> P -> A -> B -> A` remains live, as does a cycle with a leased or otherwise retained member, while the same cycle without that incoming path retires. No execution-wide sweep is needed.

Retained holders and pending writers contribute to one per-node `pinCount`. A pin preserves liveness without forcing COW; a read lease also protects the value. Initialize a fresh holder with one pin and release each writer's contribution at its existing publication boundary. Dropping one use never releases another use's pin.

Use one reverse search with batch-local proof records. A record says whether a visited identity has a proven root path and which other visited identities depend on that proof. Record only dependencies actually examined by this search, not another persistent graph.

- Walk incoming dependencies lazily. When examining `parent -> child`, record that proving the parent live also proves the child live. An independent hold proves its identity immediately; propagate that proof through the recorded dependents and stop enumerating parents of each identity as soon as it becomes live.
- Reuse an existing record on revisiting an identity. An unresolved cycle is neither a live proof nor a failure by itself. Recording its dependency without recursing again lets a root found later prove every visited identity that actually has a path from it. A separate unsuccessful branch does not become live merely because the candidate has another live parent.
- After the candidate's recursive search returns, retire its newly discovered identities that remain unproved, as one group. Each exhausted all incoming dependencies: only a proved identity can stop early. Root proofs have propagated through every examined dependency, so the unproved group is incoming-closed and contains no retained root. This also handles dead ancestors encountered before a successful path.

Reuse these records for all candidates and downstream removals in the same callback-free cleanup batch. Retirement removes only dependencies owned by identities proved dead, so it cannot invalidate a proven live path. Clear all proof state before another graph transition or callback can add relationships or release holds. The retained model validates early exit, cycles, dead branches, and batch reuse together; Experiment A still must integrate the same proof with every runtime dependency producer.

Where Array storage retains values under the whole-backing allowance below, the same liveness proof includes those maintained representation dependencies and container-owned recovery. They do not become logical placements or independent roots. An owner registry's strong bookkeeping references alone never prove that its views are live. Absence of logical cycles does not prove an acyclic retirement graph: pushing an Array into itself can produce logical `[[]]` while the physical backing contains itself. Import-time cycle discovery alone cannot certify that later representation dependencies are acyclic.

Independent holds and nodes without incoming dependencies are short cases of this same proof, not separate collectors. Coalesce candidates within one synchronous batch, including a ledger releasing several leases. Bound work and temporary storage to the affected dependency region: create each proof record once, examine each incoming dependency at most once, propagate each recorded proof link at most once, and remove each retiring outgoing relationship once. Scan only the newly discovered records when finishing a search; repeatedly filtering the whole batch map would reintroduce quadratic work. Newly exposed downstream candidates join the same batch. Parent enumeration must support immediate early exit without first allocating all placements. Array owner candidates rejected by bounds or overlays are additional enumeration work and must be counted separately; the abstract proof bound does not hide that cost. This bound does not promise constant-time collection or constant total work across separate source commands; Experiment A separately measures repeated releases below deep live parents. A remaining parent alone is not a liveness proof. Keep proof state local rather than adding a persistent cyclicity cache or adaptive collector.

##### Remove obsolete references; preserve authoritative value state

Retirement removes every obsolete ownership, index, representation, and finished-work reference, not just the retiring node's own incoming-parent field. Suppose `x -> oldParent -> child` and `y -> child`. After clearing `x`, with no independent use of `oldParent`, the live child's incoming relationships must stop referring to `oldParent`. Otherwise that reverse reference keeps the discarded parent and its other children alive even though the metadata table is a WeakMap. Follow the same rule through intermediate ancestors and detached cycles that point to a surviving child.

Audit the actual strong references at their owning mechanisms:

- Remove retired parents from their children's incoming relationships and counter projections. Also drop the retired node's own optional counter state: `parents`, `frontierCount`, `errorCount`, and `cycleCuts`. Detached summaries no longer receive child updates and cannot remain authoritative. Preserve surviving children's indexes. Reactivation leaves retired nodes unindexed until ordinary counter preparation rebuilds the affected region, reusing surviving indexes; preparation completion and logical versions are not reset.
- Remove retired Array owners from active backing registrations and unlink obsolete physical reverse relationships. Preserve authoritative bounds, overlays, captured versions, and forward physical facts needed for supported re-entry; retire only bookkeeping whose removal cannot change that value or its restoration. This includes an imported native Array's own backing record: a physical Promise slot may already have a different settled logical value. Durable state can be collected with its identity once that identity is unreachable. Section 2.3's Array rules define active whole-backing lifetime separately from logical placement retirement.
- In a live execution, release completed lease/capture records, operation-only holders, construction records, and callback-captured state after their last required use. An abandoned continuation must not retain a discarded graph merely because its source Promise remains pending. Remove container-owned recovery dependencies with their owner, preserving independent captures, unfinished publication, and authoritative version state still needed elsewhere; retirement does not cancel shared settlement.

**Completed source capture must also discard its ordinary JavaScript references.** Correct parent indexes and zero lease counts do not make a graph collectible while a placement object, work field, or callback closure still points to it. End source access at the common capture or receiver boundary; do not make the collector inspect operation closures or add a second retention registry. The following changes are required alongside destination detachment:

- In `PropertyPlacement.ensureCaptured`, capture the complete placement/version first, then drop the original owner reference. Subsequent value and presence resolution must use that capture. Keep the owner while the placement is still lazy; remap construction and presence-only inspection must not consume an unused value merely to enable cleanup. Reuse this transition for Array element reads, remaps, and conversion instead of adding per-method owner clearing.
- In `collectFencedErrorWaits`, clear the source parameter after synchronous inspection and capture. Its synchronous inspection closure and pending query callbacks can share a lexical context even when the pending callback does not explicitly read the source. Keep exact pending versions, visited captured-generation identities under section 2.4, and required Error collection. Apply the same source-release rule to `hasError`, `getErrors`, export, and shared traversal; completion or short-circuit closure must not leave an unused source reachable from an unresolved sibling callback.
- End invocation receiver access through the common work boundary, releasing its protection and clearing receiver fields that no remaining stage uses. Controlled algorithms must also stop keeping duplicate local receiver references after their last read. In particular, `at` needs only its captured element after selection, and `includes` needs only captured comparisons after scanning finishes; a match also ends unfinished scanning. Preserve receiver access while bounds, unread placements, native invocation, or required publication still need it. Use existing operation closure for early completion and abandoned branches. Consolidating lease ledgers remains optional; removing spent references is required.
- End invocation input access when selected preparation takes responsibility for the required inputs. Clear spent original-argument references in both `InvocationWork.args` and `run`'s enclosing closure; clearing either alone leaves the other retention path. Pending preparation keeps only inputs/captures it still needs, so a completed export or an unused argument does not remain rooted until another argument or the host result settles. Preserve batch-export alias handling and independent pending input protection. Provisional argument reception can synchronously deliver the receiver and start selected preparation while its own loop is running: keep that active registration's local inputs valid, stop provisional processing when dispatch takes over or work closes, and release the outer references after transfer. Use existing work ownership and release boundaries, not a new input protocol or a sweep of pending Promises.

The optional counter projection also needs reciprocal outgoing facts. An indexed ArrayView can have counter-parent links from its logical children even though its ownership relationships are compressed into backing occurrences. Dropping the view's own counters or unregistering it from the backing does not remove those child-to-view references. Maintain a lazy set of child parent-maps at the existing counter-edge add/remove boundary, deduplicated across repeated placements; remove an entry when its last counter edge disappears. Retirement unlinks the retiring parent from those maps and discards its outgoing set along with its summaries. This is the reverse direction of the existing optional acyclic projection, not another ownership graph or a per-view element index. Only counter-indexed containers pay for it; unindexed view retirement still does not scan a shared prefix. Counter-index construction stages these facts with its existing publication and failure rules.

Export needs a concrete capture change in this phase. Its current pending callbacks retain the source parent to address `copies.get(value)`, after ready source access has finished. Retain output destinations through clearable output-work state and keep only exact pending versions for future source input; do not capture the source parent solely as an output-map key. Address output slots by the captured-generation identity from section 2.4, with shells owned by clearable output work. A weak source-address map alone is insufficient once that address can be reused. Error discovery clears output state while required Error collection continues, so directly closing over an output shell is insufficient too. Clear the source parameter after capture in both export traversal and the common `walkManagedProperties` helper: the latter's synchronous inspection closures can share a context with its pending callbacks, retaining the parameter even when those callbacks do not explicitly read it. Preserve aliases, cycles, key order, and captured shape. Test source collection both during successful pending export and after output discard, with an independently retained pending child, live execution, and removed source root; also test collection of discarded output shells before Error collection completes. Phase 4's no-op identity assembly remains separate; source/output lifetime and generation-safe capture are Phase 2 prerequisites.

Do not implement cleanup as unconditional deletion of the whole metadata record. Preserve admission category, prototype, imported protection, authoritative logical versions, and required publication state for identities that can still be observed or reintroduced. An imported physical property can contain a Promise while its logical version holds a contextualized Error; deleting that overlay changes value and attribution. These facts are part of the identity's semantics, rather than disposable ownership bookkeeping. Keeping them must not also keep obsolete reverse edges or finished-work references.

Execution-local WeakMaps do not root their keys: once an identity is otherwise unreachable, JavaScript can collect it and its remaining metadata together, including internal cycles. Explicitly deleting that metadata is unnecessary for collection. This does not excuse a strong path from a surviving child's metadata, backing registration, or unfinished callback into a retired ancestor; remove each obsolete path at its actual release boundary. Add no finalizer-driven cleanup or execution-wide identity registry.

##### Imported protection and supported re-entry

Imported protection constrains writes; it is not a liveness root or a synthetic parent. Host-owned identities first admitted by import already receive their own protection, including later deliveries through that boundary. Retiring their relationships must preserve that identity fact and authoritative versions. A host may legitimately return the same cached imported graph again, before or after pending settlement. Experiment B verifies reactivation without reclassification, resubscription, or changed Error attribution and measures repeated cached imports.

A managed method may return `this.items` directly or a fresh wrapper containing an already admitted runtime-owned child. Those results use ordinary delivery, placement, and capture protection; imported reception must not reclassify that child or make its temporary use permanent. This does not authorize host retention of an unexported receiver or source after the call's permitted lifetime. A host-retained runtime-owned ArrayView returning after retirement is outside the data contract. Do not introduce a protection-transfer walk, permanent backing protection, host-lifetime tracking, or tests solely to support that scenario. Preserve the supported mixed-input cases from Phase 1 and the active-view storage rule in section 3.

Imported graphs remain in the maintained relationship and cleanup model. Excluding them wholesale would also require accounting for the counter index's reverse references and pending destination lifetimes; it does not automatically eliminate those costs. Retaining obsolete imported graphs until execution end would weaken this phase's cleanup requirement and is not selected. Measure the reactivation cost and retained state together before proposing a narrower indexing strategy.

**Cached logical copies retain imported protection.** Supported cached input can contain runtime-created logical state even when the host never retains a runtime-owned identity. For example, first import host child `C = { k: 1, waiting: promise }`, then receive a host method's cached object `P = { child: C }`. Current method-result admission copies the already admitted pending child for result validation and installs copy `C2` in `P`'s logical overlay. Host storage still contains `C`, while Cascada sees `C2`. This route is implemented in `input-preparations.js`; ordinary cached method re-entry preserves the logical copy. Phase 2 changes the new copy's protection as specified below.

If a second Chain retains `C2` and `P` loses its runtime holder, removing `P -> C2` must not authorize that Chain to overwrite state that `P` will expose on legitimate re-entry. A model using the current copy-admission rule, removing that parent and the old `shared` protection, allowed `C2.k = 2` to change cached re-entry from `1` to `2` while host storage remained `1`. This is a proposed-retirement counterexample, not a defect exposed with current permanent sharing enabled. The witness cannot be dismissed as unsupported host retention: fix the copy's protection rather than rejecting the cached input. Distinguish preserved admission state from a missing consumer hold.

The selected rule is that a fresh validation copy of an imported node inherits the source's imported write protection at admission. Apply it to each copied container during the existing copy-shell commit, before cyclic/aliased relationships publish. Reuse the imported-protection fact; add no cached-owner registry, reverse protection-transfer walk, or separate permanent-sharing flag. A validation copy of a runtime-owned source remains runtime-owned, and an already admitted borrowed child is not reclassified merely because an imported wrapper contains it. Ordinary mutation copies continue to start runtime-owned.

This protection does not make the copy a liveness root or prevent its relationships and counter state from retiring. It conservatively requires COW for a later write even when only one active Chain retains the validation copy. Its logical Promise versions can still settle; ordinary imported-storage rules suppress physical writeback and prevent protected Array storage from becoming mutable backing. It gains no external mutation authority. ##### Version settlement and relationship reactivation

The version owns its captured settlement and causal Error context. Its destination supplies only the authority to update current storage and indexes. Use the existing installed-version check and a detachable destination lifetime for input preparation, construction, copying, and ordinary publication. Retiring a destination removes that authority and its obsolete strong reference; it does not cancel a source Promise or a version retained by another consumer. A live unfinished writer still retains the holder needed for its promised effects. A mere subscription for an abandoned property does not.

Cached-root preparation returns its maintained logical state directly. Receiving placements or leases perform any required reactivation, rather than repeating it in the preparation fast path.

The prototype supports one lazy destination cell per container with pending publication. Construction owns its private destination until publication; published construction and ordinary transfers then refer to the same cell. Retirement clears its owner reference, and legitimate reactivation restores it. A callback keeps the version and cell, never a forward entry that points back to the container. It always settles required version state; it updates live storage only when the cell has an active owner and the existing installed-version check still matches. Reopening the cell therefore cannot authorize an overwritten version. Discarded private construction retains its existing no-destination-work rule. Do not conflate clearing publication authority with closing shared settlement, or allocate a cell for ready-only work that retains no callback.

For example, replacing `x = { child: keptElsewhere, waiting: neverSettles }` with `null` must release the old container in a live execution unless a separate use actually needs it. An earlier capture of `waiting` may continue using its version without keeping `child` or the old container alive. On resumption, settle required version state before local-consumer work, and update relationships only for a currently active destination. This follows the existing shared-settlement ordering and does not create a second cancellation or delivery system.

Preparation completion and active relationship indexing have different lifetimes. Retirement may deactivate outgoing relationships while the identity's prepared logical state, admission, versions, and contextualized Errors remain authoritative. Reception reactivates relationships from that state before publication; it does not clear preparation merely to rerun admission, reconsume thenables, or duplicate subscriptions. Settlements while relationships are inactive must preserve the value for legitimate re-entry without rebuilding a discarded index. Derive activity from the chosen index representation where possible instead of adding overlapping completion flags. Experiment B validates this complete lifecycle.

Reactivation uses maintained forward facts, not a new walk of host properties. Keep the identity's own authoritative outgoing information needed for re-entry while removing its reverse entries from children, counter projections, and backing owner sets. An entry whose value or presence can settle refers to the captured version rather than a frozen child snapshot. Such versions settle without a strong reference back to a retired destination; re-entry reads their current logical state and restores only currently applicable relationships. Preserve Array bounds, overlays, and required recovery state through the same representation. These forward facts must contain no obsolete operation, callback, or destination ownership. Reuse the selected outgoing representation rather than maintaining a second reactivation graph.

Relationship reactivation performs no host reflection or subscription and visits only the inactive region and relationships being restored, stopping at already active descendants. Counter construction remains separate: a query or publication into an indexed parent can require it at its existing fallible boundary. Existing method-result validation keeps its own required inspection too; the no-reflection rule applies to restoring relationships, not to unrelated boundary obligations. Experiment B must measure repeated cached re-entry against this bound. If its allocation or repeated-use cost remains material, discuss a narrower imported-data strategy; do not silently keep reverse references until execution end or weaken cached-value semantics.

**Phase 2 restores retired inputs through ordinary reception.** Cached-root reception restores and transfers within one graph transition, without an intermediate lease. Longer preparation retains borrowed restored input under an ordinary lease, even if a later sibling fails inspection. Restoration uses forward records without host reflection or resubscription and stops at active descendants. Release that preparation lease on success or failure; normal retirement removes the restored region unless a surviving holder needs it. Fresh admission, copies, versions, and topology still publish only after successful validation. This removes the separate inactive-frontier retention walk and its pending observers. Failed and ignored cached inputs can pay for restoration followed by retirement; this is an accepted cost.

**Lazy reactivation experiment: completed and rejected.** Deferring restoration from ordinary lease acquisition loses protection below an inactive cached root. In the retained regression, a retired imported wrapper contains an already admitted runtime-owned child; the wrapper is passed to a call waiting for its receiver, then another Chain mutates the child. The current implementation returns the captured `k: 1`; the prototype returns `k: 2`, for both record and Array wrappers. A root lease cannot protect a descendant without the connecting relationships. Restoring a separate borrowed frontier or maintaining a second inactive-retention mode would duplicate the ownership mechanism. Keep ordinary restoration on reception/retention; silently ignored cached results still pay restoration and retirement work proportional to their inactive region. This optimization trial is closed without changing the ownership contract.

Preserve the existing fatal-execution lifecycle. Outward result boundaries release their own delivery holds on fatal rejection, but a fatal does not sweep internal owners, settle dependencies, or cancel host Promises. Phase 2 does not guarantee reclamation of all state captured by a host Promise that never settles after execution failure. This exception does not weaken retirement of abandoned destinations in a live execution or authorize retaining finished operation state after its normal release point.

##### Outgoing relationships and Array backing lifetime

Incoming placements alone cannot enumerate a retiring parent's children. Maintain callback-free outgoing facts through the same placement transitions as incoming facts; cleanup must not reflect on arbitrary host/Proxy storage, consume Promises, or build optional refcounts to discover children. Ordinary containers supply managed outgoing placements; an Array backing supplies physical occurrences once; views supply bounds and overlays. Experiment A compares shared placement records with reciprocal compact indexes, including memory cost and retirement work. Commands must not maintain an independent cleanup graph. For an ArrayView, retiring an owner removes only its logical range/overlay participation. A lease or unfinished operation that still needs the owner's backing storage prevents that owner from retiring, even after its last Chain placement disappears. Keep all active runtime physical storage access attached to such a registered logical owner, including the original Array's projection; the backing needs no separate registry of leases or captured ranges. A captured value or property version that can be consumed independently of physical storage does not keep its former view registered merely because it originated there. Expansion must continue to exclude out-of-range and masked occurrences.

This permits physical child-to-backing occurrences to remain without treating excluded slots as logical placements. When no registered logical owners remain, remove all physical child-to-backing occurrences and active backing registrations. No active runtime storage use may outlive its owner registration. The discarded backing need not be resized to zero to become collectible. Removing owners must not rescan their shared prefix or materialize each retiring view.

These are implementation design obligations. Keep the surface small: publication supplies changed placements, retention supplies ended uses, and representation code supplies maintained dependencies. One retirement transition owns proof and removal; individual commands add no separate cleanup policy.

#### 2.4 Captured identity when storage is reused

Releasing source storage after capture permits another operation to reuse its JavaScript address while the earlier traversal or comparison remains pending. The earlier captured value and a later value at that address are different generations. Export caches, query visited sets, conversion ancestry, and retained search identities must distinguish them without keeping finished source storage leased until the whole operation ends. This foundation belongs in Phase 2; Phase 3 adds settled publication decisions and Phase 4 uses those decisions to deduplicate output objects.

Capture an execution-local opaque generation identity together with values, structure, and pending versions. Repeated capture before a new mutation view uses the same identity. A newly exposed mutation view receives a new capture identity, whether its working storage was copied or reused; looking up current metadata later cannot reinterpret an old capture. The token must not retain its source container or an unbounded history. Preserve it across retirement and supported re-entry when the logical generation is unchanged; representation-only replacement may preserve it only where value equivalence is already established.

Generation change follows logical mutation, including affected ancestors on the recorded mutation path when their descendants are mutated in place. Rotating only the edited leaf leaves cached ancestor exports stale. Cover controlled writes and Array structure, receiver publication, entry views, repair, and recovery at their common mutation/publication boundaries. Establish the next capture identity before exposing a later mutation view, including a pending gate; waiting until its effective outcome is known would let a later capture reuse the earlier cache entry. Ordinary settlement completes the version and mutation view already captured; it is not by itself another source mutation. Metadata writes, counter updates, and physical settlement writeback must not invent new generations. Experiment C selects the concrete capture/advance representation and checks pending and overlapping publication before it becomes authoritative.

Phase 2 conservatively gives a newly exposed controlled mutation view a new generation even for a same-value assignment; it does not compare contents to suppress that advance. Same-value assignment remains effective under the selected write-based contract; protection-only advances still require Phase 3 integration. A route already known to have no effect before exposing a mutation view, such as direct deletion of an absent property, preserves its generation. An attempted command alone therefore does not advance identity, and linking a captured right-hand value into a destination does not advance that value's own generation. Add no activity counters or copy/source equality proof here. Phase 3 distinguishes actual publication from protection, including validation-copy producers, and integrates identity searches; Phase 4 completes the remaining assembly consumers through the same decisions.

For example, deleting `root.missing` preserves the root's generation when absence is known at that target. Deleting `root.b.missing` may already have opened mutation views and copied ancestors before discovering absence. Phase 2 does not undo those advances or add a preflight path walk. Phases 3 and 4 own protection-copy identity inheritance and consumer integration; physical reuse is outside the selected design.

Use that one capture surface where an operation remembers a value across later work:

- Export caches key output shells by captured generation, preserving aliases and cycles within that generation while allowing a later generation at the same address to produce different output.
- `hasError`, `getErrors`, and shared traversal remember visited captured generations. A later generation must still be inspected, including when it introduces an Error. These consumers do not wait for Phase 3's pending publication decisions.
- Array conversion and recursive Array traversal record captured ancestry, not just source addresses. Audit `hasArrayAncestor` and every caller, including nested conversion: reuse of an address must not look like recursion into the earlier captured Array. Genuine cycles must still terminate.
- `includes`, `indexOf`, and `lastIndexOf` capture the managed needle's generation when consuming the needle, and each managed candidate's generation when consuming that candidate. Capture identity before a later callback or source write, not when the final comparison resumes. Compare those captured identities while preserving each method's primitive equality, ranges, holes, short-circuiting, and Error behavior. An identity-only comparison needs neither a recursive value snapshot nor retention of the source graph after identity capture. Do not wait for unrelated descendant values or introduce Phase 3's pending publication decisions here. Phase 3 later extends the same search surface with equivalence resolution; basic storage-reuse correctness cannot wait for it.

Current placement, backing, and counter indexes continue to describe live nodes and locations; do not indiscriminately replace their keys with generation tokens. The new rule concerns retained observations of logical values. Source access ends only after both data and required identity have been captured. No consumer may repair a stale cache by rereading released storage, keeping a blanket traversal lease, or comparing complete graphs afterward.

### 3. One COW decision using those facts

Keep `requiresCopyOnWrite` as the internal ownership decision. The caller must establish ownership through its selected placement or retain its captured value through descent. A queued writer releases its capture lease before descent only after publication into its still-live destination; a displaced writer retains that protection until its walk has preserved the value. An unrelated sole parent is never evidence that the writer owns the value. The decision answers whether this access requires preservation; it is not `getParentPlacements(node).length > 1`.

For an ordinary controlled path, inspect local protections and the known path from its holder. Imported storage, outstanding retained uses, container-owned preservation dependencies such as installed recovery, and protection inherited from an ancestor require preservation. A baseline retained by another placement cannot appear exclusive merely because only one Chain has a logical parent entry for it. Another incoming placement prevents proving exclusive use of that node through the selected placement. When ancestors are copied, register their reused children before relying on the children's new ownership facts. Private construction and a completely isolated native receiver retain their established ability to update their own working graph, including its internal aliases.

Simple cases should finish using local facts. Ambiguous aliases or cycles may conservatively require copying; do not traverse unrelated ancestors or descendants to prove an optimization. No parent-count shortcut may change alias behavior, bypass a mutation baseline, or overwrite a captured generation. Ownership permission remains separate from storage writability and representation requirements, which continue through ordinary materialization.

Logical-node ownership alone cannot authorize physical Array writes. An original native Array and its slice can each have one root parent while sharing storage; the current materialization check permits the original Array to remain in place when its logical and physical lengths match. Before Phase 2, `markShared(backing)` supplied that protection. Replace that responsibility with an Array storage-preservation check beneath the common COW decision, using the existing backing-owner registry and host-storage protection.

Conservatively copy/materialize ordinary indexed assignment or deletion within existing storage when another registered logical owner remains, including primitive elements and creation in holes. An optional settlement writeback keeps its authoritative overlay when that storage cannot be reused. Preserve the existing safe-extension path beyond all preserved bounds on runtime-owned backing; ordinary ownership, version authority, and storage-writability rules still apply. Imported storage remains protected independently of owner counts and never becomes mutable backing. Removing the last other owner can restore storage eligibility where those other rules permit it. Do not add another owner count, per-element lease, or command-specific sharing path.

Apply storage permission to every route that actually writes shared physical storage, not every method classified as mutating. Current `sort`, `reverse`, `fill`, `splice`, `copyWithin`, `shift`, and `unshift` use a remap and publish a replacement Array; they already preserve earlier views without backing `shared` protection. Keep that common replacement path and test it during migration. Any future in-place implementation must use the same storage permission; add no redundant copy or per-method check to the existing replacement path.

Ordinary native-owner Promise settlement can update its optional physical cache without another owner scan: derived owners already capture that pending placement in their own overlays, and a new mutation checks storage isolation before installing its version. Distinct views still publish only to their overlays. Imported backing is excluded when storage sharing is created, so the sole-owner representation check does not repeat that exclusion.

Reuse phase 1's parent expansion internally with early exit when another relevant placement is found. `getParentPlacements` keeps its snapshot contract for consumers that need all locations; the COW predicate need not allocate that snapshot. There must be one implementation of Array offsets, bounds, and overlay masking beneath both consumers. Add no cached owner total until a demonstrated cost justifies its invalidation protocol.

Protection must be established before publication exposes a value to later writers. A pending capture therefore retains an obligation before its value is available; settlement attaches the required protection to the delivered identity before consumers resume. Shared settlement and surviving captures continue after one local consumer closes. Release is synchronous, idempotent, and non-throwing, with no host reflection, pending-value consumption, or cancellation of gates or source Promises.

### 4. Encapsulation and implementation sequence

Use a small ownership module beside parent relations. Its responsibilities are counted retention, retirement after established releases, and the COW predicate. Common managed-value result boundaries carry producer delivery retention and install the outward cleanup observer; common receiving boundaries establish independent consumer protection. Parent relations continue to describe placements; Array code continues to own backing expansion. Existing operation owners and resource-release hooks carry operation-specific lifetimes. Captured generation identity belongs with logical value metadata and common mutation/publication, behind one opaque capture/advance surface. Individual commands do not schedule delivery cleanup, discover capture records, manage sharing Booleans, interpret raw parent-map sizes, or maintain identity caches of their own.

**Completed experiment: retain pending-writer pins.** Removing both writer contributions passed the existing 2,573-test instrumented suite, the 288-case mutation lifecycle fixture, its 112 inspection-failure cases, and the existing work checks. 1. A managed root has `items: [{ k: 1 }]` and a pending property that will resolve to that same root. Another Chain retains the item.
2. Issue `pop()` through `root.pending.items`, receiving its result in a Chain, then remove the source root or its containing placement.
3. Mutate the surviving item's alias to `{ k: 2 }`, then deliver the pending cycle.

The pin preserves relationships that unfinished work can still reach, not merely the destination's storage. ## Phase 3: Establish write-based identity and searches

**Status: implemented; review corrections are tracked in section 6.** Command publication and the necessary Phase 4 consumers landed together. ### 1. Selected contract

A command is effective when it makes a semantic publication. Equal contents do not suppress that effect. Starting with `v.k === 1`, `v.k = 1` separates the affected managed identity from a retained earlier version. Writing `2` and then `1` also leaves it distinct. The accepted consequence is that same-value writes separate aliases in searches, exports, and prepared native receivers. This is the selected behavior, not an optimization tradeoff to revisit.

Only a command that publishes nothing is a no-op. Copies made solely for protection, observation, or representation inherit their captured source identity. Fresh language results remain fresh. Linking a managed right-hand value into a placement changes the destination and affected ancestors, not the right-hand value's own identity.

| Command or transition | Identity consequence |
| --- | --- |
| Assignment to a placement, including an equal scalar, the same managed reference, or an equal Array length | Effective when published. No comparison with the old value. |
| Deletion of a present placement, including one containing `undefined` | Effective when deletion is published. |
| Deletion of an absent placement or Array hole | No-op if no other scope effect is published. |
| Repair of healthy data | No-op. |
| Repair that restores a poisoned placement, presence, or recovery state | Effective when restoration is published. |
| Failed operation | Classify the actual publication: committed poison is effective; an independent result Error with no publication is not. |
| Controlled Array mutation | Effective if its logical operation writes any placement or structural state, even if all written values equal the previous values. |
| Entry | Preserve the publications of its contained commands. Empty entry and entry containing only nonpublishing commands are no-ops. Effective commands cannot cancel by restoring entry's initial contents. |
| Protection, gates, representation copying, index maintenance | No semantic publication by themselves; preserve captured identity. |
| Settlement of an already captured Promise-backed placement | Completes that version; does not invent another command or another identity split. |

Publication means the language command's committed placement/scope/structural effect, not every JavaScript write used to build storage. An assignment of pending data normally publishes that pending version immediately and is already effective. It does not wait for the old or new value to determine equality. A validation or gate that actually delays publication retains the existing ordered completion requirement.

Array classification comes from the operation's logical write footprint, never a comparison of completed contents or backing maps. An empty `fill` range, zero-count `copyWithin`, or `reverse` with fewer than two elements writes nothing. A nonempty `fill` with equal values, `copyWithin` of present positions onto themselves, and reversing two equal present elements write and are effective. A sorted Array is not automatically a no-op: writes performed by `sort` count. Representation remapping alone is not an extra semantic write. Explicit structural assignments count even when equal; an empty operation that makes no structural publication does not acquire one merely because its implementation allocates a view.

The complete Array write rule is based on the logical algorithm, not host storage optimizations:

| Controlled mutator | Publishes on successful execution when... |
| --- | --- |
| `fill` | The normalized target range is nonempty. |
| `reverse` | At least one mirrored pair contains a present index. A lone middle element and pairs of two holes cause no write. |
| `copyWithin` | The normalized count is positive and at least one relevant source/destination position is present. A write of the same value counts; deletion of an already absent position does not. |
| `sort` | At least one element is present, including a singleton. An all-hole Array performs only absent deletions. |
| `push`, `unshift`, `pop`, `shift`, `splice` | Always: these algorithms explicitly write length, including equal length on an empty/zero-item operation. |

Use already prepared bounds and placement presence. The remap path derives the fact during its required work; view shortcuts supply the same fact from the method definition. Add no Proxy around production Arrays and no second value walk. Ordinary validation, consumed arguments, callback order, failure publication, and independent results still run as required. Observation-mode results remain fresh even if the corresponding mutator would publish nothing.

**Selected simplification: a nonwriting Array mutation reuses its baseline outcome.** After required preparation establishes zero writes, return the captured receiver and its receiver-returning result without constructing a replacement Array. The scope coordinator maps that outcome to its captured baseline placement, using the same preservation rule as healthy repair. A pending gate may still need to transfer that placement to finish publication; reuse is not permission to skip gate completion. Explicit length-writing mutators and singleton sort remain effective. Observation-mode calls still produce fresh results. If presence is still undecided, publish the remapped representation immediately and settle its identity contribution separately; a possible no-op must not block unrelated value access. Do not undo path protection already performed or substitute old storage afterward.

This eliminates unnecessary receiver materialization, topology construction, and replacement publication for these cases. It adds no second footprint scan: empty bounds can decide immediately; presence-dependent cases reuse required remap/presence work. Required argument validation, reads, and Error processing still precede the outcome. Repair-and-call may restore poison even when its Array call writes nothing, and final storage failure may publish poison; the scope coordinator, not the Array footprint alone, decides the command's actual publication. Receiver/result retention remains separate from that decision.

The compact model checks 98,252 small sparse-Array/selected-bound combinations against native store/deletion observation, including 72,741 zero-write outcomes. Every zero-write outcome preserves complete Array contents and the mutator returns its receiver. The singleton-sort engine exception below is excluded only from physical-store equality. This establishes the reuse rule at the algorithm boundary, not production allocation or scope integration. Implementation acceptance must cover pending arguments and receiver placements, views, explicit wider scopes, failed publication, repair-and-call, unused never-settling payloads, and unchanged earlier captures; count receiver allocations to confirm that no replacement is constructed.

The [standard Array algorithms](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-properties-of-the-array-prototype-object) define these logical writes. The host probe agrees on the retained multi-element/length cases, but Node 24's native singleton `sort` skips its physical store. Cascada already controls sorting; its contract follows the specified logical write, not that engine shortcut. The public singleton witness pins the distinction.

A successful native mutating call publishes every managed node in its adopted receiver graph, including apparently untouched descendants, and separates the affected path ancestors. The runtime cannot observe the method's individual writes: a native method that writes nothing still publishes its complete isolated receiver. Preserve aliases and cycles within that new graph. Protection copies in unrelated branches inherit identity; ancestors containing the published receiver do not. Failure follows the actual poison/fallback publication rule. External identities remain opaque under their existing authority rules. No before/after comparison, Proxy instrumentation, or native subtree-preservation follow-up is required.

### 2. Publication owns identity

`src/captured-identity.js` supplies capture, inheritance, publication, comparison, and completion of captured identities. Keys contain no source storage. Exact object leaves also use execution-local keys for comparison, so identity processing never probes a host object; export still preserves those leaves exactly.

`IdentityPublication` belongs to existing path/gate work. A ready path collects affected metadata at its reached occurrences. Before suspension it replaces those references with source-free predecessor/future pairs. A committed write settles each future as fresh; no publication forwards it to its predecessor. Ready no-ops allocate no pending cells or listeners; ready writes allocate their fresh key only when captured. Later completion changes its captured future, never a later generation installed on the same container.

The command producer supplies its write contribution in the mutation outcome. `transformProperty` decides the actual effect after transfer, restoration, or fallback. An independent result Error cannot determine that effect. A successful repair accompanying a nonwriting Array call still publishes; failed restoration that preserves the original poison/recovery does not. Failed publication uses the actual fallback destination, including a newly copied parent. Generic copying, Promise settlement and index maintenance do not report semantic writes.

Private scope work aggregates contained contributions. Each child registers with its enclosing publication at issuance, before an entry callback can return. One count records unfinished contributions; completed children leave only the publication bit. A separately returned nested entry can therefore keep enclosing identity pending without extending ordinary value publication. Closing and descendant completion drain upward in a synchronous loop, with no rolling Promise joins or completed-child history. Entry reserves ancestor futures while its private value keeps the captured prefix. Contained commands use ordinary publication; entry delivers their final value without creating a second identity for it. An earlier sibling's completion cannot overwrite a later sibling's generation. Optional discovery failure drops abandoned descendant captures before selecting its enclosing placement.

#### Integration experiment: publication completion

**Accepted in production.** Scope transfer/restoration/fallback, direct writes, failed prefixes, Array outcomes and entry completion supply the effect at their existing boundaries. Identity finishes before gate delivery. A resumed path must finish a ready effect inside the source-version transition, not one Promise reaction later; the stacked-command oracle exposed and now covers that ordering.

Array presence can leave an identity-only effect pending after value publication. Presence resolution continues as shared work even if the initiating call or a comparison closes. One local publication accumulator consumes presence contributions and also owns the output identity decision. One known write settles that decision without waiting for other undecided presences; otherwise all contributions must finish as nonpublishing. The destination accepts the producer decision only after its actual transfer/restoration/fallback classification. There is no extra command owner, registry, value scan, or scheduler. The original proposal to avoid every new completion count was rejected: data readiness cannot derive completion of independent contained publications. One identity-contribution count is the narrow authoritative fact, separate from value and result completion. It lets completed siblings release immediately behind an unfinished child; an established write settles the enclosing identity without awaiting irrelevant remaining contributions.

#### Integration experiment: captured-path propagation

**Accepted.** Reached mutation-path occurrences and enclosing entry dependencies cover the affected ancestors. The old recursive `advanceIdentity` parent walk is removed; the complete parent index remains authoritative for ownership. Repeated cyclic path occurrences remain separate contributions. Failure-only reconstruction captures the actual copied parent; assignment changes its destination ancestors, never its right-hand value.

Public tests cover protected and unprotected paths, aliases/cycles, nested/overlapping entries, failed discovery, poison/recovery, same-value writes, pending presence, source release and later generations. The production work fixture bounds identity captures by path length; it does not rediscover affected ancestors through a graph scan.

#### Integration experiment: validation-copy completion

**Historical experiment, closed with the fresh-identity fallback.** The approved Phase 4 preservation revision now replaces this mechanism; its production cutover remains pending. The producer audit found that `prepareInput` discards its staging parent graph after commit, while pending deliveries continue independently through committed versions. Those versions supply data/validation completion, but do not retain a complete unchanged-versus-replaced identity contribution for every copied ancestor across aliases and cycles. Inheriting before removing that revalidation would expose equality before a possible replacement.

Keep fresh settled identities for validation-copy containers through the common identity surface. Preserve their internal aliases/cycles, unchanged shared branches, source isolation, required Errors, retirement and ordinary version completion. No speculative inheritance, retained staging graph, strategy switch, or second identity subsystem is added. This can falsely distinguish unchanged copies, but cannot falsely equate different values. N2's strict expectations are unchanged.

### 3. Small alias representation and lineage-aware comparisons

Cells have named numeric pending, settled and forwarding states. A settled representative never moves and is itself the stable key. Pending representatives keep a class size and live query registrations. Every cell also carries one immutable lineage reference. A fresh settled cell names its own lineage; pending successors inherit it. Forwarding stays within a lineage. The tag retains only one source-free settled cell, never a predecessor chain. Forwarding cells retain their representative link and lineage, but no source, producer, previous value, size or registrations.

Weighted union joins pending classes; iterative path compression shortens later access. Forwarding to a settled identity always selects that representative. Move only the losing class's registrations, updating their endpoints. Deliver a query when its endpoints join or an endpoint settles, without waking and resubscribing every comparison along command history. A transition-local loop clears deliveries as it drains them.

Comparison has three rules:

1. Equal representatives are equal, including a shared pending identity.
2. Distinct endpoints are unequal if either is primitive, their lineages differ, or both identity representatives are settled.
3. Otherwise wait on the unresolved endpoints.

Primitive equality follows the search method's rule, including SameValueZero for `includes`. These rules apply to available values; waiting for a value that could itself be primitive or an object remains necessary. Primitive-versus-object and different-lineage decisions are synchronous, including in streaming cycle checks.

Queries release their endpoints and registrations on result or local-owner closure. `includes` can close losing comparisons on a known match; ordered searches preserve index precedence. Streaming cycle checks use the same comparison mechanism. Physical-representation inspection and live graph indexes do not wait for canonical identity.

For `T` allocated cells and `R` registrations, pending forwarding depth and moves per registration are bounded by `O(log T)`; a settled target adds at most one terminal hop. Conservative total work for `K` identity operations is `O((K + R) log T)`, excluding ordinary resumed operation work. A query receives at most two endpoint-settlement deliveries or an equality completion. An idle captured reference can retain logarithmically many source-free redirects until normalization; no eager member registry or GC-driven pruning is needed.

The production fixture checks reverse and balanced completion through 8,192 generations, 1,024 abandoned comparisons, collection of an old source while its comparison remains pending, synchronous completion through 8,192 nested publications, and collection of 1,024 completed siblings behind an unfinished contribution. Reverse completion moves 16,383 registrations; balanced completion moves 61,440. Both deliver 16,384 initial/final notifications for 8,192 queries. No comparison reconstructs history.

#### Progress invariant and work bound

A successful preparation segment initializes each newly traversed managed container once, after installing all of its pending-delivery obligations. Its identity map bounds cycles within the segment. Later result traversal stops at prepared containers, and each raw pending placement has one owning delivery chain that prepares newly revealed data; several placements containing the same Promise still have separate obligations. Existing versions retain their producer instead of spawning another validation. Retirement restores relationships without clearing the preparation fact.

For finite inputs and finitely many deliveries, successful preparation is therefore bounded by newly initialized containers **and their visited placements/edges**, plus reception and delivery work. A failed segment publishes no fresh preparation, discards its callbacks' authority and cannot retry itself; a new reception, including a separately owned delivery, can retry failed input, with that attempt's work charged separately. This is a preparation bound, not a bound on all receiver/export, COW, retention or relationship-restoration work.

Instrument successful initialization and preparation entry in generated fixtures: no managed container is re-prepared after a successful initialization in that execution, and preparation never installs a second owning delivery for an authoritative version. Count failed attempts, raw subscriptions and ordinary destination transfers separately. Include admitted-but-unprepared producer routes, control overlays, retirement/re-entry and repeated returns around a small graph; use test instrumentation, not a production registry.

Check stable boundaries after an atomic construction batch, and preserve original producer/policy/context when a second holder receives the graph. ### Investigation outcome: repeated validation through a late back-reference (2026-10-17)

**The current fresh-segment path can unfold a finite graph indefinitely. The minimal cached-wrapper witness uses two host containers and one ordinary Promise. Neither host container is mutated after admission; later fulfillment supplies only an inert reference to the wrapper:

```js
const ctx = { execution: new r.Execution(), errorContext: "N2 back-reference" }
const pending = Promise.withResolvers()
const child = { p: pending.promise }
const source = new r.Chain(r.import(child, ctx), ctx)
const wrapper = { child }
const result = new r.Chain(r.importMethodResult(wrapper, ctx), ctx)
pending.resolve(wrapper)
```

The source Chain retains the imported child. Result validation copies that pending child to `C1` and installs `wrapper.child -> C1` in the wrapper's logical overlay; the host property still contains the original child. This cached logical-copy route is supported. No host mutation, forged runtime record, or direct host-Promise self-wait is involved.

The borrowed-version trace is:

1. Ordinary source settlement publishes the wrapper into the original child's `p` version.
2. Delivery to `C1.p` enters `prepareInput(wrapper)` before committing `C1.p`.
3. That segment follows the wrapper's logical child to `C1`. Its `p` version is still pending, so preparation creates `C2`, copies the wrapper to `W1`, and registers `C2.p` on the unfinished `C1.p` version.
4. The segment returns immediately; `commitPromiseVersion` publishes `C1.p -> W1`, where `W1.child -> C2`. The next callback can now consume that publication.
5. Delivery to `C2.p` validates `W1`, encounters its own still-pending destination through `W1.child`, and repeats with `C3` and `W2`.

Each publication finishes independently of identity; the trace is repeated forward discovery rather than a fixed verdict deadlock. Waiting for the new segment's complete verdict before step 4 would instead introduce a mixed cycle: the new segment borrows the version whose publication that wait would prevent. This diagnosis explains the retired validation-completion proposal. The approved replacement stops revalidation at prepared managed references instead.

## Phase 8: Cut Cascada over to the execution Error architecture
