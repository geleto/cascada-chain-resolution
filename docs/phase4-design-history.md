### Contract decision: reusing already-prepared method results

**Approved architecture revision, 2026-10-17; implemented.** Prepare new data, preserve existing managed values, and export detached copies when native code needs to use managed data. A method return does not certify or sanitize an existing graph for that call. The authoritative [method-result contract](data-limitations.md#method-results) and shared architecture documents describe the implemented behavior.

- New or not-yet-prepared managed containers receive ordinary atomic preparation, including result restrictions on newly reached values and owned pending deliveries. Admission alone is insufficient: `placementsInitialized` records established graph preparation and delivery obligations, not readiness or absence of Errors.
- At a prepared managed reference in the same execution, retain its captured logical value, identity, origin and pending obligations through ordinary reception, leases, versions and COW. Stop result-specific traversal there. This applies to roots, descendants of fresh wrappers and later deliveries; each existing property keeps its original producer and causal context.
- Keep direct Error/capability checks and the exact-receiver check for calls inside mutable external state before this stop. Fresh result data keeps these checks during its required walk. Preserve existing poison; an inert registered-resource reference inside a reused graph is not newly replaced by an Error. Authority, direct extraction, native receiver preparation and outbound export still enforce their own restrictions.
- Export continues to consume its required graph, collect Errors, resolve identities and detach managed storage. Exported argument copies returned as data are new inputs, not an identity round trip. Native mutation receiver validation/publication remains separate because host code actually changed its private working graph. Mutable-external property snapshots keep their existing ready-data and ownership rules.
- This changes observable diagnostics: reused interiors receive no call-specific capability replacement or repeated result-admission reflection, and are not searched for this call's exact external receiver. Errors and mutation-scope poison caused solely by that revalidation disappear. A registered-resource alias remains unusable off-path and unexportable. An unregistered mutable receiver hidden inside an existing graph is not reconstructed by those checks; exposing aliases to receiver-owned mutable state remains a prohibited host behavior, without a new registry or scan.
- Required Error collection, publication/recovery, source isolation, causal attribution and resource last-use rules remain. A failed managed receiver combines its failure with Errors encountered by the result's required fresh preparation. It adds no walk into reused interiors to collect Errors from a discarded result and does not await independent nested result Promises. Queries, export and native receiver preparation retain the complete collection required by their own consumption.

For example, an already-managed `{ value: pending }` returned unchanged retains source identity. If the original pending producer later stores an inert registered resource, neither source nor returned graph gains poison solely from the return: `hasError` remains false, while off-path use reports `ExternalLocationConflict` for a healthy binding and export rejects the alias with `ExternalCapabilityEscape`. A newly supplied forbidden result reference still fails result admission. Reception history is observable: ordinary import can establish a reusable graph that fresh method-result admission would reject; a failed segment establishes nothing, so repeated failed returns do not prepare the object. Managed does not mean ready, Error-free or exportable.

#### Receiver finalization correction: 2026-10-18

Review reproduced a missing producer check. A managed mutation can create `fresh = { resource: supply() }`, store it in `this.x` and return it. Current `validateReceiver` marks that graph prepared without rejecting its registered resource. The preservation stop then skips result validation; returning the same fresh graph without storing it still fails. Even production can publish the invalid receiver and attribute its first rejection to an unrelated later call. Finalization must enforce the already documented prohibition on registered mutable identities in a managed mutation receiver. No admission history, result-first workaround or second graph walk is needed.

Check every reached registered identity during the existing finalization walk, including identities inside introduced prepared references. Continue collecting other accessible receiver Errors. On failure, discard the working receiver and poison the introducing call's scope with its receiver failure; repair restores the baseline. A result-only forbidden reference still fails independently without rolling back a valid mutation. Later calls preserve the original scope Error; a compound first result may additionally contain result-only failures, so do not require those two results to be identical in that case.

**Keep initialization conditional on successful validation.** Retirement removes reverse relationships; it does not revoke `placementsInitialized`. A failed method can store a fresh `{ later: pending }` whose category was admitted during validation. If failure nevertheless initializes that child, a later method-result admission skips its raw pending slot; delivery of a registered capability then escapes result validation. The public regression in [managed-invocation.test.js](../test/managed-invocation.test.js) requires the later admission's `ExternalCapabilityEscape` and causal context. Removing the success guard fails this witness. The guard is not redundant cleanup, even if orphaned edges retire correctly.

The evaluation also found a last-use gap: an unformatted finalization Error could retain the discarded working receiver while an independent result property stayed pending. Clear the completed validation walk's captured visited/entry/Error collections, and drop spent receiver/work/result captures in terminal invocation continuations after result retention and outcome construction. The validation function's uncaptured receiver parameter needs no explicit clear. Required direct-Promise work, publication outcomes and rollback baselines keep their own lifetimes. The focused GC witness fails if either validation scratch cleanup or invocation-capture cleanup is removed; both local releases suffice without a new lifetime mechanism.

**Further whole-surface finding:** cleaning only `complete()` leaves `failed()`'s direct rejection route retaining the working receiver. The [terminal release witness](../test/fixtures/terminal-release.mjs) crosses observation/mutation with ready Error, throw, native-Promise Error/rejection and ordered-thenable Error/rejection. Production retains discarded mutation receivers in four forms; the earlier combined prototype still retains both rejection forms. Route rejection through causal poison normalization into `complete()`, whose Error branch creates the failure outcome without calling back into `failed()`. Its single terminal `finally` then covers both lanes. All twelve cases pass, including a control requiring the mutation receiver to remain alive before direct settlement. This preserves behavior without adding cancellation or weakening receiver lifetime.

#### Boundary-lifetime correction: 2026-10-18

The second review reproduced external-call and completed-property retention through unformatted Errors, and a fresh-host-Error control found another shared action capture. Implement these at their existing last-use boundaries:

- In [ExternalAccess.call](../src/external-access.js), put synchronous receiver selection, method lookup and invocation under one callable/argument cleanup. Route all classified outcomes through the existing direct-result handler, whose final cleanup releases the receiver after admission and mutation-outcome capture. This covers early selection, rejection and shallow capability/receiver failures without extending argument lifetime through a direct Promise or duplicating early receiver clears.
- In [invokeFunction](../src/invocation.js), release the synchronous action closure's callable, receiver and arguments in `finally` after the native boundary returns or throws. Its caller owns any unfinished direct-result work. Freshly thrown native Errors retain this action frame too; prebuilt-cause tests alone miss it.
- In [input-preparations.js](../src/input-preparations.js), give each raw property's delivery its own clearable capture of the existing staging record. Drop that capture after delivery or discarded-delivery resumption, including failure. Keep synchronous staging records until atomic commit, and pending siblings' publication authority until their own last use. The evaluated helper reuses the staging record and needs no pending-key counter, last-child event, shared cleanup registry or stack access. Clearing only a shared construction after its last pending key is unnecessarily coupled.

Existing versions are authoritative: skip them, including settled/fixed/absent versions, rather than walking their values under the new result policy. For raw slots, `createVersionFromPlacement` already initializes presence, recovery and position; synchronous delivery changes only the value. Keep late publication's common commit/fallback boundary. The full candidate, not branch-hit counts alone, must validate these deletions. Retain other clears and first-failure stops until their actual lifetime or work obligation is disproved.

**Preserve diagnostics; do not adopt stack suppression as the cleanup mechanism.** A scratch `Error.captureStackTrace` change removes many runtime-wrapper retention paths, but a freshly thrown exact host cause still retains runtime action closures. A heap snapshot also shows an unavoidable distinct edge: native cause → native CallSite → method receiver. The existing exact-cause/native-stack contract permits that diagnostic retention; it cannot simultaneously guarantee collection of that receiver while the cause remains held. GC oracles must distinguish it from removable runtime captures, returned receiver data and published mutation state. Do not eagerly read `.stack` (which can invoke a formatter), mutate global stack settings, or erase host stacks. V8's custom capture/formatting facilities are [engine-specific](https://v8.dev/docs/stack-trace-api); Phase 8's language-facing Error view does not authorize changing host diagnostics.

#### Exact-receiver lifetime correction

See the additional shared lifetime requirements in the [catalogue follow-up](#catalogue-follow-up-and-construction-lifetime); the weak-membership policy below does not replace those strong native-work and construction obligations.

**Selected: preserve exact-receiver checks with weak membership (2026-10-18).** Replace the strong receiver field in the method-result preparation policy with one invocation-local, one-member `WeakSet`. Create it at [ready result admission](../src/import.js) for an object or Function receiver supplied by the existing external-call boundary; primitive receivers cannot match this object-only check. Test membership at the existing [result check](../src/input-preparations.js), before the prepared-reference stop, and share that same policy with newly owned later segments. Keep registered-identity checks and Error precedence. This supersedes the proposed early cutoff without changing the approved result contract or introducing another traversal mode.

The evaluated substitutions are local to `importReadyMethodResult` and the existing preparation check; no caller changes its receiver argument:

```diff
 // import.js, method-result policy:
-        receiver,
+        receiverIdentity: receiver !== null &&
+            (typeof receiver === "object" || typeof receiver === "function")
+            ? new WeakSet([receiver]) : undefined,

 // input-preparations.js, direct result check:
-            (value === policy.receiver || operationContext.execution._externalIdentities.has(value))) {
+            (policy.receiverIdentity?.has(value) || operationContext.execution._externalIdentities.has(value))) {
```

The proof is local: any value supplied for comparison is live. If it is the receiver, weak membership still identifies it; if the receiver has become unreachable and collected, that exact object cannot later be supplied. [WeakSet membership](https://tc39.es/ecma262/multipage/keyed-collections.html#sec-weakset-objects) provides this identity test without retaining or retrieving the receiver. [WeakRef](https://tc39.es/ecma262/multipage/managing-memory.html#sec-weakrefderef) also passed the experiment, but retrieval is unnecessary and its dereference keeps the target alive for the current job. Prefer membership; add no finalizer, cleanup callback, receiver registry, history, counter, or early/late policy split.

Keep strong references required for native work, direct Promise completion, publication and external ordering until their existing last use. Only the identity-only preparation capture becomes weak. Independent nested data may then outlive the receiver without ending its checks. Do not clear membership at call completion, transfer this call's policy into a prepared graph's existing producer, or change immediate capability failure's scope-poison effect versus a later independent result Error. Cost is one small weak collection per applicable result admission and one membership test at each already-required result check, with no additional graph work. Pending callbacks and retained diagnostics may keep the small policy alive; they must not thereby retain the receiver. Once those holders release, the policy leaves no execution history.

#### Progress invariant and work bound

A successful preparation segment initializes each newly traversed managed container once, after installing all of its pending-delivery obligations. Its identity map bounds cycles within the segment. Later result traversal stops at prepared containers, and each raw pending placement has one owning delivery chain that prepares newly revealed data; several placements containing the same Promise still have separate obligations. Existing versions retain their producer instead of spawning another validation. Retirement restores relationships without clearing the preparation fact.

For finite inputs and finitely many deliveries, successful preparation is therefore bounded by newly initialized containers **and their visited placements/edges**, plus reception and delivery work. A failed segment publishes no fresh preparation, discards its callbacks' authority and cannot retry itself; a new reception, including a separately owned delivery, can retry failed input, with that attempt's work charged separately. This is a preparation bound, not a bound on all receiver/export, COW, retention or relationship-restoration work.

Instrument successful initialization and preparation entry in generated fixtures: no managed container is re-prepared after a successful initialization in that execution, and preparation never installs a second owning delivery for an authoritative version. Count failed attempts, raw subscriptions and ordinary destination transfers separately. Include admitted-but-unprepared producer routes, control overlays, retirement/re-entry and repeated returns around a small graph; use test instrumentation, not a production registry.

At completed producer publication and receiving handoff, assert that every escaping managed container has completed preparation and its pending placements have an owning producer. Check stable boundaries after an atomic construction batch, and preserve original producer/policy/context when a second holder receives the graph. Do not assert that initialization requires zero incoming parents: ordinary `import({ child: { n: 1 } })` links the private parent before initializing its child, and that assertion wrongly makes valid import fatal. Private batch edges, aliases and cycles are legitimate; absence of parents also cannot prove absence of leases or ordinary JavaScript references. Use producer-boundary instrumentation and retained-view witnesses, not another production ownership flag or repeated graph scan.

Provisional output retention is not an outward handoff either. A method returning an invalid working receiver can temporarily retain it before delivering only its validation Error. Instrument final outward delivery and completed construction/finalization boundaries; do not require rejected private state to become prepared merely to satisfy a lease-site assertion.

### Investigation outcome: repeated validation through a late back-reference (2026-10-17)

**The current fresh-segment path can unfold a finite graph indefinitely. Cycle grouping alone does not fix repeated data validation.** This is an existing preparation-progress defect under the fresh-identity fallback, before adding any verdict coordinator. It does not establish that dynamic SCCs or an earlier identity verdict are required.

The minimal cached-wrapper witness uses two host containers and one ordinary Promise. Neither host container is mutated after admission; later fulfillment supplies only an inert reference to the wrapper:

```js
const ctx = { execution: new r.Execution(), errorContext: "N2 back-reference" }
const pending = Promise.withResolvers()
const child = { p: pending.promise }
const source = new r.Chain(r.import(child, ctx), ctx)
const wrapper = { child }
const result = new r.Chain(r.importMethodResult(wrapper, ctx), ctx)
pending.resolve(wrapper)
```

The source Chain retains the imported child. Result validation copies that pending child to `C1` and installs `wrapper.child -> C1` in the wrapper's logical overlay; the host property still contains the original child. This cached logical-copy route is supported. No host mutation, forged runtime record, or direct host-Promise self-wait is involved.

The borrowed-version trace is:

1. Ordinary source settlement publishes the wrapper into the original child's `p` version.
2. Delivery to `C1.p` enters `prepareInput(wrapper)` before committing `C1.p`.
3. That segment follows the wrapper's logical child to `C1`. Its `p` version is still pending, so preparation creates `C2`, copies the wrapper to `W1`, and registers `C2.p` on the unfinished `C1.p` version.
4. The segment returns immediately; `commitPromiseVersion` publishes `C1.p -> W1`, where `W1.child -> C2`. The next callback can now consume that publication.
5. Delivery to `C2.p` validates `W1`, encounters its own still-pending destination through `W1.child`, and repeats with `C3` and `W2`.

Each publication finishes independently of identity; the trace is repeated forward discovery rather than a fixed verdict deadlock. Waiting for the new segment's complete verdict before step 4 would instead introduce a mixed cycle: the new segment borrows the version whose publication that wait would prevent. This diagnosis explains the retired validation-completion proposal. The approved replacement stops revalidation at prepared managed references instead.

### Simplification decisions and deferred experiments

The approved preservation contract supersedes the proposed validation coordinator and all coverage/producer-handle experiments. Do not extract extra Phase 3 identity helpers or retain a second validation mode to support that retired design.

**One complete placement capture per reached key: implemented and retained.** [Managed capture](../src/managed-capture.js) captures candidate keys, then reads each complete placement at its traversal turn. Presence, value and the exact pending version come from that capture; separate presence filtering and version reacquisition are removed. Receiver validation applies the same local pattern with its existing non-consuming capture. Ready-only snapshot inspection stays separate; no generic walker, retained index, new policy or lifetime is introduced. Export and receiver-validation probes now read each ready property descriptor once instead of twice, and method selection reuses that same capture.

Candidate-frontier capture still precedes fallible descriptor reads, while values are consumed at their own turns. Existing key ordering, shape capture, synchronous/FIFO delivery, final presence and complete Error collection remain authoritative. Raw consuming reads still normalize properties; native validation never subscribes to stored thenables. Six new checks cover descriptor work and raw ready/native/ordered capture; existing tests cover sparse Arrays, absent overlays, pending presence, duplicate representations and release. Canonical node/copy counts stay unchanged. The same temporary candidate frontier is used, with absent candidates removed from output entries at their turn; pending work retains only existing versions and source-free records. Follow-up validation is recorded in [the review](phase4-review.md#placement-capture-experiment-2026-10-19).

**Retire investigation execution paths after production replacements pass.** Promote the unchanged identity witnesses, revised progress cases and still-relevant publication/lifetime checks into ordinary tests and subprocess fixtures. Remove the source-substitution reuse loader, duplicate completion algorithm and coverage-only experiments once their relevant protections are covered by production tests; the new design needs no coverage-trie or SCC-specific acceptance. Retain independent oracles and useful trace/fault instrumentation. Verify each replacement fixture runs the intended production path before removing its predecessor, and update historical links when artifacts move.
