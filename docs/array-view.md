# `ArrayView`

`ArrayView` owns Array bounds and backing storage when those differ from a simple native Array. It supports both pending length and the shared-storage operations `slice`, `concat`, `push`, `pop`, and `shift`. Ordinary native Arrays use their physical length; their metadata acquires a range when they need captured growth knowledge or bounded storage.

## Representation

A view is a half-open logical range over shared storage:

```js
physicalIndex = range.start + logicalIndex
minimumLength = range.lengthState.minimum ?? range.lengthState
```

The constructor accepts an Array or `ArrayView`; `start` and `end` are relative to that logical source and default to its full range. The constructor reads the source owner's range, if present, and converts the bounds to storage coordinates.

`meta.arrayRange` holds `{ backing, start, lengthState }` on each owner that needs a range. `lengthState` is either a fixed number or the ordered growth/watcher sequence. A native owner's backing is itself; a published view references the native backing directly and keeps independent bounds. The range is plain representation metadata: it is never admitted, indexed, leased, or published as another graph identity. Ordinary native Arrays allocate no range until needed.

Callers use the `ArrayView` class for both native Arrays and views; they never access the length sequence or its maximum directly. `resolveLength` supplies exact length, and `resolveInRange` supplies index validity, immediately when known. `captureLength` retains the current program position and supplies its ready answer or pending completion independently of placement traversal. `minimumLength` supplies only the committed prefix for incremental scans and storage allocation; `readyLength` returns exact length or `undefined` for a boundary that must reject pending shape without subscribing. There is no generic `ArrayView.length` getter that could mistake a lower bound for an exact answer. Language-level `array.length` uses `resolveLength`.

Before sharing storage, `tryShareStorage` captures the source owner's resolved bounds in its range. The native Array keeps its existing owner-local property versions. Only a separately published `ArrayView` is a new logical identity. `ArrayBacking` records physical occurrences and registered owners; it does not own logical length. An optional `ArrayBackingProducers` record holds canonical logical versions for eligible shared backing positions. Physical storage and logical producers remain separate because optional writeback can fail or a local version can mask a backing slot.

The producer record's internal range contains only `backing` and `start` physical coordinates. It owns no logical length state; logical bounds belong to the registered owners, and required physical-length observations read the backing directly.

Imported Arrays have physical occurrence records for parent indexing, but never supply writable backing to derived views. Operations materialize runtime-owned Arrays when needed, preserving borrowed host data and its admission metadata.

`ArrayView` is not exported from the package.

Controlled Array intrinsics operate on ordinary sparse Arrays of placement references. Capturing that remap does not resolve element values. The intrinsic moves or replaces the references, then common placement transfer publishes the resulting Array. Removed-element results retain their own captured placements independently of receiver publication; ArrayView derivation remains the backing-reuse path.

`fill` and `copyWithin` capture only their selected replacement range. When the receiver has exclusive writable storage and no owner-local overlays, a baseline view captures the old destination range and shares unchanged backing. Its lease replaces the operation's original baseline lease before writes begin. The complete old value therefore remains available if a later slot write or parent publication fails. Overlapping copyWithin sources are captured before the first destination write. Other representations use ordinary private materialization; imported data, retained views, pending scope gates and local overlays keep their existing isolation rules.

Representation copies of unresolved placements share captured delivery while keeping independent destination versions. Retirement removes obsolete delivery destinations; independently captured versions still receive settlement. Restoring an inactive copied version adopts its completed logical delivery without inspecting host storage or subscribing again. This sharing does not replace the FIFO continuations of actual reads or mutations.

## Logical surface

A view exposes the translated enumerable indexes inside its range and a virtual non-enumerable `length`. Canonical string indexes such as `"0"` are indexes exactly as in JavaScript; other string properties are not Array data. Holes remain holes. Runtime fields, backing indexes outside the range, symbols, non-enumerable properties, and metadata are outside the language surface.

Installed placement versions also contribute logical indexes, including without physical slots. The view's length is authoritative; physical length cannot erase committed growth or determine possible growth. Enumeration merges version keys with physical candidates in numeric order. Materialization, export, and detached snapshots preserve logical length and trailing holes. Sharing backing requires resolved length, including for a zero-growth derivation.

The common language-property boundary reads the logical owner's installed version first, then an in-range canonical backing version, then its translated physical descriptor. It also enumerates candidates and resolves logical presence for records, Arrays, and views. ArrayView supplies storage projection and length knowledge, without a separate logical element-read, enumeration, or iteration API. Traversal, ownership, import, export, refcounting, Error search, and copy-on-write use the same owner and property boundary.

Physical writes and deletions also use the common language-property boundary. At the write point, a view translates the logical key to its backing destination; the common writer uses the descriptor captured during preflight and maintains physical backing occurrences. A canonical producer destination already has an authorized physical key and follows the native backing's index-write rule, including before physical growth; a real view still enforces its own bounds. Descriptor preflight remains separate from this translation so inspecting a native Array slot does not advance pending length state. ArrayView has no separate storage mutation implementation.

An in-range indexed write or deletion can retain a view when it is the sole active owner of runtime-owned backing and ordinary ownership permits the change. The common writer translates its key and validates the physical destination. This avoids materializing an unrelated prefix for one point write or mutable element entry. Other owners, imported storage, incompatible bounds, or growth can require materialization. Endpoint methods may derive views over shared storage because they do not change any preserved view's logical surface.

## Length state and backing ownership

Possible out-of-range creation adds a contribution to the existing length sequence and a gate to the logical placement. It neither creates a physical element nor resizes backing storage. ArrayView owns length state and backing bounds; placement publication owns the corresponding graph effects. The linked-list module handles only contributions, captured questions, and their ordering.

Placement publication uses two class operations: `beginIndexTransition` returns the completion action for possible creation, and `prepareIndexCreation` returns a growth commit for a known creation. Preparation performs fallible storage reads before publication; the commit updates logical growth after the element write without another host read. Callers hold neither sequence nodes nor a separate length-registration token.

Copying a logical Array also copies its shape through `prepareShapeCopy`, called by common container-copy bookkeeping. This is distinct from copying backing storage: an independently mutable copy retains earlier growth outcomes but must exclude later source operations. Only that case forks the sequence. Read-only captures retain one position instead. Native Arrays with no range continue to use their physical length directly.

Each backing record maintains its active logical owners. Storage permission is separate from logical-node ownership: another view may preserve a slot even when the node being changed has one incoming placement. Existing-slot writes check that storage use, and optional Promise writeback leaves an overlay whenever the backing cannot safely change. Pre-existing storage outside a view's range remains unavailable for extension, even when it consists entirely of holes. Imported backing is never modified. End extension can reuse backing when it adds storage beyond preserved bounds.

Runtime-owned backing accepts valid length changes under the [managed-storage contract](data-limitations.md#proxies-in-managed-storage). A failed element write can still commit logical poison and length beyond physical storage; placement versions and the view's length remain authoritative. Both native managed call modes copy the complete canonical receiver from captured logical shape and placements. Observation copies inherit identity; mutation copies start fresh. Controlled Array methods retain their narrower remap and backing-sharing mechanisms.

The representation supplies `descriptor` and `mutationTarget` operations on an explicit logical owner. The common language-property boundary performs physical writes and deletions; representation metadata gives no permission to bypass ownership or placement publication. Logical consumers call `readLanguageProperty`, `hasLanguageProperty`, and `enumerableLanguageKeys` with the logical owner. Complete collectors use `enumerableLanguageKeyCandidates` or pass a per-key `inspect` guard to `enumerableLanguageKeys` so a failed descriptor does not hide other candidates. The guarded enumeration also preserves keys captured before a listing failure. Optional Array ranges filter stored and version candidates together.

Bounded physical ranges capture their numeric bounds immediately and stream candidate indexes; iteration itself neither reads nor retains backing storage. Captured overlay keys merge in numeric order without allocating a set containing every hole. Broad native ranges still capture stored keys immediately, while bounded views inspect only their own range. This bounds intermediate allocation; a sparse bounded range still requires a range scan to preserve the reflection and complete-Error-collection contract.

## Derivation

A derivation is allowed only when the receiver is not imported.

The first derivation captures the source bounds and creates the selected result range. Registering the new logical owner supplies all inherited physical placements dynamically, without scanning ready elements to mark them shared. Owner-local overlays receive result-view versions forked at the derivation's FIFO position. Unchanged canonical backing producers project through the new bounds without copying their versions or subscribing again. Inserted properties use ordinary placement transfer: an eligible unshared position in an unindexed bounded view can establish a canonical producer, while explicit destinations, gates and owner-local overrides retain their own authority. A ready scalar write needs no producer record.

`copyArrayOverlays` transfers relevant owner-local versions, including absent overlays and captured pending delivery. Canonical backing versions are inherited by projection. Ordinary physical occurrences were established at preparation and are reused through the backing record. There is no retained-prefix cache or separate element-sharing scan.

Derivation work follows transferred overlays and newly inserted elements, rather than the ready backing prefix. Copying an ineligible representation and building a requested refcount index still require their ordinary graph work; this is not an unconditional constant-time promise for every `push` or `pop`. Observation and mutation use the same derivation, publication, and rollback paths.

A copied owner-local placement settles through its own captured version without acquiring shared storage authority. A projected backing producer settles once; every still-projecting view observes that producer, and owner-local versions continue to mask it. An explicit copy still captures the producer at the copier's FIFO position. This also applies to synchronous thenable normalization. Fresh suffix insertion may write beyond the source's preserved bounds; ordinary indexed mutation follows the storage-permission rule above. No storage copy is required solely to settle a retained element.

`pop` and `shift` derive the retained subrange; an empty result is an empty native Array. Non-empty `push` requires the logical end to equal the physical end. `unshift` uses the ordinary remap path whenever its receiver must be preserved; physically moving shared backing would require mutable coordinates shared by every existing view.

`slice` logically converts its bounds before representation work, then returns a subview over the selected range when backing reuse is eligible. Empty results use an empty native Array; otherwise an ineligible source is remapped directly.

`concat` extends only the receiver backing; it never prepends into an argument backing. The receiver's range keeps its old end while the result view includes the appended suffix. The suffix is built as a sparse property-placement remap, so holes, ownership, Promise versions, and indexed-edge accounting use the same placement path as materialization. Overlapping inputs, including `array.concat(array)`, are captured before placement. If the receiver does not reach the physical end or its backing cannot extend, concat materializes normally.

End growth is shared by `push`, `concat`, and past-length assignment. It requires the physical end and writable length, plus extensibility when properties will be added. A nonempty extension also materializes when the discarded offset prefix exceeds the live range. This bounds a moving queue's backing and amortizes the live-range copy over prior removals; retained views keep their original backing. The extension helper owns prefix capture, backing growth, any suffix population, and construction publication or discard; it returns only a published view. If extension is ineligible, the logical range materializes and the operation continues on a native Array.

Canonical producers retain authoritative forward state for the backing's lifetime, including masked or currently out-of-range slots. This follows the existing whole-backing retention allowance and preserves cached re-entry. A local override does not erase the producer needed by another view. Releasing the final backing owner retires reverse relationships, obsolete destinations and optional counter projections; independently captured versions retain their own settlement. The record contains at most one current canonical version per backing slot, not a history of local overrides.

An optional counter index registers only the backing versions its owner actually projects. Shared publication updates those maintained consumers, without scanning every backing owner. A local override or owner retirement removes its reciprocal memberships. Counter construction is the ordinary fallible graph walk; publication does not rediscover that index by traversing unrelated views.

## Incoming placements

A backing Array's execution-local metadata lazily owns an `ArrayBacking` record. It stores the native logical owner and derived published owners once. A managed physical child stores `(backing, index)`; parent enumeration expands it into in-range owners without a local or canonical overlay. A canonical producer's child has its separate logical backing occurrence, expanded into in-range owners without a local override. An owner-local overlay child instead stores its direct `(owner, key)` placement. This avoids recording every inherited child again when creating a view. Internal projection objects are not additional logical owners.

Storage preflight captures the actual physical descriptor separately from the logical value. Successful writes maintain backing occurrences even when a source gate masks the slot. Optional writeback failure keeps the old physical occurrence and the accepted logical overlay. Private view construction registers its owner and final overlays only at completion, without buffering edges or rescanning backing elements. Physical recording skips an uninitialized backing, not an uninitialized view: writes to existing backing remain immediate. A later construction failure discards the unfinished owner without undoing successful backing writes.

Retirement unregisters owners that have no path from a holder or independent retained use, including disconnected cycles. Active views retain their backing record; a backing may retain physical elements outside their logical ranges. Whole-backing retention is intentional: retirement does not invoke host storage writes or compact interior slots. Retired forward backing facts remain available for re-entry, while obsolete reverse links and optional counter projections are removed.

## Materialization and length

Materialization creates an owned native Array containing the logical length and indexed elements. It rebuilds ownership, refcounts, cycle cuts, and Promise versions from those logical placements; import status remains on the retained child identities, while storage and view state are not copied.

Length assignment preserves its rollback baseline through the ordinary scope transition. It materializes directly into an Array of the assigned length, transferring only retained placements; discarded elements need no capture, subscription, indexing, or physical deletion. The baseline stays intact even if publishing the resized Array fails. This also handles restricted source storage without a separate in-place resize path. Endpoint methods retain their shared-backing optimizations: deriving shorter bounds does not delete backing, and eligible extension grows backing without changing earlier views.

Indexed assignment follows JavaScript Array length behavior. Assignment beyond a view's end can extend shared storage, including holes, when the view reaches the physical end and the backing is extensible with writable length. It publishes a derived view ending at `index + 1`; otherwise the receiver materializes before assignment. Unlike native endpoint methods, this direct own-property write need not inspect inherited indexes.

Both endpoint methods and indexed extension check the native backing owner's existing maximum possible length against the physical end. Only that owner can reserve growth beyond physical storage: distinct views materialize before an out-of-range transition, or extend storage before publishing their larger bounds. A pending native index creation reserves the intervening holes as well as its eventual slot. Extending that region for a sibling would expose the sibling's values when the earlier creation commits. Use ordinary materialization while that tail is reserved, including when the native owner has retired but its captured transition remains pending. This check needs no scan of registered views or additional backing summary; committed length alone cannot prove extension safe.

Export always materializes the logical surface and resolves reachable Promises according to the normal export contract. Native Array methods never receive the physical backing as an ordinary receiver.

## Captured shape and pending placements

Element state and Array length answer different questions. Creating index 4 commits length at least 5 even if its value is pending or the entry stays open; deleting that index later leaves length 5. Entering index 4 without creating it adds no growth. The element's placement version orders access to that element; length state records only whether creation has happened or is still possible.

Length questions keep their program position. For an initially empty Array, an entry at index 4, a length read, and then an entry at index 8 mean the read can return only 0 or 5. The later entry cannot change that earlier answer, even if it finishes first. Conversely, a length read issued after both entries can return 9 as soon as index 8 is created, without waiting for the earlier entry at index 4. This is why length knowledge has an ordered sequence rather than a single array-wide gate.

Each logical Array owns its length knowledge through its ArrayView projection when physical length alone is insufficient. Its ordered growth contributions and length/range questions preserve captured prefixes: the minimum is committed growth, and the maximum also includes unresolved bounds. Exact length is ready when bounds coincide; a range question can answer earlier. Reads and read-only captures use the same active questions in that sequence; only independently mutable copies fork it. Forks share earlier outcomes but exclude later contributions and questions. When current bounds coincide, the Array retains the ready number while earlier questions keep their own sequence. Coalesce adjacent settled growth and unlink completed watchers, including behind an unresolved head. Pending watchers use the existing operation owner and release-on-close mechanism; output capture also releases its questions when discarded. Intrinsic length reads create no property version or graph Promise edge.

Every sequence has its own revision counter. A pending growth source keeps one consumer map from each retained sequence's counter to an optional contribution node needing active notification. One source occurs at most once per sequence. Earlier shared outcomes update both an original and its fork; later private outcomes cannot invalidate the other branch. A passive entry holds only its counter, with no reference to the sequence or Array. An active Array or an unfinished captured question retains its sequence; retirement, shape replacement, capture release, and question completion release that use. The last release removes its consumer entries. Retired sequences retain authoritative forward outcomes and refresh before registering again on restoration.

Adding or removing an active question promotes or demotes consumer entries only where the observed prefix changes. Multiple questions in one sequence reuse one notification registration per source. Completion increments every dependent counter and snapshots active targets before clearing the map and notifying them. An active refresh updates bounds from its changed contribution onward, using the already-current subscribed prefix and compacting affected nodes in the same pass. Normal completion, discarded output or local closure releases notification nodes. No source retains an unused passive sequence or Array.

Conclusive range questions use their existing conservative bounds before refreshing outcomes: completion can only raise the minimum or lower the maximum. A point already below the minimum remains in range, and a point at or beyond the maximum remains out of range. An unresolved question refreshes only when its own sequence's revision changed. Ready reads remain synchronous, and an unchanged retained frontier requires no repeated scan.

Array candidate enumeration includes installed versions beyond the published minimum or physical length, bounded by the requested range. Undecided presence is a candidate, not a present undefined element. Length readiness does not release element gates: sparse output retains absence, while dense output turns a retained absent position into present undefined. A consumer resolving a placement uses its captured presence and value; a settled overlay remains authoritative over stale storage.

Deriving a view transfers in-range absence overlays as well as present placements. An absent overlay may hide a physical backing slot or a canonical backing version; omitting it would expose that stale value in the derived view. Ordinary holes need no overlay. Transfer logical contents without copying the source's storage authority or physical-absence bookkeeping.

Length shrink excludes every logical placement in its truncated suffix, including versions with no physical property. Only retained placements transfer to the resized Array, so discarded versions have no authority to publish into it. Earlier captures keep their own settlement; shrink waits for conflicting transitions, never for the ordinary payloads they publish. This includes canonical backing transitions projected into the suffix, except where a local version masks them. Enumeration translates the selected bounds and chooses between maintained sparse producer entries and the bounded numeric range; it performs no host scan or index construction. A later payload cannot regrow the Array or write outside a subsequently derived ArrayView.

Complete traversal captures shape before suspension and visits all required placement candidates. Shape has independent completion: deleting an undecided out-of-range placement removes its value dependency but leaves its earlier possible growth. Export and native materialization resolve captured length for successful assembly and preserve holes; discarded output releases shape while required Error collection continues. Bounded consumers exclude placements outside their consumed range; positive at needs no length query, positive bounded slice may use a range proof, and with still needs exact output length after index validation. Physical backing reuse additionally requires resolved shape equal to its storage window. External snapshot reads, including a length read through a managed alias, require their selected value to be ready synchronously; unresolved shape produces `InvalidExternalSnapshot` without subscribing.

Controlled Array algorithms own their shape dependencies. `at`, `slice`, and searches prepare their selected indexes or ranges through their ordinary argument preparation. Check for provably empty ranges and invalid indexes before requesting exact length, retaining required argument processing. For a negative index `i`, validity is the range question at `-i - 1`; only a potentially valid position needs exact length for normalization. `with` uses that same range rule for validation, then requires exact output shape on success. Searches capture their consumed range, including an empty range when their start cannot reach an element. `join`, `toString`, and sorting capture their required placements and shape together, without an earlier exact-length wait. `flat` captures placements only: every prepared level is flattened, so holes contribute nothing and need no position or length capture. `concat` captures each remap before waiting for its length and retains input leases until output placement; ordinary element data need not settle before it returns the outer Array. Intrinsic methods prepare exact remap length before execution.

Flattening, string conversion, default sort keys and scalar arguments capture available placements and start independent conversions before joining pending results. Managed inspection is pure; output positions, shape and method-specific search rules determine semantic order. Captured versions and nested conversions own remaining work, allowing sources to release promptly. Failure discards successful output but still completes required poison collection. A search key's identity capture does not delay independent bound conversion. Flattening preserves retained element payloads without resolving them below the requested depth.

Forward searches scan the committed prefix before requesting more range knowledge; a known match does not wait for unrelated growth. A nonnegative backward start proven in range also needs no exact length. Relative starts and unbounded backward search wait for the shape needed to locate their start. Index searches preserve scan order; `includes` may finish on any match while other comparisons or growth remain pending. Searches lease the receiver while they may read more placements. Once `includes` has captured every candidate, it releases that lease even if captured values are still pending; an early match also releases unused range questions through ordinary operation closure.

Ordered searches likewise release the receiver after capturing their final candidate, while a comparison may still be pending; unread candidates and unresolved forward growth retain it. Terminal source cleanup has a separate last use. The pending [Phase 4 corrections](phase4-design-history.md#array-representation-and-terminal-path-corrections) release remaining closure captures after ordered-search reflection failure and failed recursive flattening. Flat can assemble from consumed placements' final presence without retaining a second source/key correspondence. These corrections preserve shape, traversal and Error-consumption rules.

Array methods publish independently owned placements through remaps or derived views. Retained placements transfer their complete captured value, presence, recovery, and transition state; discarded or overwritten source placements retain no write authority over the resulting Array. Element entry completion therefore adds no method-wide wait. Intrinsics still need exact shape and prepared arguments, and algorithms such as sorting still consume their required values. A removed-element result may remain pending after the new receiver and its length are ready. This isolation follows destination publication authority, not mandatory eager copying of every source element; backing reuse and future optimizations must preserve it. Assignment of length `n` waits for unfinished transitions at indexes at least `n`, including logical candidates beyond physical storage, without waiting for ordinary data those transitions publish. Transitions in the retained prefix carry into the resulting Array; neither they nor unknown growth confined to that prefix delay the length assignment.
