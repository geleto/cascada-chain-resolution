## Review method

The earlier review relied too much on aggregate passes and the immediately changed functions. Its lifetime witnesses did not cover the complete call stack or all neighboring callers. The replacement method is an obligation ledger:

1. **Freeze the candidate and expectations.** Use complete source files after deletions, with individually reviewed contract migrations. Record the source revision or hashes and exact commands. Distinguish production, prototype, instrumented execution and reported evidence. A test stopped by its first obsolete assertion contributes no evidence for its remaining body.
2. **Trace in both directions.** For every skip/reuse decision, identify its authoritative fact and all writers, transfers and invalidation rules. From each producer, follow publication, retained holders, consumers, failure and release. Include unchanged code. A writer being correct on success says nothing about its failure path.
3. **Cross the relevant states explicitly.** Derive cases from catalogues of public operations, internal managed/external/snapshot routes, resources (including constructors, routes, tree nodes and registry links), and exits, rather than from the diff. Cover ready, synchronous custom delivery, native/deferred ordered delivery, fulfillment, rejection, supported reflection failure, publication failure/fallback, local closure, discarded construction and fatal resumption. Cross these with root/wrapper/late reference, fresh/prepared/admitted-but-unprepared data, representation, aliasing, retained earlier views, and unresolved independent work. Use small required combinations per obligation rather than an unreviewable Cartesian product.
4. **Give each resource a last-use proof.** List what owns it while pending, what operation transfers that responsibility, and which synchronous transition removes the former reference. Separate input capture, native use, publication, recovery, required Error collection and result delivery. Trace ordinary closure references as well as metadata/leases. Clearing a binding does not clear a still-required placement or baseline.
5. **Challenge the test oracle.** Compare values, aliases, ordering, Error membership/source and recovery with independent expectations. Verify sources remain live before last use, and release actual holders before requiring retirement. Keep unformatted Errors; test prebuilt and fresh causes at default, 50 and deeper stack limits. Distinguish exact native CallSite receivers and returned/published data from runtime leaks. In heap analysis, WeakMap ephemeron edges alone are not strong retaining paths.
6. **Require falsification evidence.** Remove each distinct prerequisite or release and require a named witness to fail for the intended reason. Surviving mutants mean an untested obligation or a possible simplification requiring proof. Zero branch hits prove neither unreachability nor redundancy. Shared symptoms may have several independent retaining paths; remove each path separately.
7. **Close the ledger, not just the suite.** Each row needs a source argument, applicable timing/exit cases, tests that exercise them, and fault evidence for changed enforcement. Report gaps explicitly. Promote strict witnesses and faults when implementing; do not convert expected production failures into passing assertions. Rerun affected rows after changes, then the normal/traced suite and extended histories before acceptance.

Derive the representation and method catalogues independently too. Sampling one Array method does not cover the others' capture, conversion, traversal or terminal paths. Assert that the method catalogue covers the runtime dispatch table, but derive expected semantics from the contract/native reference, not the runtime's dispatch flags. Count actual reflection and suspension hits. Track generated native copies as well as original sources. Run the safeguard registry itself: a passing ordinary suite does not detect stale fault definitions. After finding a retaining path, remove it and trace again; a second path can mask otherwise-correct cleanup.

Subprocess fixtures must use their real prerequisites. For example, `construction-retention.js` requires `--import ./test/trace-runtime.js`; without it, its copy-count assertion fails before testing retention. Verify each child's status and required instrumentation receipt. Source-reading VM fixtures must consume the actual candidate files. Use parent timeouts with startup margin; never infer semantic failure from a heavily loaded two-second test, or kill unrelated processes.

Instrumentation must also compose. With the tracer inherited by children, ten internal-stage tests and the ownership-work test initially stopped at missing source anchors: the tracer had renamed their target functions. The candidate fault/counter hooks now target the actual renamed bodies when tracing, retaining their mandatory anchor assertions. Both instrumented and ordinary tests must run; a hook-startup failure supplies no semantic evidence.

## New findings and evaluated corrections

Running the existing **131-case completed-work fixture at 50 frames fails 46 cases in both production and the previous complete candidate**. These are pre-existing shared-mechanism gaps, not 46 distinct Phase 4 regressions. Heap paths with prebuilt causes show runtime ownership, rather than only permitted native-cause retention. A separate ready lookup retains its former holder while its pending equivalent releases it.

| Confirmed retaining path | Simpler correction and protected last use |
| --- | --- |
| Error → public entry closure → input/Chain; Error → Chain initialization closure → original input | Drop public wrapper inputs after synchronous issuance has transferred them to core work; drop constructor input/setup after its receiving transition. Do not wait for the outward result. |
| Error → `receiveValue.accept` → completed delivery callback → settled version → former root | Drop `onValue` in the actual delivery's `finally`, after preparation and capture. Pending delivery still retains that callback until it runs. |
| Error → native `Array.map` CallSite → temporary capture input Array | Use an ordinary indexed loop in `ManagedCapture.capture`, preserving synchronous order and per-index callbacks. This removes the retained native receiver without mutating caller arrays or Error stacks. Its uncaptured input parameter needs no explicit clear. |
| Error → mutation scope continuation → old value/state | Clear the continuation's bindings after it invokes the transform, including failure. Do this inside the resumed continuation, not before external readiness. |
| Error → transform action → `current` | Clear the action's local binding after invocation. Authoritative baseline/recovery and any returned pending work remain owned separately. |
| Error → completed mutation path → `operationResult.placement.recovery` | Clear path-only `operationResult`/`publicationValue` after reconstruction and publication finish. Do not clear them at target selection or before fallible enclosing reconstruction. |

These corrections add no graph traversal, retained bookkeeping, cancellation mechanism, new caller mode or diagnostic policy. They preserve the exact Error/cause contract. Each of the six binding-cleanup groups has an independently failing mutation witness; capture-loop and ready-lookup witnesses supplement them. Mutation success, failure/repair and still-pending work retain their separate controls.

The scratch candidate passes all **131 completed-work cases at default, 50 and 1,000 frames**, plus **30 boundary**, **12 terminal** and **4 ready/pending path** cases at 50 and 1,000 frames. Snapshot identity-wait source release passes for lookup and export; failed-construction retention passes with its required tracer. The new strict [path witness](../test/experiments/phase4-path-release.mjs) remains outside the default suite until implementation, alongside the existing strict release probes. The two ready production cases fail; pending cases are controls.

**External authority has a separate last use.** Releasing copied arguments is insufficient. Holding a completed external-call Error after dropping its ContextChain retains `ExternalAccess.identity` through a runtime CallSite. The same class affects failed property reads, refused writes/deletions and invalid repair paths. It also affects successful snapshots while identity alone remains pending: the operation's retained route still reaches the external resource after native access has ended. Exact host causes are prebuilt in these witnesses, so native-cause receiver retention does not explain the failures.

The evaluated correction gives `PathOperation` ownership of its one `ExternalAccess`, replacing the duplicate capture in `run`. Its existing `completeExternalEffect()` clears the access's identity/path/boundary and the spent route/selected node, while retaining the operation/context still needed by snapshot result work. The actual readiness callback clears its captured identity/boundary/scope in a `finally` covering **all** exits, including repair validation. External call result handling clears its strong receiver after direct admission/publication capture; early getter/noncallable exits clear it too. A direct pending result retains the receiver until that point. No release registry, new completion flag, traversal or semantic change is needed.

The strict [external-owner witness](../test/experiments/phase4-external-owner-release.mjs) checks **20 cases**: terminal observation/mutation paths, property operations and repair, both snapshot routes before identity completion, and direct-pending retention/release controls. The candidate passes at default, 50 and 1,000 frames. Four independent reversions fail: access fields, direct receiver, readiness captures, and route release. The route mutant fails both identity-wait snapshot cases, establishing why operation closure is too late. The first three corrections also preserve the existing native-work, Error attribution, scope-poison and recovery tests.

### First-preparer attribution remains an open general issue

We independently reproduced this on both the current production tree and the frozen candidate:

```js
const ctx = { execution: new r.Execution(), errorContext: "attribution" };
const inner = { bad: new Error("stored") };
const delivery = Promise.withResolvers();
const outer = { next: delayed ? delivery.promise : inner };
const fromCall = new r.Chain(r.importMethodResult(outer, ctx), ctx);
const fromImport = new r.Chain(r.import(inner, ctx), ctx);
delivery.resolve(inner);
// getErrors on either holder: ready -> InvocationFailed;
// delayed -> ContextValueFailed. Both holders share the resulting Error.
```

The first actual preparation supplies the stored Error's kind; delaying discovery lets the later ordinary import establish it first. This variation is not listed in the authoritative [Error nondeterminism exceptions](data-limitations.md#allowed-nondeterminism-in-error-handling). Record it separately from N2: the preservation cutover neither introduces nor fixes it. The review recommends permitting it, but its example does not establish that waiting on unrelated work is the only possible correction. Resolving it requires an explicit architecture decision about attribution, while preserving non-blocking issuance, one authoritative pending producer, existing Error identity/source guarantees and bounded preparation. **No new exception is accepted here.** Keep a minimized strict differential witness when promoting the generators; report this known discrepancy separately instead of normalizing away Error kinds or counting the case as passing.

### Clarifications and cutover work

- **Prepared is not ready.** Independently reproduced on production and the candidate: a method that stores an imported `{ value: pending }` into its working receiver fails with `InvalidManagedReceiver`; after that property settles to valid data, it succeeds. The original holder still receives its value. This follows the existing completed-receiver rule and is now explicit under [Method results](data-limitations.md#method-results). Result-only preservation and native receiver finalization need separate assertions.
- **Subprocess timing is a harness issue.** The two child-process tests in [runtime-boundaries.test.js](../test/runtime-boundaries.test.js) allow their children 30 seconds but leave the outer tests at Mocha's default 2 seconds. Give those wrappers a budget beyond the child deadline with overhead, and audit the other coverage-timeout cases by name before changing them. Do not raise deliberate progress deadlines or treat a timeout as a successful run. Production cutover must still promote the 80 identity witnesses/update their old expected-failure baseline and remove the two superseded validation-copy safeguards; those red gates are not runtime regressions or passing evidence.
- **Snapshot waits remain supported coverage.** The review's exclusion of raw managed references in host state is too broad. [External-state rules](data-limitations.md#external-state) permit inert retained managed references and runtime logical snapshot reads through them; they prohibit native inspection/mutation of raw managed storage. Ready-data snapshots may legitimately wait for an identity partition. Keep the existing snapshot alias, reservation-release, source-GC and fatal-schedule witnesses; valid internal seam tests of that mechanism remain useful even when this review's generators cannot construct the state publicly.
- **Preserve generator validity.** The reviewer corrected three harness errors: treating a reused host object as a fresh literal, awaiting a raw result before its supported handoff, and choosing random inputs inside timing-dependent callbacks. These rules are now explicit in [the test guide](../test/README.md#harness-rules). Evaluate promotion of the generators by new contract combinations and independent expectations, reusing the existing harness rather than adding a parallel model solely for larger counts.
