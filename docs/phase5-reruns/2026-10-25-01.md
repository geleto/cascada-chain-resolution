## Findings

### F1 — B22 reopened: quadratic peak retention when histories *copy* unresolved placements

B22's stated invariant is that pending structural Array histories must not have excessive peak retention. The shared-backing-producer fix removed copying for **bounds-only** successors (push/concat/slice/pop/shift) and its success criterion was fixed to the append-only witness. Every route that performs an actual copy still forks one fresh, subscribed version per copied unresolved placement. When the copy's owner is superseded, nothing can unsubscribe from the unsettled source, so the [B22 review's own pre-fix trace](../phase5-b22-review.md#pre-fix-authoritative-route-trace) (steps 4–6, "only the latest logical owner survives, all unfinished producer-to-copy dependencies remain until their inputs settle") still describes these routes. Settlement returns heap to baseline: this is peak retention, not a leak.

Reproduction (`f1-history-scale`): Chain `{ a: [0] }`, N unresolved native payloads, heap after forced GC **before any settlement**; separate processes.

| History (all payloads pending) | N=128 | N=256 | N=512 |
| --- | ---: | ---: | ---: |
| `push(p)` — B22 control | 1.3 MB | 2.0 MB | 3.5 MB |
| `a[i+1] = p` — control | 1.3 MB | 2.1 MB | 3.7 MB |
| `unshift(p)` | 31.6 MB | 122.8 MB | 486.4 MB |
| `splice(0, 0, p)` / `splice(i/2, 0, p)` | 31.7 MB | 122.8 MB | 486.5 MB |
| `push(p); reverse()` | 62.1 MB | 243.7 MB | 968.6 MB |
| `push(p); copyWithin(1, 0, 1)` | 61.2 MB | 241.9 MB | 964.8 MB |
| `push(0); fill(p, i, i + 1)` | 61.6 MB | 242.8 MB | 966.7 MB |
| `a = a.toSpliced(0, 0, p)` | 31.9 MB | 123.4 MB | 488.5 MB |
| `push(0); a = a.with(i, p)` | 62.2 MB | 244.9 MB | 974.7 MB |
| `a = a.concat([p])` (append view) | 1.8 MB | 3.0 MB | 5.2 MB |

At N=1,000 `unshift` peaks at **1.85 GB and takes 24 s to issue**, against 5.4 MB / 0.15 s for `push`. Exactly 4× per doubling.

The same mechanism applies to container COW. `f1-cow-cleared` models compiled code that holds a snapshot, writes, and then clears the holder at scope exit (`r[k_i] = p; snap = Chain(lookup r); r.z = i; deletePath(snap, [])`): 32 / 124 / 488 MB for records and Arrays alike. COW re-subscribes the host thenable for every copied pending value (`f1-subscription-count`): 33,408 `then` calls at N=256 and 526,848 at N=1,024 (≈1.88 GB peak). Remaps keep one host subscription per payload; their chain is internal.

Mechanism (`f1-heap-diff`, unshift N=96): each abandoned copy keeps ≈4 KB reachable from its unsettled source — about 23 closure contexts, 25 closures (`deliver`/`fulfill`/`resume`/`complete`, a capture `visit` registered in the source version's `captures` Set, a lease ledger's `acquire`/`release`, `queuedRelease`), 5 Promises and one `PropertyPlacement`. Holder retention is *not* the cause: with explicit `deletePath` the abandoned containers collect, and the per-copy cost no longer depends on container size.

Contract basis: AGENTS.md *Property Versions* ("Retained bookkeeping follows live data and unfinished dependencies, not operation history"), *Work Bounds*, and the Phase 5 rule that a confirmed present-contract violation needs a fix or an explicit architecture decision. The fresh-version-per-copy rule (AGENTS.md *Ownership and Copy-on-Write*) and the ban on subscribe-once fan-out (*Promise Continuations*) constrain the remedy. One direction: let a copy whose source owner is retired in the same transition take over that version's publication authority instead of forking. It needs an explicit decision because it touches the fresh-version-at-copier-position invariant.

### F2 — point `fill`/`copyWithin` remap the whole exclusive Array (ready work bound)

`f2-ready-point`: exclusive Chain `{ a: [0..N-1] }`, N single-element operations. Index assignment costs a flat ~20 µs/op. `fill(v, i, i + 1)` costs 6.2 / 12.9 / 20.2 **ms**/op at N=1k/2k/4k (81 s for 4,000 operations); `copyWithin(i, i+1, i+2)` costs 3.6 / 9.6 / 18.7 ms/op. Native cost is O(range). `fill` and `copyWithin` build `createRemap(receiver, 0, length)` and publish a new Array from it. AGENTS.md *Work Bounds*: "Do not process unrelated data." Phase 2 F8 documents point-*assignment* materialization only with retained views (exclusive assignment is O(1)); this controlled-method case is not recorded. Lower practical impact than F1.

### F3 — documented whole-backing retention composes into unbounded queue growth

`f3-queue-weak` and `f3-queue-mechanism`: `q.push(x); q.shift()` keeps logical length 4, but after N iterations the view sits at `range.start = N - 4` on an N-slot backing whose slot 0 still holds the first payload. **Every** sampled shifted-out payload stays strongly reachable (400/400 at N=4,000), ready or pending, and heap grows with history. `q = q.slice(1)` behaves the same. The controls collect (Array replacement, `push`/`pop`, `push`/`splice(0, 1)`, `unshift`/`pop`). [array-view.md](../array-view.md#incoming-placements) makes whole-backing retention intentional because retirement must not perform host storage writes. The composition is the gap: `push` always extends an offset view at the physical end, so a constant-size queue retains O(history). A remedy could materialize at push time when the unused prefix exceeds the live range — an ordinary mutation-time storage operation that is already allowed, not retirement-time compaction. This needs an explicit decision.
